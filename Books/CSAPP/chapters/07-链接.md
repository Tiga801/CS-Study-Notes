链接（Linking）是将各种代码和数据片段收集并组合成一个单一文件的过程，该文件可以被加载（复制）到内存中并执行。链接可以在编译时执行，即将源代码翻译成机器代码时；也可以在加载时执行，即程序被加载器（loader）加载到内存并运行时；甚至可以在运行时执行，由应用程序动态完成。在早期的计算机系统中，链接是手动完成的。在现代系统中，链接由称为链接器（linker）的程序自动完成。

链接器在软件开发中扮演着至关重要的角色，因为它支持分离编译（separate compilation）。我们可以将一个大型应用程序分解为更小、更易管理的模块，这些模块可以被单独修改和编译，而无需将整个应用程序组织为一个巨大的单一源文件。当我们修改其中某个模块时，只需重新编译它并重新链接应用程序，而不必重新编译其他文件。

链接通常由链接器静默处理，对于在入门级编程课程中构建小型程序的学生来说，链接并不是一个重要的问题。那么，为什么要学习链接呢？

- **理解链接有助于构建大型程序。** 构建大型程序的程序员经常会遇到由缺少模块、缺少库或库版本不兼容引起的链接器错误。除非你理解链接器如何解析引用、什么是库、以及链接器如何使用库来解析引用，否则这类错误将令人困惑和沮丧。

- **理解链接有助于避免危险的编程错误。** Linux 链接器在解析符号引用时所做的决策，会悄悄地影响程序的正确性。错误地定义了多个全局变量的程序，在默认情况下可以通过链接器而不产生任何警告。由此产生的程序可能表现出令人困惑的运行时行为，并且极难调试。我们将展示这是如何发生的，以及如何避免它。

- **理解链接有助于理解语言作用域规则是如何实现的。** 例如，全局变量和局部变量之间有什么区别？当你使用 `static` 属性定义变量或函数时，这究竟意味着什么？

- **理解链接有助于理解其他重要的系统概念。** 链接器生成的可执行目标文件在加载和运行程序、虚拟内存、分页以及内存映射等重要系统功能中扮演着关键角色。

- **理解链接将使你能够利用共享库。** 多年来，链接被认为是相当简单且无趣的。然而，随着共享库和动态链接在现代操作系统中的重要性日益增加，链接已经成为一个复杂的过程，为有知识的程序员提供了强大的能力。例如，许多软件产品使用共享库在运行时升级已打包的二进制程序。此外，许多 Web 服务器依赖共享库的动态链接来提供动态内容。

## 7.1 编译器驱动程序

考虑图 7.1 中的 C 程序。在本章中，它将作为一个简单的运行示例，帮助我们说明一些关于链接器工作原理的重要观点。

大多数编译系统提供一个编译器驱动程序（compiler driver），它根据用户的需要调用语言预处理器、编译器、汇编器和链接器。例如，要使用 GNU 编译系统构建示例程序，我们可以在 shell 中输入以下命令来调用 gcc 驱动程序：

```
linux> gcc -Og -o prog main.c sum.c
```

图 7.2 概述了驱动程序将示例程序从 ASCII 源文件翻译成可执行目标文件的活动。（如果你想亲自查看这些步骤，可以使用 `-v` 选项运行 gcc。）驱动程序首先运行 C 预处理器（cpp）$^{1}$，它将 C 源文件 main.c 翻译成一个 ASCII 中间文件 main.i：

---

<!-- Page 0699 -->

<div style="text-align: center;"><img src="../raw_texts/imgs/img_in_image_box_536_0_1315_535.jpg" alt="图 7.2 静态链接。链接器将可重定位目标文件组合成一个可执行目标文件 prog。" width="39%" /></div>

```
cpp [other arguments] main.c /tmp/main.i
```

接着，驱动程序运行 C 编译器（cc1），它将 main.i 翻译成一个 ASCII 汇编语言文件 main.s：

```
cc1 /tmp/main.i -Og [other arguments] -o /tmp/main.s
```

然后，驱动程序运行汇编器（as），它将 main.s 翻译成一个二进制可重定位目标文件 main.o：

```
as [other arguments] -o /tmp/main.o /tmp/main.s
```

驱动程序通过相同的过程生成 sum.o。最后，它运行链接器程序 ld，将 main.o 和 sum.o 以及必要的系统目标文件组合在一起，创建二进制可执行目标文件 prog：

```
ld -o prog [system object files and args] /tmp/main.o /tmp/sum.o
```

要运行可执行文件 prog，我们在 Linux shell 的命令行中输入其名称：

```
linux> ./prog
```

shell 调用操作系统中一个称为加载器（loader）的函数，它将可执行文件 prog 中的代码和数据复制到内存，然后将控制权转移到程序的起始位置。

## 7.2 静态链接

静态链接器（如 Linux 的 LD 程序）以一组可重定位目标文件和命令行参数作为输入，生成一个完全链接的可执行目标文件作为输出，该文件可以被加载和运行。输入的可重定位目标文件由各种代码节和数据节组成，其中每个节是一个连续的字节序列。指令存放在一个节中，已初始化的全局变量存放在另一个节中，而未初始化的变量则存放在又一个节中。

---

<!-- Page 0700 -->

为了构建可执行文件，链接器必须完成两个主要任务：

**步骤 1. 符号解析（Symbol resolution）。** 目标文件定义和引用符号，每个符号对应一个函数、一个全局变量或一个静态变量（即，任何用 `static` 属性声明的 C 变量）。符号解析的目的是将每个符号引用恰好与一个符号定义关联。

**步骤 2. 重定位（Relocation）。** 编译器和汇编器生成从地址 0 开始的代码节和数据节。链接器通过将每个符号定义与一个内存位置关联，然后修改对这些符号的所有引用，使它们指向这个内存位置，从而重定位这些节。链接器使用由汇编器生成的称为重定位条目（relocation entries）的详细指令，盲目地执行这些重定位。

接下来的各节将更详细地描述这些任务。在阅读时，请记住关于链接器的一些基本事实：目标文件仅仅是字节块的集合。其中一些块包含程序代码，另一些包含程序数据，还有一些包含指导链接器和加载器的数据结构。链接器将这些块拼接在一起，确定拼接后的块在运行时的位置，并修改代码和数据块中的各个位置。链接器对目标机器的了解极为有限。生成目标文件的编译器和汇编器已经完成了大部分工作。

## 7.3 目标文件

目标文件有三种形式：

**可重定位目标文件（Relocatable object file）。** 包含二进制代码和数据，其形式可以在编译时与其他可重定位目标文件合并，以创建可执行目标文件。

**可执行目标文件（Executable object file）。** 包含二进制代码和数据，其形式可以直接复制到内存中并执行。

**共享目标文件（Shared object file）。** 一种特殊类型的可重定位目标文件，可以在加载时或运行时被动态地加载进内存并链接。

编译器和汇编器生成可重定位目标文件（包括共享目标文件）。链接器生成可执行目标文件。从技术上讲，目标模块（object module）是一个字节序列，而目标文件（object file）是存储在磁盘文件中的目标模块。然而，我们将交替使用这两个术语。

目标文件按照特定的目标文件格式组织，不同系统的格式各异。贝尔实验室早期的 Unix 系统使用 a.out 格式。（时至今日，可执行文件仍被称为 a.out 文件。）Windows 使用可移植可执行（PE）格式。Mac OS-X 使用 Mach-O 格式。现代 x86-64 Linux 和 Unix 系统使用可执行可链接格式（ELF）。尽管我们的讨论将集中于 ELF，但无论特定格式如何，基本概念是相似的。

## 7.4 可重定位目标文件

图 7.3 展示了一个典型 ELF 可重定位目标文件的格式。ELF 头（ELF header）以一个 16 字节的序列开始，该序列描述了生成该文件的系统的字大小和字节顺序。ELF 头的其余部分包含允许链接器解析和解释目标文件的信息，包括 ELF 头的大小、目标文件类型（如可重定位、可执行或共享）、机器类型（如 x86-64）、节头部表（section header table）的文件偏移量，以及节头部表中条目的大小和数量。各节的位置和大小由节头部表描述，节头部表中包含目标文件中每个节的固定大小条目。

夹在 ELF 头和节头部表之间的是节本身。一个典型的 ELF 可重定位目标文件包含以下几个节：

- **`.text`** 已编译程序的机器代码。

- **`.rodata`** 只读数据，例如 `printf` 语句中的格式字符串，以及 `switch` 语句的跳转表。

- **`.data`** 已初始化的全局和静态 C 变量。局部 C 变量在运行时维护在栈上，不出现在 `.data` 或 `.bss` 节中。

- **`.bss`** 未初始化的全局和静态 C 变量，以及任何被初始化为零的全局或静态变量。该节在目标文件中不占实际空间；它只是一个占位符。目标文件格式区分已初始化变量和未初始化变量是为了节省空间：未初始化变量不必在目标文件中占用任何实际的磁盘空间。在运行时，这些变量在内存中被分配，初始值为零。

---

<!-- Page 0702 -->

>**旁注 为什么未初始化数据被称为 .bss？**
>
>用 `.bss` 表示未初始化数据是通用的做法。它最初是 IBM 704 汇编语言（约 1957 年）中"由符号起始的块"（block started by symbol）指令的首字母缩写，这个缩写一直沿用至今。记住 `.data` 和 `.bss` 节区别的一个简单方法是，把"bss"看作"Better Save Space!"（更好地节省空间！）的缩写。

- **`.symtab`** 一个符号表，包含程序中定义和引用的函数及全局变量的信息。一些程序员错误地认为程序必须使用 `-g` 选项编译才能获得符号表信息。实际上，每个可重定位目标文件在 `.symtab` 中都有一个符号表（除非程序员用 STRIP 命令专门删除它）。然而，与编译器内部的符号表不同，`.symtab` 符号表不包含局部变量的条目。

- **`.rel.text`** `.text` 节中需要在链接器将该目标文件与其他文件合并时修改的位置列表。一般来说，任何调用外部函数或引用全局变量的指令都需要被修改。而调用局部函数的指令则不需要修改。注意，在可执行目标文件中不需要重定位信息，通常会被省略，除非用户明确指示链接器包含它。

- **`.rel.data`** 模块引用或定义的任何全局变量的重定位信息。一般来说，任何初始值为全局变量地址或外部定义函数地址的已初始化全局变量都需要被修改。

- **`.debug`** 一个调试符号表，包含程序中定义的局部变量和类型定义的条目、程序中定义和引用的全局变量的条目，以及原始 C 源文件。只有在编译器驱动程序以 `-g` 选项调用时才会存在。

- **`.line`** 原始 C 源程序中的行号与 `.text` 节中机器代码指令之间的映射。只有在编译器驱动程序以 `-g` 选项调用时才会存在。

- **`.strtab`** 一个字符串表，用于 `.symtab` 和 `.debug` 节中的符号表，以及节头部中的节名。字符串表是一个以 null 结尾的字符串序列。

## 7.5 符号和符号表

每个可重定位目标模块 $m$ 都有一个符号表，包含由 $m$ 定义和引用的符号的信息。在链接器的上下文中，有三种不同类型的符号：

---

<!-- Page 0703 -->

- **由模块 $m$ 定义、可被其他模块引用的全局符号。** 全局链接器符号对应于非静态 C 函数和全局变量。

- **由模块 $m$ 引用、但由其他某个模块定义的全局符号。** 这类符号称为外部符号（externals），对应于在其他模块中定义的非静态 C 函数和全局变量。

- **只由模块 $m$ 定义和引用的局部符号。** 这些符号对应于用 `static` 属性定义的静态 C 函数和全局变量。这些符号在模块 $m$ 内的任何地方都可见，但不能被其他模块引用。

需要认识到，局部链接器符号与局部程序变量是不同的。`.symtab` 中的符号表不包含任何对应于局部非静态程序变量的符号。这些变量在运行时由栈管理，链接器对此不感兴趣。

有趣的是，用 C 语言 `static` 属性定义的局部过程变量不在栈上管理。相反，编译器在 `.data` 或 `.bss` 中为每个定义分配空间，并在符号表中创建一个具有唯一名称的局部链接器符号。例如，假设同一模块中的一对函数都定义了一个名为 `x` 的静态局部变量：

```c
1 int f()
2 {
3     static int x = 0;
4     return x;
5 }
6
7 int g()
8 {
9     static int x = 1;
10    return x;
11 }
```

在这种情况下，编译器向汇编器导出一对具有不同名称的局部链接器符号。例如，它可能使用 `x.1` 表示函数 `f` 中的定义，使用 `x.2` 表示函数 `g` 中的定义。

符号表由汇编器构建，使用编译器导出到汇编语言 `.s` 文件中的符号。ELF 符号表包含在 `.symtab` 节中，它包含一个条目数组。图 7.4 展示了每个条目的格式。

`name` 是字符串表中的字节偏移量，指向符号的以 null 结尾的字符串名称。`value` 是符号的地址。对于可重定位模块，`value` 是从定义该对象的节的起始位置的偏移量。对于可执行目标文件，`value` 是一个绝对运行时地址。`size` 是对象的大小（以字节为单位）。`type` 通常是数据或函数。符号表还可以包含各个节的条目。

>**旁注 C 语言新特性？用 static 隐藏变量和函数名**
>
>C 程序员使用 `static` 属性将变量和函数声明隐藏在模块内部，就像在 Java 和 C++ 中使用 public 和 private 声明一样。在 C 语言中，源文件充当模块的角色。任何用 `static` 属性声明的全局变量或函数对该模块都是私有的。类似地，任何不带 `static` 属性声明的全局变量或函数都是公有的，可以被任何其他模块访问。在可能的情况下，用 `static` 属性保护你的变量和函数是一种良好的编程实践。

```c
// code/link/elfstructs.c
1 typedef struct {
2     int     name;      /* String table offset */
3     char    type:4,    /* Function or data (4 bits) */
4             binding:4; /* Local or global (4 bits) */
5     char    reserved;  /* Unused */
6     short   section;   /* Section header index */
7     long    value;     /* Section offset or absolute address */
8     long    size;      /* Object size in bytes */
9 } Elf64_Symbol;
// code/link/elfstructs.c
```

<div style="text-align: center;">图 7.4 ELF 符号表条目。type 和 binding 字段各为 4 位。</div>

以及原始源文件路径名的条目。因此，这些对象也有不同的类型。`binding` 字段指示符号是局部的还是全局的。

每个符号被分配到目标文件的某个节，由 `section` 字段表示，该字段是节头部表的索引。有三个特殊的伪节（pseudosections），在节头部表中没有对应条目：`ABS` 用于不应被重定位的符号；`UNDEF` 用于未定义的符号——即在该目标模块中引用但在其他地方定义的符号；`COMMON` 用于尚未分配的未初始化数据对象。对于 `COMMON` 符号，`value` 字段给出对齐要求，`size` 给出最小大小。注意，这些伪节仅存在于可重定位目标文件中；在可执行目标文件中不存在。

`COMMON` 和 `.bss` 之间的区别是微妙的。现代版本的 gcc 使用以下约定将符号分配到可重定位目标文件中的 `COMMON` 和 `.bss`：

| 节 | 内容 |
|---|---|
| COMMON | 未初始化的全局变量 |
| .bss | 未初始化的静态变量，以及初始化为零的全局或静态变量 |

## 7.6 符号解析

链接器通过将每个引用与其输入的可重定位目标文件的符号表中恰好一个符号定义相关联，来解析符号引用。对于在同一模块中定义的局部符号引用，符号解析是直接的。编译器每个模块只允许每个局部符号有一个定义。编译器还确保具有局部链接器符号的静态局部变量具有唯一名称。

然而，解析全局符号的引用更为复杂。当编译器遇到一个在当前模块中未定义的符号（变量或函数名）时，它假定该符号在其他某个模块中定义，生成一个链接器符号表条目，并留给链接器处理。如果链接器无法在其任何输入模块中找到被引用符号的定义，它会打印一条（通常很晦涩的）错误信息并终止。例如，如果我们尝试在 Linux 机器上编译和链接以下源文件：

```c
void foo(void);
int main() {
    foo();
    return 0;
}
```

编译器会顺利运行，但链接器在无法解析对 `foo` 的引用时会终止：

```
linux> gcc -Wall -Og -o linkerror linkerror.c
/tmp/ccSz5uti.o: In function 'main':
/tmp/ccSz5uti.o(.text+0x7): undefined reference to 'foo'
```

全局符号的符号解析也很复杂，因为多个目标模块可能定义了同名的全局符号。在这种情况下，链接器必须要么报告一个错误，要么以某种方式选择其中一个定义并丢弃其余的。Linux 系统采用的方法涉及编译器、汇编器和链接器之间的协作，这可能会给粗心的程序员带来一些令人困惑的 bug。

<!-- Page 0707 -->

>**旁注 C++ 和 Java 中链接器符号的名称修饰**
>
>C++ 和 Java 都允许重载方法，这些方法在源代码中具有相同的名称，但参数列表不同。那么，链接器如何区分这些不同的重载函数呢？C++ 和 Java 中的重载函数之所以能工作，是因为编译器将每个唯一的方法和参数列表组合编码为链接器的唯一名称。这种编码过程称为名称修饰（mangling），而逆过程称为反修饰（demangling）。
>
>幸运的是，C++ 和 Java 使用兼容的名称修饰方案。修饰后的类名由名称中的字符数（整数）后跟原始名称组成。例如，类 `Foo` 被编码为 `3Foo`。方法被编码为原始方法名，后跟 `___`，再后跟修饰的类名，最后是每个参数的单字母编码。例如，`Foo::bar(int, long)` 被编码为 `bar__3Fooil`。类似的方案用于修饰全局变量和模板名称。

### 7.6.1 链接器如何解析重复的符号名

链接器的输入是一组可重定位目标模块。每个模块定义了一组符号，其中一些是局部的（只对定义它的模块可见），一些是全局的（对其他模块可见）。如果多个模块定义了同名的全局符号，会发生什么？以下是 Linux 编译系统使用的方法。

在编译时，编译器将每个全局符号作为强符号（strong）或弱符号（weak）导出给汇编器，汇编器将这些信息隐式地编码在可重定位目标文件的符号表中。函数和已初始化的全局变量得到强符号。未初始化的全局变量得到弱符号。

基于强符号和弱符号的概念，Linux 链接器使用以下规则处理重复的符号名：

**规则 1.** 不允许有多个同名的强符号。

**规则 2.** 如果有一个强符号和多个同名弱符号，则选择强符号。

**规则 3.** 如果有多个同名弱符号，则从这些弱符号中任意选择一个。

例如，假设我们尝试编译和链接以下两个 C 模块：

```c

{
    return 0;
}
```

```c

{
    return 0;
}
```

### 7.6.2 与静态库链接

到目前为止，我们假设链接器读取一组可重定位目标文件并将它们链接成一个输出可执行文件。实际上，所有编译系统都提供了一种将相关目标模块打包成一个称为静态库（static library）的单个文件的机制，该文件随后可以作为输入提供给链接器。当链接器构建输出可执行文件时，它只复制应用程序引用的库中的目标模块。

为什么系统支持库的概念？考虑 ISO C99，它定义了大量标准 I/O、字符串操作和整数数学函数，如 `atoi`、`printf`、`scanf`、`strcpy` 和 `rand`。它们通过

---

`libc.a` 库对每个 C 程序都可用。ISO C99 还在 `libm.a` 库中定义了大量浮点数学函数，如 `sin`、`cos` 和 `sqrt`。

考虑编译器开发人员在没有静态库的情况下向用户提供这些函数的不同方法。一种方法是让编译器识别对标准函数的调用并直接生成适当的代码。Pascal 提供了一小组标准函数，采用了这种方法，但对于 C 语言来说这是不可行的，因为 C 标准定义的标准函数数量庞大。这会给编译器增加显著的复杂性，并且每次添加、删除或修改函数时都需要新版本的编译器。然而，对于应用程序员来说，这种方法会非常方便，因为标准函数总是可用的。

另一种方法是将所有标准 C 函数放在一个可重定位目标模块中（如 `libc.o`），应用程序员可以将其链接到他们的可执行文件中：

```
linux> gcc main.c /usr/lib/libc.o
```

这种方法的优点是将标准函数的实现与编译器的实现解耦，对程序员来说仍然相当方便。然而，一个很大的缺点是系统中每个可执行文件现在都包含标准函数集合的完整副本，这极其浪费磁盘空间。（在我们的系统上，`libc.a` 大约 5 MB，`libm.a` 大约 2 MB。）更糟的是，每个运行中的程序现在在内存中都包含这些函数的副本，这极其浪费内存。另一个大缺点是，任何标准函数的任何更改，无论多小，都需要库开发人员重新编译整个源文件，这是一个耗时的操作，会使标准函数的开发和维护变得复杂。

我们可以通过为每个标准函数创建一个单独的可重定位文件并将它们存储在一个众所周知的目录中来解决其中一些问题。然而，这种方法需要应用程序员显式地将适当的目标模块链接到他们的可执行文件中，这个过程容易出错且耗时：

```
linux> gcc main.c /usr/lib/printf.o /usr/lib/scanf.o ...
```

静态库的概念就是为了解决这些不同方法的缺点而发展起来的。相关函数可以编译为单独的目标模块，然后打包在一个静态库文件中。应用程序随后可以通过在命令行上指定单个文件名来使用库中定义的任何函数。例如，使用 C 标准库和数学库中函数的程序可以用如下形式的命令编译和链接：

```

```

### 7.6.3 链接器如何使用静态库解析引用

虽然静态库很有用，但由于 Linux 链接器使用它们解析外部引用的方式，它们对程序员来说也是一个困惑的来源。在符号解析阶段，链接器按照从左到右的顺序扫描可重定位目标文件和归档，顺序与它们在编译器驱动程序命令行上出现的顺序相同。（驱动程序自动将命令行上的任何 `.c` 文件翻译成 `.o` 文件。）在此扫描过程中，链接器维护一个可重定位目标文件的集合 $E$（将合并形成可执行文件）、一个未解析符号的集合 $U$（即已引用但尚未定义的符号）以及一个在之前输入文件中已定义的符号集合 $D$。初始时，$E$、$U$ 和 $D$ 均为空。

- 对于命令行上的每个输入文件 $f$，链接器确定 $f$ 是目标文件还是归档。如果 $f$ 是目标文件，链接器将 $f$ 添加到 $E$，更新 $U$ 和 $D$ 以反映 $f$ 中的符号定义和引用，然后继续处理下一个输入文件。

- 如果 $f$ 是归档，链接器尝试将 $U$ 中的未解析符号与归档成员定义的符号匹配。如果某个归档成员 $m$ 定义了一个解析 $U$ 中引用的符号，则将 $m$ 添加到 $E$，链接器更新 $U$ 和 $D$ 以反映 $m$ 中的符号定义和引用。此过程在归档的成员目标文件上迭代，直到达到 $U$ 和 $D$ 不再变化的不动点。此时，不在 $E$ 中的任何成员目标文件都被简单地丢弃，链接器继续处理下一个输入文件。

- 如果链接器完成扫描命令行上的输入文件后 $U$ 不为空，它打印错误并终止。否则，它合并并重定位 $E$ 中的目标文件，以构建输出可执行文件。

不幸的是，这种算法可能导致一些令人困惑的链接时错误，因为命令行上库和目标文件的顺序很重要。如果定义符号的库在命令行上出现在引用该符号的目标文件之前，那么该引用将无法解析，链接将失败。例如，考虑以下情况：

```
linux> gcc -static ./libvector.a main2.c
/tmp/cc9XH6Rp.o: In function 'main':
/tmp/cc9XH6Rp.o(.text+0x18): undefined reference to 'addvec'
```

发生了什么？当处理 `libvector.a` 时，$U$ 为空，所以 `libvector.a` 中没有成员目标文件被添加到 $E$。因此，对 `addvec` 的引用永远无法解析，链接器发出错误信息并终止。

---

<!-- Page 0716 -->

关于库的一般规则是将它们放在命令行的末尾。如果不同库的成员是独立的，即没有成员引用另一个成员定义的符号，那么这些库可以以任何顺序放在命令行的末尾。另一方面，如果这些库不是独立的，那么它们必须按照这样的顺序排列：对于归档成员外部引用的每个符号 $s$，至少有一个 $s$ 的定义在命令行上位于对 $s$ 的引用之后。例如，假设 foo.c 调用 libx.a 和 libz.a 中的函数，这些函数又调用 liby.a 中的函数。那么 libx.a 和 libz.a 必须在命令行上先于 liby.a：

```

```

如果有必要满足依赖要求，库可以在命令行上重复出现。例如，假设 foo.c 调用 libx.a 中的函数，该函数调用 liby.a 中的函数，该函数又调用 libx.a 中的函数。那么 libx.a 必须在命令行上重复出现：

```

```

或者，我们可以将 libx.a 和 liby.a 合并成一个归档。

## 7.7 重定位

一旦链接器完成了符号解析步骤，它就将代码中的每个符号引用与其输入目标模块中的一个符号定义（即某个输入目标模块的符号表条目）关联起来了。此时，链接器知道其输入目标模块中代码节和数据节的确切大小。现在它可以开始重定位步骤了，在这个步骤中，它合并输入模块并为每个符号分配运行时地址。重定位由两步组成：

1. **重定位节和符号定义。** 在这一步中，链接器将相同类型的所有节合并成一个同类型的新聚合节。例如，输入模块中的所有 `.data` 节被合并成一个节，它将成为输出可执行目标文件的 `.data` 节。

---

<!-- Page 0717 -->

链接器随后为新的聚合节、输入模块定义的每个节以及输入模块定义的每个符号分配运行时内存地址。当这一步完成时，程序中的每条指令和全局变量都有了唯一的运行时内存地址。

2. **重定位节中的符号引用。** 在这一步中，链接器修改代码节和数据节体中的每个符号引用，使它们指向正确的运行时地址。为了执行这一步，链接器依赖于可重定位目标模块中称为重定位条目（relocation entries）的数据结构，我们接下来描述这些数据结构。

### 7.7.1 重定位条目

当汇编器生成目标模块时，它不知道代码和数据最终将被存储在内存的什么位置。它也不知道被模块引用的任何外部定义的函数或全局变量的位置。因此，每当汇编器遇到对一个最终位置未知的对象的引用时，它就生成一个重定位条目，告诉链接器在将目标文件合并成可执行文件时如何修改该引用。代码的重定位条目存放在 `.rel.text` 中，数据的重定位条目存放在 `.rel.data` 中。

图 7.9 展示了 ELF 重定位条目的格式。`offset` 是需要修改的引用的节偏移量。`symbol` 标识修改后的引用应指向的符号。`type` 告诉链接器如何修改新的引用。`addend` 是一个有符号常数，某些类型的重定位用它来偏置修改后引用的值。

```c
// code/link/elfstructs.c
typedef struct {
    long offset;    /* 要重定位的引用的偏移量 */
    long type:32,   /* 重定位类型 */
         symbol:32; /* 符号表索引 */
    long addend;    /* 重定位表达式的常数部分 */
} Elf64_Rela;
// code/link/elfstructs.c
```

ELF 定义了 32 种不同的重定位类型，许多都相当难懂。我们只关注两种最基本的重定位类型：

**`R_X86_64_PC32`。** 重定位使用 32 位 PC 相对地址的引用。回想 3.6.3 节，PC 相对地址是当前程序计数器（PC）运行时值的偏移量。当 CPU 使用 PC 相对寻址执行指令时，它通过将指令中编码的 32 位值与 PC 的当前运行时值（总是内存中下一条指令的地址）相加，来形成有效地址（例如，call 指令的目标）。

**`R_X86_64_32`。** 重定位使用 32 位绝对地址的引用。使用绝对寻址，CPU 直接使用指令中编码的 32 位值作为有效地址，无需进一步修改。

这两种重定位类型支持 x86-64 小代码模型（small code model），该模型假设可执行目标文件中代码和数据的总大小小于 2 GB，因此可以在运行时使用 32 位 PC 相对地址访问。小代码模型是 gcc 的默认设置。大于 2 GB 的程序可以使用 `-mcmodel=medium`（中代码模型）和 `-mcmodel=large`（大代码模型）标志编译，但我们不讨论这些。

### 7.7.2 重定位符号引用

图 7.10 展示了链接器重定位算法的伪代码。第 1 行和第 2 行遍历每个节 $s$ 以及与每个节关联的每个重定位条目 $r$。具体地，假设每个节 $s$ 是一个字节数组，每个重定位条目 $r$ 是类型为 `Elf64_Rela` 的结构体（如图 7.9 所定义）。还假设当算法运行时，链接器已经为每个节（记为 $ADDR(s)$）和每个符号（记为 $ADDR(r.symbol)$）选定了运行时地址。第 3 行计算需要重定位的 4 字节引用在 $s$ 数组中的地址。如果该引用使用 PC 相对寻址，则由第 5–9 行重定位。如果引用使用绝对寻址，则由第 11–13 行重定位。

```
foreach section s {
    foreach relocation entry r {
        refptr = s + r.offset; /* ptr to reference to be relocated */

        /* Relocate a PC-relative reference */
        if (r.type == R_X86_64_PC32) {
            refaddr = ADDR(s) + r.offset; /* ref's run-time address */
            *refptr = (unsigned) (ADDR(r.symbol) + r.addend - refaddr);
        }

        /* Relocate an absolute reference */
        if (r.type == R_X86_64_32)
            *refptr = (unsigned) (ADDR(r.symbol) + r.addend);
    }
}
```

## 7.9 加载可执行目标文件

要运行可执行目标文件 prog，我们可以在 Linux shell 的命令行中输入其名称：

```
linux> ./prog
```

由于 prog 不对应于内置的 shell 命令，shell 假设 prog 是一个可执行目标文件，并通过调用一段称为加载器（loader）的内存驻留操作系统代码来为我们运行它。任何 Linux 程序都可以通过调用 `execve` 函数来调用加载器，我们将在 8.4.6 节中详细描述该函数。加载器将可执行目标文件中的代码和数据从磁盘复制到内存，然后通过跳转到程序的第一条指令（即入口点）来运行该程序。这个将程序复制到内存然后运行的过程称为加载（loading）。

每个运行中的 Linux 程序都有一个类似于图 7.15 所示的运行时内存映像。在 Linux x86-64 系统上，代码段从地址 `0x400000` 开始，随后是数据段。运行时堆紧随数据段之后，通过对 `malloc` 库的调用向上增长。（我们将在 9.9 节中详细描述 `malloc` 和堆。）接下来是为共享模块保留的区域。用户栈从最大合法用户地址（$2^{48} - 1$）以下开始，向下增长，指向较小的内存地址。栈上方、从地址 $2^{48}$ 开始的区域，为内核的代码和数据保留，内核是操作系统的内存驻留部分。

## 7.10 动态链接共享库

我们在 7.6.2 节中研究的静态库解决了许多与向应用程序提供大型相关函数集合相关的问题。然而，静态库仍然有一些重大缺点。静态库与所有软件一样，需要定期维护和更新。如果应用程序员想使用最新版本的库，他们必须以某种方式知道库已更改，然后明确地将他们的程序重新链接到更新后的库。

另一个问题是，几乎每个 C 程序都使用标准 I/O 函数，如 `printf` 和 `scanf`。在运行时，这些函数的代码在每个运行进程的文本段中都被复制了一份。在典型的运行着数百个进程的系统上，这可能是对稀缺内存系统资源的大量浪费。（内存有一个有趣的特性：无论系统有多少内存，它总是稀缺的资源。）

>**旁注 加载器究竟是如何工作的？**

>对于迫不及待的读者，这里是加载真正工作方式的预览：Linux 系统中的每个程序都在具有自己虚拟地址空间的进程上下文中运行。当 shell 运行程序时，父 shell 进程 fork 出一个作为父进程副本的子进程。子进程通过 `execve` 系统调用调用加载器。加载器删除子进程现有的虚拟内存段，并创建新的代码段、数据段、堆段和栈段。新的栈段和堆段被初始化为零。新的代码段和数据段通过将虚拟地址空间中的页面映射到可执行文件的页面大小块，来初始化为可执行文件的内容。最后，加载器跳转到 `_start` 地址，这最终调用应用程序的 `main` 例程。除了一些头部信息外，加载过程中没有从磁盘到内存的数据复制。复制被推迟到 CPU 引用映射的虚拟页面时，此时操作系统使用其分页机制自动将该页面从磁盘传输到内存。

共享库是解决静态库缺点的现代创新。共享库是一个目标模块，可以在运行时或加载时被加载到任意内存地址，并与内存中的程序链接。这个过程称为动态链接（dynamic linking），由称为动态链接器（dynamic linker）的程序执行。共享库也被称为共享目标（shared objects），在 Linux 系统上以 `.so` 后缀标识。微软操作系统大量使用共享库，称之为 DLL（动态链接库）。

共享库在两种不同的意义上是"共享的"。首先，在任何给定的文件系统中，特定库只有一个 `.so` 文件。该 `.so` 文件中的代码和数据被所有引用该库的可执行目标文件共享，而静态库的内容则被复制并嵌入到引用它们的可执行文件中。其次，共享库 `.text` 节在内存中的单个副本可以被不同的运行进程共享。我们将在第 9 章研究虚拟内存时更详细地探讨这个问题。

## 7.11 从应用程序中加载和链接共享库

到目前为止，我们讨论了动态链接器在应用程序加载时（即执行前）加载和链接共享库的场景。然而，应用程序也可以在运行时请求动态链接器加载和链接任意共享库，而不必在编译时将应用程序链接到这些库。

动态链接是一种强大而有用的技术。以下是一些实际应用示例：

- **软件发布。** 微软 Windows 应用程序的开发者经常使用共享库来发布软件更新。他们生成共享库的新副本，用户可以下载并用作当前版本的替代。下次用户运行应用程序时，它将自动链接和加载新的共享库。

- **构建高性能 Web 服务器。** 许多 Web 服务器生成动态内容，如个性化网页、账户余额和横幅广告。早期 Web 服务器通过使用 `fork` 和 `execute` 创建子进程，并在子进程上下文中运行"CGI 程序"来生成动态内容。然而，现代高性能 Web 服务器可以使用基于动态链接的更高效、更复杂的方法来生成动态内容。

这个思路是将每个生成动态内容的函数打包在一个共享库中。当来自 Web 浏览器的请求到达时，服务器动态加载并链接适当的函数，然后直接调用它，而不是使用 `fork` 和 `execute` 在子进程上下文中运行函数。该函数被缓存在服务器的地址空间中，因此后续请求只需一次简单的函数调用即可处理。这对繁忙站点的吞吐量有显著影响。此外，现有函数可以在运行时更新，新函数可以在不停止服务器的情况下添加。

Linux 系统为动态链接器提供了一个简单的接口，允许应用程序在运行时加载和链接共享库：

```c
#include <dlfcn.h>
void *dlopen(const char *filename, int flag);
/* 返回：成功则返回指向句柄的指针，出错则返回 NULL */
```

`dlopen` 函数加载并链接共享库 `filename`。`filename` 中的外部符号使用之前用 `RTLD_GLOBAL` 标志打开的库来解析。如果当前可执行文件是用 `-rdynamic` 标志编译的，那么其全局符号也可用于符号解析。`flag` 参数必须包含 `RTLD_NOW`（告诉链接器立即解析对外部符号的引用）或 `RTLD_LAZY`（指示链接器推迟符号解析，直到执行库中的代码）之一。这些值中的任意一个都可以与 `RTLD_GLOBAL` 标志进行 OR 运算。

```c
#include <dlfcn.h>
void *dlsym(void *handle, char *symbol);
/* 返回：成功则返回指向符号的指针，出错则返回 NULL */
```

`dlsym` 函数接受一个指向已打开共享库的句柄和一个符号名，返回该符号的地址（如果存在），否则返回 NULL。

```c
#include <dlfcn.h>
int dlclose(void *handle);
/* 返回：成功则返回 0，出错则返回 -1 */
```

`dlclose` 函数在没有其他共享库仍在使用它的情况下，卸载该共享库。

```c
#include <dlfcn.h>
const char *dlerror(void);
/* 返回：若 dlopen、dlsym 或 dlclose 的前一次调用失败，则返回错误消息；
   若前一次调用成功，则返回 NULL */
```

`dlerror` 函数返回一个字符串，描述调用 `dlopen`、`dlsym` 或 `dlclose` 时发生的最近一次错误，如果没有错误则返回 NULL。

```c

    addvec(x, y, z, 2);

    if (dlclose(handle) < 0) {

        exit(1);
    }
    return 0;

## 7.12 位置无关代码（PIC）

共享库的一个关键目的是允许多个运行进程在内存中共享相同的库代码，从而节省宝贵的内存资源。那么，多个进程如何共享程序的单个副本呢？一种方法是为每个共享库先验地分配一块专用的地址空间，然后要求加载器始终将共享库加载到该地址。虽然这种方法直接，但会产生一些严重问题。这会低效地使用地址空间，因为即使进程不使用该库，空间的部分也会被分配。管理起来也会很困难。我们必须确保没有任何块相互重叠。每次修改库时，我们都必须确保它仍然适合其分配的块。如果不适合，我们就必须找一个新块。如果我们创建一个新库，我们必须为它找到空间。随着时间的推移，考虑到系统中数百个库和库版本，要防止地址空间碎片化成许多小的未使用但不可用的空洞，将会很困难。更糟的是，库到内存的分配在每个系统上都会不同，从而产生更多的管理麻烦。

为了避免这些问题，现代系统编译共享模块的代码段，使它们可以加载到内存中的任意位置，而无需被链接器修改。通过这种方法，共享模块代码段的单个副本可以被无限数量的进程共享。（当然，每个进程仍然会获得读/写数据段的自己的副本。）

可以在不需要任何重定位的情况下加载的代码称为位置无关代码（PIC）。用户通过向 gcc 传递 `-fpic` 选项来指示 GNU 编译系统生成 PIC 代码。共享库必须始终使用此选项编译。

在 x86-64 系统上，对同一可执行目标模块中符号的引用不需要特殊处理即可成为 PIC。这些引用可以使用 PC 相对寻址编译，并在链接器构建目标文件时由静态链接器重定位。然而，对共享模块定义的外部过程和全局变量的引用需要一些特殊技术，我们接下来描述这些技术。

这些条目负责调用特定函数。PLT[1]（此处未显示）调用系统启动函数（`__libc_start_main`），它初始化执行环境、调用 `main` 函数并处理其返回值。从 PLT[2] 开始的条目调用用户代码调用的函数。在我们的示例中，PLT[2] 调用 `addvec`，PLT[3]（未显示）调用 `printf`。

**全局偏移表（GOT）。** 如我们所见，GOT 是一个由 8 字节地址条目组成的数组。与 PLT 结合使用时，GOT[0] 和 GOT[1] 包含动态链接器在解析函数地址时使用的信息。GOT[2] 是 `ld-linux.so` 模块中动态链接器的入口点。其余的每个条目对应一个需要在运行时解析地址的被调用函数。每个条目都有一个匹配的 PLT 条目。例如，GOT[4] 和 PLT[2] 对应 `addvec`。最初，每个 GOT 条目指向对应 PLT 条目中的第二条指令。

图 7.19(a) 展示了 GOT 和 PLT 如何协同工作，在第一次调用函数 `addvec` 时懒惰地解析其运行时地址：

**步骤 1.** 程序不是直接调用 `addvec`，而是调用 PLT[2]，即 `addvec` 的 PLT 条目。

**步骤 2.** 第一条 PLT 指令通过 GOT[4] 做间接跳转。由于每个 GOT 条目最初指向其对应 PLT 条目中的第二条指令，间接跳转只是将控制权传递回 PLT[2] 中的下一条指令。

**步骤 3.** 将 `addvec` 的 ID（`0x1`）压入栈后，PLT[2] 跳转到 PLT[0]。

**步骤 4.** PLT[0] 通过 GOT[1] 间接为动态链接器压入一个参数，然后通过 GOT[2] 间接跳转到动态链接器。动态链接器使用两个栈条目来确定 `addvec` 的运行时位置，用这个地址覆写 GOT[4]，然后将控制权传递给 `addvec`。

图 7.19(b) 展示了后续调用 `addvec` 的控制流：

**步骤 1.** 控制权像以前一样传递到 PLT[2]。

**步骤 2.** 然而，这次通过 GOT[4] 的间接跳转将控制权直接传递给 `addvec`。

## 7.13 库打桩

Linux 链接器支持一种称为库打桩（library interpositioning）的强大技术，它允许你拦截对共享库函数的调用并执行你自己的代码。使用打桩，你可以追踪某个特定

---

<!-- Page 0735 -->

库函数被调用的次数，验证并追踪其输入和输出值，甚至用完全不同的实现来替换它。

基本思路如下：给定一个要打桩的目标函数，你创建一个原型与目标函数相同的包装函数（wrapper function）。使用某种特定的打桩机制，你欺骗系统调用包装函数而不是目标函数。包装函数通常执行自己的逻辑，然后调用目标函数，并将其返回值传递给调用者。

打桩可以在编译时、链接时或程序加载执行时的运行时发生。为了探索这些不同的机制，我们将使用图 7.20(a) 中的示例程序作为运行示例。它调用 C 标准库（`libc.so`）中的 `malloc` 和 `free` 函数。对 `malloc` 的调用从堆中分配一个 32 字节的块，并返回指向该块的指针。对 `free` 的调用将该块还给堆，以供后续对 `malloc` 的调用使用。我们的目标是使用打桩追踪程序运行时对 `malloc` 和 `free` 的调用。

### 7.13.1 编译时打桩

图 7.20 展示了如何使用 C 预处理器在编译时进行打桩。`mymalloc.c`（图 7.20(c)）中的每个包装函数调用目标函数，打印一个跟踪，然后返回。本地头文件 `malloc.h`（图 7.20(b)）指示预处理器将每个对目标函数的调用替换为对其包装函数的调用。以下是编译和链接程序的方法：

```

linux> gcc -I. -o intc int.c mymalloc.o

打桩发生是因为 `-I.` 参数，它告诉 C 预处理器在查找通常的系统目录之前，先在当前目录中查找 `malloc.h`。注意，`mymalloc.c` 中的包装函数是用标准 `malloc.h` 头文件编译的。

## 7.15 小结

链接可以在编译时由静态链接器执行，也可以在加载时和运行时由动态链接器执行。链接器操作称为目标文件的二进制文件，有三种不同形式：可重定位、可执行和共享。可重定位目标文件由静态链接器组合成可加载到内存并执行的可执行目标文件。共享目标文件（共享库）在运行时由动态链接器链接和加载，要么在调用程序加载并开始执行时隐式进行，要么在程序调用 `dlopen` 库中的函数时按需进行。

链接器的两个主要任务是符号解析（将目标文件中的每个全局符号与唯一定义绑定）和重定位（确定每个符号的最终内存地址，并修改对这些对象的引用）。

静态链接器由 GCC 等编译器驱动程序调用。它们将多个可重定位目标文件合并成单个可执行目标文件。多个目标文件可以定义相同的符号，链接器用于静默解析这些多重定义的规则可能会在用户程序中引入微妙的 bug。

多个目标文件可以被拼接成一个静态库。链接器使用库来解析其他目标模块中的符号引用。许多链接器使用的从左到右的顺序扫描来解析符号引用是另一个令人困惑的链接时错误来源。

---

<!-- Page 0741 -->

加载器将可执行文件的内容映射到内存并运行程序。链接器还可以生成部分链接的可执行目标文件，其中包含对共享库中定义的例程和数据的未解析引用。在加载时，加载器将部分链接的可执行文件映射到内存，然后调用动态链接器，动态链接器通过加载共享库并重定位程序中的引用来完成链接任务。

编译为位置无关代码的共享库可以加载到任意位置，并在运行时被多个进程共享。应用程序也可以在运行时使用动态链接器来加载、链接和访问共享库中的函数和数据。
