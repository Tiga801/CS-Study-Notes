系统中的进程与其他进程共享 CPU 和主内存。然而，共享主内存带来了一些特殊的挑战。随着对 CPU 需求的增加，进程以某种合理平稳的方式减慢速度。但如果太多进程需要太多内存，那么其中一些进程将根本无法运行。当程序空间耗尽时，就无路可走了。内存也容易受到损坏。如果某个进程不小心写入了另一个进程使用的内存，那么该进程可能会以某种令人困惑的方式失败，这与程序逻辑完全无关。

为了更高效、更少出错地管理内存，现代系统提供了一种对主内存的抽象，称为虚拟内存（VM, Virtual Memory）。虚拟内存是硬件异常、硬件地址翻译、主内存、磁盘文件和内核软件的优雅交互，为每个进程提供一个大型、统一且私有的地址空间。通过一种简洁的机制，虚拟内存提供了三项重要能力：（1）通过将主内存视为存储在磁盘上的地址空间的高速缓存来高效使用主内存，只在主内存中保留活跃区域，并根据需要在磁盘和内存之间传输数据。（2）通过为每个进程提供统一的地址空间来简化内存管理。（3）通过保护每个进程的地址空间不被其他进程破坏来确保安全。

虚拟内存是计算机系统中最伟大的思想之一。它成功的一个主要原因在于它默默地、自动地工作，无需应用程序员的任何干预。既然虚拟内存在幕后工作得如此出色，程序员为什么还需要理解它呢？原因有以下几点。

- 虚拟内存是核心所在。虚拟内存贯穿计算机系统的各个层次，在硬件异常、汇编器、链接器、加载器、共享目标文件、文件和进程的设计中扮演着关键角色。理解虚拟内存将有助于你更好地理解系统的整体工作原理。

- 虚拟内存功能强大。虚拟内存赋予应用程序强大的能力，可以创建和销毁内存块、将内存块映射到磁盘文件的某些部分，以及与其他进程共享内存。例如，你是否知道可以通过读写内存位置来读取或修改磁盘文件的内容？或者可以不做任何显式复制就将文件内容加载到内存中？理解虚拟内存将帮助你在应用程序中充分利用其强大功能。

- 虚拟内存具有危险性。每当应用程序引用变量、解引用指针或调用动态分配包（如 malloc）时，都会与虚拟内存交互。如果虚拟内存使用不当，应用程序可能遭受令人困惑且隐蔽的内存相关错误。例如，带有错误指针的程序可能立即因"段错误"或"保护故障"而崩溃，也可能在崩溃前静默运行数小时，或者——最令人担忧的——以错误结果运行至完成。理解虚拟内存以及管理它的分配包（如 malloc）可以帮助你避免这些错误。

## 9.1 物理寻址与虚拟寻址

计算机系统的主内存被组织为一个由 M 个连续字节大小单元组成的数组。每个字节都有一个唯一的物理地址（PA）。第一个字节的地址为 0，下一个字节的地址为 1，再下一个字节的地址为 2，以此类推。给定这种简单的组织方式，CPU 访问内存最自然的方式是使用物理地址。我们称这种方法为物理寻址。图 9.1 展示了在执行读取从物理地址 4 开始的 4 字节字的加载指令时，物理寻址的示例。当 CPU 执行加载指令时，它生成一个有效的物理地址并通过内存总线将其传递到主内存。主内存取出从物理地址 4 开始的 4 字节字并将其返回给 CPU，CPU 将其存储在寄存器中。

早期的 PC 使用物理寻址，数字信号处理器、嵌入式微控制器和 Cray 超级计算机等系统至今仍然如此。然而，现代处理器使用一种称为虚拟寻址的寻址方式，如图 9.2 所示。

## 9.2 地址空间

地址空间是一个由非负整数地址组成的有序集合：

$$\{0, 1, 2, \cdots\}$$

如果地址空间中的整数是连续的，我们就称它为线性地址空间。为简化讨论，我们始终假设线性地址空间。在具有虚拟内存的系统中，CPU 从一个包含 $N = 2^n$ 个地址的地址空间中生成虚拟地址，该地址空间称为虚拟地址空间：

$$\{0, 1, 2, \cdots, N-1\}$$

地址空间的大小由表示最大地址所需的位数来表征。例如，包含 $N = 2^n$ 个地址的虚拟地址空间称为 n 位地址空间。现代系统通常支持 32 位或 64 位虚拟地址空间。

系统还有一个与系统中 M 字节物理内存对应的物理地址空间：

$$\{0, 1, 2, \cdots, M-1\}$$

M 不必是 2 的幂，但为简化讨论，我们假设 $M = 2^m$。

地址空间的概念很重要，因为它在数据对象（字节）和它们的属性（地址）之间做出了清晰的区分。一旦我们认识到这种区分，就可以进行推广，允许每个数据对象拥有多个独立的地址，每个地址从不同的地址空间中选取。这就是虚拟内存的基本思想。主内存中的每个字节都有一个从虚拟地址空间中选取的虚拟地址，以及一个从物理地址空间中选取的物理地址。

## 9.3 虚拟内存作为高速缓存的工具

从概念上讲，虚拟内存被组织为存储在磁盘上的 N 个连续字节大小单元的数组。每个字节都有一个唯一的虚拟地址，作为数组的索引。磁盘上的数组内容被缓存在主内存中。与内存层次结构中的其他高速缓存一样，磁盘上的数据（较低层）被划分为块，作为磁盘和主内存（较高层）之间的传输单元。VM 系统通过将虚拟内存划分为称为虚拟页（VP, Virtual Page）的固定大小块来处理这一问题。每个虚拟页的大小为 $P = 2^p$ 字节。类似地，物理内存被划分为物理页（PP, Physical Page），也是 P 字节大小。（物理页也称为页帧。）

在任意时刻，虚拟页的集合被划分为三个不相交的子集：

**未分配的（Unallocated）**。VM 系统尚未分配（或创建）的页。未分配的块没有与之关联的任何数据，因此不占用磁盘上的任何空间。

**已缓存的（Cached）**。当前缓存在物理内存中的已分配页。

**未缓存的（Uncached）**。未缓存在物理内存中的已分配页。

### 9.3.1 DRAM 高速缓存的组织

为了帮助区分内存层次结构中的不同高速缓存，我们将使用术语 SRAM 高速缓存来表示 CPU 和主内存之间的 L1、L2 和 L3 缓存存储器，使用术语 DRAM 高速缓存来表示 VM 系统在主内存中缓存虚拟页的高速缓存。

DRAM 高速缓存在内存层次结构中的位置对其组织方式有很大影响。回想一下，DRAM 至少比 SRAM 慢 10 倍，而磁盘大约比 DRAM 慢 100,000 倍。因此，与 SRAM 高速缓存的缺失相比，DRAM 高速缓存的缺失代价非常昂贵，因为 DRAM 高速缓存的缺失由磁盘提供服务，而 SRAM 高速缓存的缺失通常由基于 DRAM 的主内存提供服务。此外，从磁盘扇区读取第一个字节的代价大约比读取扇区中连续字节慢 100,000 倍。总之，DRAM 高速缓存的组织完全由缺失的巨大代价所驱动。

由于巨大的缺失惩罚和访问第一个字节的高代价，虚拟页往往很大——通常为 4 KB 到 2 MB。由于缺失惩罚很大，DRAM 高速缓存是全相联的；也就是说，任何虚拟页都可以放置在任何物理页中。缺失时的替换策略也变得更加重要，因为替换错误虚拟页的惩罚非常高。因此，操作系统为 DRAM 高速缓存使用的替换算法比硬件为 SRAM 高速缓存使用的算法复杂得多。（这些替换算法超出了本书的讨论范围。）最后，由于磁盘的访问时间很长，DRAM 高速缓存总是使用写回而不是直写。

虚拟页存储在磁盘的哪个位置，在物理内存中选择一个受害页，并将虚拟页从磁盘复制到 DRAM，替换受害页。

### 9.3.3 页命中

考虑 CPU 读取 VP 2 中包含的虚拟内存字时会发生什么，VP 2 已缓存在 DRAM 中（图 9.5）。使用我们将在 9.6 节详细描述的技术，地址翻译硬件使用虚拟地址作为索引来定位 PTE 2 并从内存中读取它。由于有效位已设置，地址翻译硬件知道 VP 2 已缓存在内存中。因此，它使用 PTE 中的物理内存地址（指向 PP 1 中缓存页的起始位置）来构造该字的物理地址。

### 9.3.4 页故障

在虚拟内存术语中，DRAM 高速缓存缺失称为页故障（page fault）。图 9.6 展示了故障发生前示例页表的状态。CPU 已引用 VP 3 中的一个字，而 VP 3 未缓存在 DRAM 中。地址翻译硬件从内存中读取 PTE 3，从有效位推断 VP 3 未缓存，并触发页故障异常。页故障异常处理程序调用内核中的页故障异常处理程序，该处理程序选择一个受害页——在本例中为存储在 PP 3 中的 VP 4。如果 VP 4 已被修改，则内核将其复制回磁盘。无论如何，内核修改 VP 4 的页表条目，以反映 VP 4 不再缓存在主内存中的事实。

### 9.3.6 局部性的再次拯救

当我们许多人第一次了解虚拟内存的思想时，最初的印象往往是它一定效率极低。鉴于巨大的缺失惩罚，我们担心分页会破坏程序性能。在实践中，虚拟内存工作得很好，主要得益于我们的老朋友——局部性。

尽管程序在整个运行过程中引用的不同页的总数可能超过物理内存的总大小，但局部性原理承诺，在任意时刻，程序倾向于在一个较小的称为工作集（working set）或常驻集（resident set）的活跃页集合上工作。在初始开销（将工作集分页到内存中）之后，对工作集的后续引用产生命中，不会产生额外的磁盘流量。

只要我们的程序具有良好的时间局部性，虚拟内存系统就工作得相当好。但当然，并非所有程序都表现出良好的时间局部性。如果工作集大小超过物理内存的大小，那么程序可能会产生一种称为颠簸（thrashing）的不幸情况，即页面被连续不断地换入换出。尽管虚拟内存通常是高效的，但如果程序的性能降至极低，明智的程序员会考虑它是否正在颠簸。

## 9.4 虚拟内存作为内存管理的工具

在上一节中，我们看到了虚拟内存如何提供一种机制，使用 DRAM 来缓存来自通常更大的虚拟地址空间中的页。有趣的是，一些早期系统（如 DEC PDP-11/70）支持比可用物理内存还小的虚拟地址空间。然而虚拟内存仍然是一种有用的机制，因为它极大地简化了内存管理，并提供了一种保护内存的自然方式。

到目前为止，我们假设了一个将单个虚拟地址空间映射到物理地址空间的单一页表。实际上，操作系统为每个进程提供一个独立的页表，从而提供一个独立的虚拟地址空间。图 9.9 展示了基本思想。在示例中，进程 i 的页表将 VP 1 映射到 PP 2，将 VP 2 映射到 PP 7。类似地，进程 j 的页表将 VP 1 映射到 PP 7，将 VP 2 映射到 PP 10。注意，多个虚拟页可以映射到同一个共享物理页。

按需调页与独立虚拟地址空间的结合对系统中内存的使用和管理方式产生了深远影响。特别是，虚拟内存简化了链接和加载、代码和数据的共享，以及向应用程序分配内存。

- **简化链接**。独立的地址空间允许每个进程对其内存映像使用相同的基本格式，而不管代码和数据实际驻留在物理内存中的什么位置。例如，如我们在图 8.13 中所见，给定 Linux 系统上的每个进程都有相似的内存格式。对于 64 位地址空间，代码段总是从虚拟地址 0x400000 开始。数据段在适当的对齐间隙之后紧随代码段。栈占用用户进程地址空间的最高部分，

---

<!-- Page 0837 -->

并向下增长。这种统一性极大地简化了链接器的设计和实现，使其能够生成与代码和数据在物理内存中最终位置无关的完全链接的可执行文件。

- **简化加载**。虚拟内存还使得将可执行文件和共享目标文件加载到内存变得容易。为了将目标文件的 `.text` 和 `.data` 节加载到新创建的进程中，Linux 加载器为代码和数据段分配虚拟页，将它们标记为无效（即未缓存），并将其页表条目指向目标文件中的相应位置。有趣的是，加载器实际上从不将任何数据从磁盘复制到内存中。数据由虚拟内存系统在每个页第一次被引用时自动按需调入——无论是 CPU 取指令时还是执行指令引用内存位置时。

  将一组连续的虚拟页映射到任意文件中任意位置的概念称为内存映射（memory mapping）。Linux 提供了一个称为 `mmap` 的系统调用，允许应用程序自行进行内存映射。我们将在 9.8 节更详细地描述应用程序级别的内存映射。

- **简化共享**。独立的地址空间为操作系统提供了一种一致的机制来管理用户进程之间以及操作系统本身之间的共享。通常，每个进程都有自己的私有代码、数据、堆和栈区域，不与任何其他进程共享。在这种情况下，操作系统创建的页表将对应的虚拟页映射到不相交的物理页。

  然而，在某些情况下，进程共享代码和数据是可取的。例如，每个进程都必须调用相同的操作系统内核代码，每个 C 程序都会调用标准 C 库中的例程，如 `printf`。操作系统不必在每个进程中包含内核和标准 C 库的单独副本，而是可以通过将不同进程中的相应虚拟页映射到相同的物理页，来安排多个进程共享这些代码的单个副本，正如我们在图 9.9 中所看到的。

- **简化内存分配**。虚拟内存为用户进程分配额外内存提供了一种简单的机制。当用户进程中运行的程序请求额外的堆空间时（例如，调用 `malloc` 的结果），操作系统分配适当数量（比如 k 个）的连续虚拟内存页，并将它们映射到位于物理内存任意位置的 k 个任意物理页。由于页表的工作方式，操作系统无需定位物理内存中 k 个连续的页。这些页可以随机分散在物理内存中。

### 9.6.2 利用 TLB 加速地址翻译

### 9.6.3 多级页表

到目前为止，我们假设系统使用单一页表进行地址翻译。但如果我们有一个 32 位地址空间、4 KB 的页以及 4 字节的 PTE，那么我们将需要一个始终驻留在内存中的 4 MB 页表，即使应用程序只引用了虚拟地址空间的一小部分。对于具有 64 位地址空间的系统，问题更为严重。

压缩页表的常用方法是使用页表层次结构。通过一个具体示例最容易理解这个思想。考虑一个 32 位虚拟地址空间，被划分为 4 KB 的页，页表条目各为 4 字节。还假设此时虚拟地址空间具有以下形式：内存的前 2K 个页分配给代码和数据，接下来的 6K 个页未分配，再接下来的 1023 个页也未分配，最后一个页分配给用户栈。图 9.17 展示了如何为这个虚拟地址空间构造两级页表层次结构。

第 1 级表中的每个 PTE 负责映射 4 MB 的虚拟地址空间块，其中每个块由 1024 个连续页组成。例如，PTE 0 映射第一个块，PTE 1 映射下一个块，依此类推。由于地址空间为 4 GB，1024 个 PTE 足以覆盖整个空间。

如果块 i 中的每个页都未分配，则第 1 级 PTE i 为空。例如，在图 9.17 中，块 2–7 未分配。但是，如果块 i 中至少有一个页被分配，则第 1 级 PTE i 指向第 2 级页表的基址。例如，在图 9.17 中，块 0、1 和 8 的全部或部分已分配，因此它们的第 1 级 PTE 指向第 2 级页表。

第 2 级页表中的每个 PTE 负责映射 4 KB 的虚拟内存页，就像我们之前看到的单级页表一样。注意，使用 4 字节 PTE，每个第 1 级和第 2 级页表都是 4 千字节，恰好与一个页大小相同。

这种方案以两种方式减少内存需求。第一，如果第 1 级表中的某个 PTE 为空，则相应的第 2 级页表甚至不必存在。这代表了可观的节省空间潜力，因为典型程序的 4 GB 虚拟地址空间大部分是未分配的。第二，只有第 1 级表需要始终驻留在主内存中。第 2 级页表可以由 VM 系统根据需要创建并换入换出，这减少了对主内存的压力。只有最常使用的第 2 级页表才需要缓存在主内存中。

**页表**。页表是单级设计，共有 $2^8 = 256$ 个页表条目（PTE）。然而，我们只关注其中前 16 个。为了方便，我们用索引各 PTE 的 VPN 来标记每个 PTE；但请注意，这些 VPN 不是页表的一部分，也不存储在内存中。另外，注意每个无效 PTE 的 PPN 用破折号表示，以强调恰好存储在那里的任何位值都没有意义。

**高速缓存**。直接映射高速缓存由物理地址中的字段寻址。由于每个块为 4 字节，物理地址的低 2 位用作块偏移（CO）。由于有 16 个组，接下来的 4 位用作组索引（CI）。其余 6 位用作标记（CT）。

给定这些初始设置，让我们来看看当 CPU 执行读取地址 0x03d4 处字节的加载指令时会发生什么。（回想一下，我们假设的 CPU 读取 1 字节字而不是 4 字节字。）为了进行此类手工模拟，我们发现将虚拟地址中的位写出来、识别我们需要的各种字段并确定其十六进制值是有帮助的。硬件在解码地址时执行类似的任务。

如果 TLB 缺失，MMU 将需要从主内存中取出 PTE。然而，在这种情况下，我们很幸运地获得了 TLB 命中。MMU 现在拥有构建物理地址所需的一切。它通过将来自 PTE 的 PPN（0x0D）与来自虚拟地址的 VPO（0x14）拼接，形成物理地址（0x354）。

Linux 将虚拟内存组织为一组区域（area）（也称为段）。区域是现有（已分配）虚拟内存的连续块，其中的页在某种意义上相关。例如，代码段、数据段、堆、共享库段和用户栈都是独立的区域。每个现有的虚拟页都包含在某个区域中，任何不属于某个区域的虚拟页都不存在，不能被进程引用。区域的概念很重要，因为它允许虚拟地址空间有空隙。内核不跟踪不存在的虚拟页，这样的页不会在内存、磁盘或内核本身中消耗任何额外资源。

## 9.8 内存映射

Linux 通过将虚拟内存区域与磁盘上的一个对象相关联来初始化虚拟内存区域的内容，这一过程称为内存映射（memory mapping）。区域可以映射到两种类型的对象之一：

1. **Linux 文件系统中的普通文件**：区域可以映射到普通磁盘文件的连续部分，例如可执行目标文件。文件部分被划分为页大小的片段，每个片段包含虚拟页的初始内容。由于按需调页，在 CPU 第一次触及该页（即发出落在该页地址空间区域内的虚拟地址）之前，这些虚拟页实际上不会被换入物理内存。如果区域大于文件部分，则该区域用零填充。

2. **匿名文件**：区域也可以映射到由内核创建的匿名文件，该文件包含全部二进制零。CPU 第一次触及此类区域中的虚拟页时，内核在物理内存中找到一个适当的受害页，如果该受害页是脏的则将其换出，用二进制零覆盖受害页，并更新页表将该页标记为驻留。注意，磁盘和内存之间实际上没有传输任何数据。因此，映射到匿名文件的区域中的页有时称为按需零页（demand-zero pages）。

无论哪种情况，一旦虚拟页被初始化，它就在内核维护的一个特殊换出文件之间来回交换。换出文件也称为交换空间（swap space）或交换区域（swap area）。一个重要的认识是，在任意时刻，交换空间限制了当前运行进程可以分配的虚拟页的总量。

### 9.8.1 共享对象的再次探讨

内存映射的思想源于一个巧妙的洞察：如果虚拟内存系统能与传统文件系统集成，那么它可以提供一种简单高效的方式来将程序和数据加载到内存中。

如我们所见，进程抽象承诺为每个进程提供自己的私有虚拟地址空间，该地址空间受到保护，不受其他进程的错误写入或读取的影响。然而，许多进程具有相同的只读代码区域。例如，每个运行 Linux shell 程序 bash 的进程都有相同的代码区域。此外，许多程序需要访问相同的只读运行时库代码副本。例如，每个 C 程序都需要标准 C 库中的函数，如 `printf`。让每个进程在物理内存中保留这些常用代码的重复副本将是极其浪费的。

---

<!-- Page 0859 -->

幸运的是，内存映射为我们提供了一种简洁的机制来控制多个进程如何共享对象。

一个对象可以作为共享对象或私有对象映射到虚拟内存区域。如果进程将共享对象映射到其虚拟地址空间的某个区域，那么该进程对该区域所做的任何写入对于将该共享对象也映射到其虚拟内存中的任何其他进程都是可见的。此外，这些修改也会反映到磁盘上的原始对象中。

另一方面，对映射到私有对象的区域所做的修改对其他进程不可见，进程对该区域所做的任何写入都不会反映回磁盘上的对象。映射共享对象的虚拟内存区域通常称为共享区域。类似地，映射私有对象的区域称为私有区域。

对于每个映射私有对象的进程，相应私有区域的页表条目被标记为只读，区域结构体被标记为私有写时复制。只要两个进程都不试图写入各自的私有区域，它们就继续共享物理内存中对象的单个副本。然而，一旦某个进程试图写入私有区域中的某个页，写操作就会触发一个保护故障。

当故障处理程序注意到该保护异常是由进程试图写入私有写时复制区域中的页引起的，它就在物理内存中创建该页的新副本，更新页表条目以指向新副本，然后恢复该页的写权限，如图 9.30(b) 所示。当故障处理程序返回时，CPU 重新执行写操作，现在在新创建的页上正常进行。

通过将私有对象中的页的复制推迟到最后可能的时刻，写时复制使对稀缺物理内存的使用最为高效。

### 9.8.2 fork 函数的再次探讨

现在我们理解了虚拟内存和内存映射，可以清楚地了解 `fork` 函数如何创建一个具有独立虚拟地址空间的新进程。

当当前进程调用 `fork` 函数时，内核为新进程创建各种数据结构，并为其分配唯一的 PID。为了给新进程创建虚拟内存，它创建了当前进程的 `mm_struct`、区域结构体和页表的精确副本。它将两个进程中的每个页都标记为只读，并将两个进程中的每个区域结构体都标记为私有写时复制。

当 `fork` 在新进程中返回时，新进程现在拥有 `fork` 被调用时存在的虚拟内存的精确副本。当其中任何一个进程随后执行任何写操作时，写时复制机制就会创建新页，从而为每个进程保留私有地址空间的抽象。

## 9.9 动态内存分配

虽然使用低级的 `mmap` 和 `munmap` 函数来创建和删除虚拟内存区域当然是可能的，但当 C 程序员在运行时需要获取额外的虚拟内存时，他们通常发现使用动态内存分配器更方便、更具可移植性。

动态内存分配器维护进程虚拟内存的一个区域，称为堆（图 9.33）。细节因系统而异，但不失一般性，我们假设堆是一个按需零页内存区域，紧接在未初始化数据区域之后开始，并向上增长（朝向更高地址）。对于每个进程，内核维护一个变量 `brk`（发音为"break"），指向堆的顶部。

分配器将堆维护为各种大小块的集合。每个块是虚拟内存的连续块，要么已分配要么空闲。已分配块已被应用程序明确保留使用。空闲块可供分配使用。空闲块保持空闲状态，直到应用程序明确分配它。已分配块保持已分配状态，直到被释放——无论是由应用程序显式释放还是由内存分配器本身隐式释放。

分配器有两种基本类型。两种类型都要求应用程序显式分配块。它们的区别在于哪个实体负责释放已分配的块。

- **显式分配器**要求应用程序显式释放任何已分配的块。例如，C 标准库提供了一种称为 `malloc` 包的显式分配器。C 程序通过调用 `malloc`

<div style="text-align: center;"><img src="../raw_texts/imgs/img_in_image_box_451_0_1274_852.jpg" alt="Image" width="41%" /></div>

函数来分配块，通过调用 `free` 函数来释放块。C++ 中的 `new` 和 `delete` 调用与之类似。

- **隐式分配器**，另一方面，要求分配器检测程序何时不再使用已分配的块，然后释放该块。隐式分配器也称为垃圾收集器（garbage collectors），自动释放未使用的已分配块的过程称为垃圾收集（garbage collection）。例如，Lisp、ML 和 Java 等高级语言依赖垃圾收集来释放已分配的块。

```c

```

`malloc` 函数返回一个指针，指向至少 `size` 字节的内存块，该内存块适当对齐，可以容纳该块中可能包含的任何类型的数据对象。在实践中，对齐取决于代码是编译为在 32 位模式（`gcc -m32`）还是 64 位模式（默认）下运行。在 32 位模式下，`malloc` 返回的块地址始终是 8 的倍数。在 64 位模式下，地址始终是 16 的倍数。

动态内存分配器（如 `malloc`）可以通过使用 `mmap` 和 `munmap` 函数，或使用 `sbrk` 函数来显式分配或释放堆内存：

```c
#include <unistd.h>
void *sbrk(intptr_t incr);
Returns: old brk pointer on success, -1 on error
```

`sbrk` 函数通过将 `incr` 加到内核的 `brk` 指针来增大或缩小堆。如果成功，它返回 `brk` 的旧值；否则返回 -1 并将 `errno` 设置为 `ENOMEM`。如果 `incr` 为零，则 `sbrk` 返回 `brk` 的当前值。以负的 `incr` 调用 `sbrk` 是合法的，但需要注意，因为返回值（`brk` 的旧值）指向堆的新顶部之后 `abs(incr)` 个字节处。

程序通过调用 `free` 函数来释放已分配的堆块。

```c
#include <stdlib.h>
void free(void *ptr);
Returns: nothing
```

`ptr` 参数必须指向从 `malloc`、`calloc` 或 `realloc` 获取的已分配块的起始位置。如果不是，则 `free` 的行为未定义。更糟糕的是，由于 `free` 什么也不返回，它不会向应用程序提示出了什么问题。正如我们将在 9.11 节中看到的，这可能会产生一些令人困惑的运行时错误。

### 9.9.2 为什么需要动态内存分配？

程序使用动态内存分配的最重要原因是，它们通常在程序实际运行之前不知道某些数据结构的大小。例如，假设我们被要求编写一个 C 程序，从 `stdin` 中将 n 个 ASCII 整数（每行一个整数）读入一个 C 数组。输入由整数 n 组成，后跟 n 个要读取并存储到数组中的整数。最简单的方法是用一些硬编码的最大数组大小静态定义数组：

```c
#include "csapp.h"
#define MAXN 15213

int array[MAXN];

int main()
{
    int i, n;

    scanf("%d", &n);
    if (n > MAXN)
        app_error("Input file too big");
    for (i = 0; i < n; i++)
        scanf("%d", &array[i]);
    exit(0);
}
```

像这样用硬编码大小分配数组通常是个坏主意。`MAXN` 的值是任意的，与机器上实际可用的虚拟内存量没有关系。此外，如果该程序的用户想要读取比 `MAXN` 大的文件，唯一的办法就是用更大的 `MAXN` 值重新编译程序。虽然对于这个简单的例子来说不是问题，但硬编码数组边界的存在可能成为拥有数百万行代码和众多用户的大型软件产品的维护噩梦。

更好的方法是在运行时动态分配数组，在 n 的值已知之后。使用这种方法，数组的最大大小仅受可用虚拟内存量的限制。

---

<!-- Page 0869 -->

```c
#include "csapp.h"

int main()
{
    int *array, i, n;
    scanf("%d", &n);
    array = (int *)malloc(n * sizeof(int));
    for (i = 0; i < n; i++)
        scanf("%d", &array[i]);
    free(array);
    exit(0);
}
```

动态内存分配是一种有用且重要的编程技术。然而，为了正确有效地使用分配器，程序员需要理解它们的工作原理。我们将在 9.11 节中讨论不当使用分配器可能导致的一些严重错误。

### 9.9.3 分配器的要求和目标

显式分配器必须在一些相当严格的约束条件下运行：

**处理任意请求序列**。应用程序可以进行任意序列的分配和释放请求，前提是每个释放请求必须对应于从之前的分配请求获得的当前已分配块。因此，分配器不能对分配和释放请求的顺序做出任何假设。例如，分配器不能假设所有分配请求都有匹配的释放请求，或者匹配的分配和释放请求是嵌套的。

**立即响应请求**。分配器必须立即响应分配请求。因此，分配器不允许为了提高性能而对请求进行重新排序或缓冲。

**仅使用堆**。为了使分配器可扩展，分配器使用的任何非标量数据结构都必须存储在堆本身中。

**对齐块（对齐要求）**。分配器必须以可以容纳任何类型数据对象的方式对齐块。

**不修改已分配块**。分配器只能操作或更改空闲块。特别是，一旦块被分配，就不允许修改或移动块。因此，不允许使用诸如压缩已分配块等技术。

---

<!-- Page 0870 -->

在这些约束条件下，分配器作者试图满足最大化吞吐量和内存利用率这两个往往相互冲突的性能目标。

**目标 1：最大化吞吐量**。给定 n 个分配和释放请求的某个序列：

$$R_0, R_1, \cdots, R_k, \cdots, R_{n-1}$$

我们希望最大化分配器的吞吐量，吞吐量定义为每单位时间完成的请求数量。例如，如果分配器在 1 秒内完成了 500 个分配请求和 500 个释放请求，则其吞吐量为每秒 1000 次操作。通常，我们可以通过最小化满足分配和释放请求的平均时间来最大化吞吐量。我们将看到，开发出性能合理的分配器并不太难，其中分配请求的最坏情况运行时间与空闲块的数量成线性关系，释放请求的运行时间是常数。

**目标 2：最大化内存利用率**。天真的程序员通常错误地假设虚拟内存是无限资源。实际上，系统中所有进程分配的虚拟内存总量受磁盘上的交换空间量限制。好的程序员知道虚拟内存是一种有限资源，必须高效使用。对于可能被要求分配和释放大块内存的动态内存分配器来说，这尤其重要。

有多种方法可以表征分配器使用堆的效率。根据我们的经验，最有用的度量是峰值利用率。如前所述，我们给定了 n 个分配和释放请求的某个序列：

$$R_0, R_1, \cdots, R_k, \cdots, R_{n-1}$$

如果应用程序请求一个 p 字节的块，则结果分配块的有效载荷为 p 字节。在请求 $R_k$ 完成后，令聚合有效载荷（记为 $P_k$）为当前已分配块的有效载荷之和，令 $H_k$ 表示堆的当前（单调非递减）大小。

则前 $k+1$ 个请求的峰值利用率（记为 $U_k$）由下式给出：

$$U_k = \frac{\max_{i \leq k} P_i}{H_k}$$

因此，分配器的目标是在整个序列上最大化峰值利用率 $U_{n-1}$。我们将看到，最大化吞吐量和利用率之间存在矛盾。特别是，以牺牲堆利用率为代价来最大化吞吐量的分配器很容易编写。任何分配器设计中的有趣挑战之一是在两个目标之间找到适当的平衡。

>**旁注 放宽单调性假设**
>
>我们可以放宽 $U_k$ 定义中的单调非递减假设，允许堆通过令 $H_k$ 为前 $k+1$ 个请求的高水位线来上下增长。

### 9.9.4 碎片

堆利用率差的主要原因是一种称为碎片的现象，当原本未使用的内存不能用于满足分配请求时就会发生碎片。碎片有两种形式：内部碎片和外部碎片。

**内部碎片**发生在已分配块大于其有效载荷时。这可能出于多种原因。例如，分配器的实现可能对已分配块施加一个最小大小，该最小大小大于某些请求的有效载荷。或者，如我们在图 9.34(b) 中看到的，分配器可能会增加块大小以满足对齐约束。

内部碎片很容易量化。它只是已分配块大小与其有效载荷之差的总和。因此，在任意时刻，内部碎片的数量仅取决于先前请求的模式和分配器实现。

**外部碎片**发生在有足够的聚合空闲内存来满足分配请求，但没有任何单一的空闲块大到足以处理请求时。例如，如果图 9.34(e) 中的请求是八字而不是两字，则该请求将无法满足，而不需要从内核请求额外的虚拟内存，即使堆中还剩下八个空闲字。问题出现是因为这八个字分散在两个空闲块中。

外部碎片比内部碎片更难量化，因为它不仅取决于先前请求的模式和分配器实现，还取决于未来请求的模式。例如，假设在 k 个请求之后，所有空闲块的大小恰好是四字。这个堆是否存在外部碎片？答案取决于未来请求的模式。如果所有未来的分配请求都是针对小于或等于四字的块，则不存在外部碎片。另一方面，如果一个或多个请求要求超过四字的块，则该堆确实存在外部碎片。

由于外部碎片难以量化且无法预测，分配器通常采用启发式方法，试图维持少量较大的空闲块，而不是大量较小的空闲块。

### 9.9.5 实现问题

可以想象的最简单的分配器会将堆组织为一个大型字节数组和一个初始指向数组第一个字节的指针 `p`。为了分配

---

<!-- Page 0872 -->

`size` 字节，`malloc` 会将 `p` 的当前值保存在栈上，将 `p` 增加 `size`，并将 `p` 的旧值返回给调用者。`free` 只会返回给调用者而不做任何事情。

这个简单的分配器是设计空间中的一个极端点。由于每个 `malloc` 和 `free` 只执行少量指令，吞吐量将非常好。然而，由于分配器从不重用任何块，内存利用率将极差。在吞吐量和利用率之间取得更好平衡的实际分配器必须考虑以下问题：

**空闲块组织**。我们如何跟踪空闲块？

**放置**。我们如何选择适当的空闲块来放置新分配的块？

**分割**。将新分配的块放置在某个空闲块中之后，我们如何处理空闲块的剩余部分？

**合并**。对于刚刚被释放的块，我们该怎么做？

### 9.9.6 隐式空闲链表

### 9.9.7 放置已分配块

当应用程序请求 k 字节的块时，分配器搜索空闲链表，寻找足够大的空闲块来容纳请求的块。分配器执行此搜索的方式由放置策略决定。一些常见的策略是首次适配（first fit）、下次适配（next fit）和最佳适配（best fit）。

**首次适配**从头开始搜索空闲链表，选择第一个适合的空闲块。**下次适配**与首次适配类似，但不是从链表的开头开始每次搜索，而是从上次搜索结束的地方开始。**最佳适配**检查每个空闲块，选择大小最小的适合块。

首次适配的一个优点是它倾向于在链表末尾保留较大的空闲块。一个缺点是它倾向于在链表开头留下小空闲块的"碎屑"，这将增加查找较大块的搜索时间。下次适配首先由 Donald Knuth 作为首次适配的替代方案提出，其动机是：如果我们上次在某个空闲块中找到了适合的块，那么我们很有可能在该块的剩余部分中再次找到适合的块。下次适配比首次适配运行得快得多，特别是当链表前端被许多小碎屑堵塞时。然而，一些研究表明，下次适配比首次适配的内存利用率更差。研究发现，最佳适配通常比首次适配或下次适配具有更好的内存利用率。然而，使用简单空闲链表组织（如隐式空闲链表）的最佳适配的缺点是，它需要对堆进行穷举搜索。稍后，我们将研究更复杂的分离空闲链表组织，这些组织在不对堆进行穷举搜索的情况下近似最佳适配策略。

### 9.9.9 获取额外的堆内存

如果分配器无法为请求的块找到适配会怎样？一种选择是通过合并（coalescing）物理上相邻的空闲块来尝试创建一些更大的空闲块（下一节）。然而，如果这样做没有产生足够大的块，或者空闲块已经最大程度地合并，则分配器通过调用 `sbrk` 函数向内核请求额外的堆内存。分配器将额外的内存转换为一个大的空闲块，将该块插入空闲链表，然后将请求的块放置在这个新空闲块中。

### 9.9.10 合并空闲块

当分配器释放一个已分配块时，可能有其他空闲块与新释放的块相邻。这些相邻的空闲块可能会导致一种称为假碎片（false fragmentation）的现象，即存在大量可用的空闲内存，但被切碎成许多小的、无法使用的空闲块。例如，图 9.38 展示了释放图 9.37 中分配的块的结果。结果是两个相邻的空闲块，每个都有三字的有效载荷。因此，对四字有效载荷的后续请求将失败，即使两个空闲块的聚合大小足以满足请求。

为了对抗假碎片，任何实际的分配器都必须在称为合并的过程中合并相邻的空闲块。这引出了关于何时执行合并的重要策略决定。分配器可以选择**立即合并**，在每次释放块时合并任何相邻块。或者它可以选择**推迟合并**，等到稍后某个时间再合并空闲块。例如，分配器可能推迟合并直到某个分配请求失败，然后扫描整个堆，合并所有空闲块。

### 9.9.11 使用边界标记进行合并

分配器如何实现合并？让我们将要释放的块称为当前块。合并下一个空闲块（在内存中）是直接且高效的。当前块的头部指向下一个块的头部，可以检查以确定下一个块是否是空闲的。如果是，则只需将其大小添加到当前头部的大小，并在常数时间内合并这两个块。

但如何合并前一个块呢？给定一个具有头部的块的隐式空闲链表，唯一的选择是搜索整个链表，记住前一个块的位置，直到我们到达当前块。对于隐式空闲链表，这意味着每次调用 `free` 都需要与堆大小成线性关系的时间。即使使用更复杂的空闲链表组织，搜索时间也不会是常数。

Knuth 开发了一种称为**边界标记**的巧妙通用技术，允许在常数时间内合并前一个块。如图 9.39 所示，其思想是在每个块的末尾添加一个脚部（边界标记），其中脚部是头部的副本。如果每个块都包含这样的脚部，则分配器可以通过检查前一个块的脚部来确定其起始位置和状态，而该脚部始终在当前块开始位置之前一个字处。

考虑当分配器释放当前块时可能存在的所有情况：

1. 前一个块和下一个块都已分配。
2. 前一个块已分配，下一个块是空闲的。
3. 前一个块是空闲的，下一个块已分配。
4. 前一个块和下一个块都是空闲的。

边界标记的思想是简单而优雅的，可以推广到许多不同类型的分配器和空闲链表组织。然而，存在潜在的缺点。如果应用程序操作许多小块，要求每个块都包含头部和脚部可能会引入显著的内存开销。例如，如果一个图形应用程序通过重复调用 `malloc` 和 `free` 来动态创建和销毁图节点，而每个图节点只需要几个字的内存，那么头部和脚部将消耗每个已分配块的一半空间。

幸运的是，有一种巧妙的边界标记优化，消除了已分配块中对脚部的需求。回想一下，当我们试图将当前块与内存中的前一个块和下一个块合并时，只有在前一个块是空闲的情况下，才需要前一个块脚部中的大小字段。如果我们将前一个块的已分配/空闲位存储在当前块的某个多余低阶位中，则已分配块不需要脚部，我们可以将额外的空间用于有效载荷。但请注意，空闲块仍然需要脚部。

### 9.9.12 综合运用：实现一个简单的分配器

构建分配器是一项具有挑战性的任务。设计空间很大，块格式和空闲链表格式，以及放置、分割和合并策略都有众多替代方案。另一个挑战是你经常被迫在安全、熟悉的类型系统之外进行编程，依赖于低级系统编程中典型的容易出错的指针转换和指针算术。

虽然分配器不需要大量代码，但它们是微妙且不宽容的。熟悉 C++ 或 Java 等高级语言的学生在第一次遇到这种编程风格时往往会遇到概念上的障碍。为了帮助你克服这个障碍，我们将完成一个简单分配器的实现，该分配器基于具有立即边界标记合并的隐式空闲链表。最大块大小为 $2^{32} = 4$ GB。代码是 64 位干净的，在 32 位（`gcc -m32`）或 64 位（`gcc -m64`）进程中无需修改即可运行。

#### 通用分配器设计

我们的分配器使用图 9.41 中的 `memlib.c` 包提供的内存系统模型。该模型的目的是允许我们运行分配器而不干扰现有的系统级 `malloc` 包。

`mem_init` 函数将可用于堆的虚拟内存建模为一个大型双字对齐的字节数组。`mem_heap` 和 `mem_brk` 之间的字节表示已分配的虚拟内存。`mem_brk` 之后的字节表示未分配的虚拟内存。分配器通过调用 `mem_sbrk` 函数请求额外的堆内存，该函数与系统的 `sbrk` 函数具有相同的接口和语义，但拒绝缩小堆的请求。

分配器本身包含在一个源文件（`mm.c`）中，用户可以将其编译并链接到他们的应用程序中。分配器向应用程序导出三个函数：

```c
extern int mm_init(void);
extern void *mm_malloc (size_t size);
extern void mm_free (void *ptr);
```

`mm_init` 函数初始化分配器，成功返回 0，否则返回 -1。`mm_malloc` 和 `mm_free` 函数与系统对应函数具有相同的接口和语义。分配器使用块格式

```c
/* Private global variables */
static char *mem_heap;    /* Points to first byte of heap */
static char *mem_brk;     /* Points to last byte of heap plus 1 */
static char *mem_max_addr; /* Max legal heap addr plus 1 */
/*
 * mem_init - Initialize the memory system model
 */
void mem_init(void)
{
    mem_heap = (char *)malloc(MAX_HEAP);
    mem_brk = (char *)mem_heap;
    mem_max_addr = (char *)(mem_heap + MAX_HEAP);
}
/*
 * mem_sbrk - Simple model of the sbrk function. Extends the heap
 *     by incr bytes and returns the start address of the new area. In
 *     this model, the heap cannot be shrunk.
 */
void *mem_sbrk(int incr)
{
    char *old_brk = mem_brk;

    if ((incr < 0) || ((mem_brk + incr) > mem_max_addr)) {
        errno = ENOMEM;
        fprintf(stderr, "ERROR: mem_sbrk failed. Ran out of memory...\n");
        return (void *)-1;
    }
    mem_brk += incr;
    return (void *)old_brk;
}
```

#### 操作空闲链表的基本常量和宏

```c
#define DSIZE 8 /* Double word size (bytes) */
#define CHUNKSIZE (1<<12) /* Extend heap by this amount (bytes) */

#define MAX(x, y) ((x) > (y)? (x) : (y))

/* Pack a size and allocated bit into a word */
#define PACK(size, alloc) ((size) | (alloc))

/* Read and write a word at address p */
#define GET(p) (*(unsigned int *) (p))
#define PUT(p, val) (*(unsigned int *) (p) = (val))

/* Read the size and allocated fields from address p */
#define GET_SIZE(p) (GET(p) & ~0x7)
#define GET_ALLOC(p) (GET(p) & 0x1)

#define HDRP(bp) ((char *) (bp) - WSIZE)
#define FTRP(bp) ((char *) (bp) + GET_SIZE(HDRP(bp)) - DSIZE)

#define NEXT_BLKP(bp) ((char *) (bp) + GET_SIZE((char *) (bp) - WSIZE)))
#define PREV_BLKP(bp) ((char *) (bp) - GET_SIZE((char *) (bp) - DSIZE)))
```

```c
static void *extend_heap(size_t words)
{
    char *bp;
    size_t size;

    /* Allocate an even number of words to maintain alignment */
    size = (words % 2)? (words + 1) * WSIZE : words * WSIZE;
    if ((long)(bp = mem_sbrk(size)) == -1)
        return NULL;

    /* Initialize free block header/footer and the epilogue header */
    PUT(HDRP(bp), PACK(size, 0));    /* Free block header */
    PUT(FTRP(bp), PACK(size, 0));    /* Free block footer */
    PUT(HDRP(NEXT_BLKP(bp)), PACK(0, 1)); /* New epilogue header */

    /* Coalesce if the previous block was free */
    return coalesce(bp);
}
```

```c
void mm_free(void *bp)
{
    size_t size = GET_SIZE(HDRP(bp));
    PUT(HDRP(bp), PACK(size, 0));
    PUT(FTRP(bp), PACK(size, 0));
    coalesce(bp);
}

static void *coalesce(void *bp)
{
    size_t prev_alloc = GET_ALLOC(FTRP(PREV_BLKP(bp)));
    size_t next_alloc = GET_ALLOC(HDRP(NEXT_BLKP(bp)));
    size_t size = GET_SIZE(HDRP(bp));
    if (prev_alloc && next_alloc) { /* Case 1 */
        return bp;
    }

    else if (prev_alloc && !next_alloc) { /* Case 2 */
        size += GET_SIZE(HDRP(NEXT_BLKP(bp)));
        PUT(HDRP(bp), PACK(size, 0));
        PUT(FTRP(bp), PACK(size, 0));
    }

    else if (!prev_alloc && next_alloc) { /* Case 3 */
        size += GET_SIZE(HDRP(PREV_BLKP(bp)));
        PUT(FTRP(bp), PACK(size, 0));
        PUT(HDRP(PREV_BLKP(bp)), PACK(size, 0));
        bp = PREV_BLKP(bp);
    }

    else { /* Case 4 */
        size += GET_SIZE(HDRP(PREV_BLKP(bp)));
        GET_SIZE(FTRP(NEXT_BLKP(bp)));
        PUT(HDRP(PREV_BLKP(bp)), PACK(size, 0));
        PUT(FTRP(NEXT_BLKP(bp)), PACK(size, 0));
        bp = PREV_BLKP(bp);
    }

    return bp;
}
```

### 9.9.13 显式空闲链表

隐式空闲链表为我们提供了一种简单的方式来介绍一些基本的分配器概念。然而，由于块的分配时间与堆块的总数成线性关系，隐式空闲链表不适合作为通用分配器（尽管对于已知堆块数量较小的专用分配器可能没问题）。

更好的方法是将空闲块组织成某种显式数据结构。由于空闲块的主体部分不被程序使用，实现数据结构所需的指针可以存储在空闲块的主体中。例如，可以通过在每个空闲块中包含 `pred`（前驱）和 `succ`（后继）指针，将堆组织成双向链接的空闲链表，如图 9.48 所示。

使用双向链表而不是隐式空闲链表，可以将首次适配分配时间从与块总数成线性关系降低为与空闲块数量成线性关系。然而，释放一个块的时间可以是线性的或常数时间，这取决于我们为空闲链表中块的排序选择的策略。

一种方法是通过在链表开头插入新释放的块来维护后进先出（LIFO）顺序。对于 LIFO 排序和首次适配放置策略，分配器会首先检查最近使用的块。在这种情况下，释放一个块可以在常数时间内完成。如果使用了边界标记，则合并也可以在常数时间内完成。

另一种方法是按地址顺序维护链表，其中链表中每个块的地址小于其后继的地址。在这种情况下，释放一个块需要一次线性时间搜索以定位适当的前驱。折中之处在于，按地址排序的首次适配比 LIFO 排序的首次适配具有更好的内存利用率，接近最佳适配的利用率。

显式链表的一个普遍缺点是，空闲块必须足够大以包含所有必要的指针，以及头部，可能还有尾部。这导致最小块大小更大，增加了内部碎片化的可能性。

### 9.9.14 分离的空闲链表

正如我们所见，使用单个空闲块链表的分配器在分配一个块时需要与空闲块数量成线性的时间。一种流行的减少分配时间的方法，通称为**分离存储**（segregated storage），是维护多个空闲链表，每个链表保存大致相同大小的块。其基本思想是将所有可能的块大小集合划分为称为**大小类**（size classes）的等价类。定义大小类有很多方式。例如，可以按 2 的幂划分块大小：

$$\{1\},\{2\},\{3,4\},\{5-8\},\cdots,\{1{,}025-2{,}048\},\{2{,}049-4{,}096\},\{4{,}097-\infty\}$$

或者可以将小块分配到各自的大小类，并按 2 的幂划分大块：

$$\{1\},\{2\},\{3\},\cdots,\{1{,}023\},\{1{,}024\},\{1{,}025-2{,}048\},\{2{,}049-4{,}096\},\{4{,}097-\infty\}$$

分配器维护一个空闲链表数组，每个大小类对应一个空闲链表，按大小递增排列。当分配器需要一个大小为 $n$ 的块时，它搜索相应的空闲链表。如果找不到合适的块，它就搜索下一个链表，以此类推。

动态存储分配的文献描述了数十种分离存储的变体，它们在如何定义大小类、何时执行合并、何时向操作系统请求额外的堆内存、是否允许分割等方面各有不同。为了让你了解其中的可能性，我们将描述两种基本方法：简单分离存储和分离适配。

#### 简单分离存储

采用简单分离存储时，每个大小类的空闲链表包含相同大小的块，每个块的大小等于该大小类中最大元素的大小。例如，如果某个大小类定义为 $\{17-32\}$，则该类的空闲链表完全由大小为 32 的块组成。

要分配给定大小的块，我们检查相应的空闲链表。如果链表不为空，我们简单地将链表中的第一个块完整分配出去。空闲块不会被分割以满足分配请求。如果链表为空，分配器会向操作系统请求固定大小的一块额外内存（通常是页大小的倍数），将该块划分为等大小的块，并将块链接在一起形成新的空闲链表。要释放一个块，分配器只需将其插入到相应空闲链表的开头。

这种简单方案有许多优点。分配和释放块都是快速的常数时间操作。此外，每个块内相同大小的块、不分割以及不合并的组合意味着每个块几乎没有内存开销。由于每个块中只有相同大小的块，已分配块的大小可以从其地址推断出来。由于没有合并，已分配块不需要在头部设置已分配/空闲标志。因此，已分配块不需要头部，由于没有合并，也不需要任何尾部。由于分配和释放操作在空闲链表的开头插入和删除块，链表只需要单向链接而不是双向链接。总而言之，任何块中唯一需要的字段是每个空闲块中一个字的 `succ` 指针，因此最小块大小只有一个字。

一个显著的缺点是，简单分离存储容易受到内部碎片和外部碎片的影响。内部碎片是可能的，因为空闲块从不分割。更糟糕的是，某些引用模式可能导致极端的外部碎片，因为空闲块从不合并（练习题 9.10）。

#### 分离适配

采用这种方法，分配器维护一个空闲链表数组。每个空闲链表与一个大小类相关联，并组织为某种显式或隐式链表。每个链表包含可能不同大小的块，其大小是该大小类的成员。分离适配分配器有很多变体。这里我们描述一个简单版本。

要分配一个块，我们确定请求的大小类，并对相应的空闲链表执行首次适配搜索以找到合适的块。如果找到了，则（可选地）分割它并将碎片插入到相应的空闲链表中。如果找不到合适的块，则搜索下一个更大大小类的空闲链表。我们

不断重复，直到找到合适的块。如果没有空闲链表能提供合适的块，则向操作系统请求额外的堆内存，从这块新堆内存中分配块，并将剩余部分放入适当的大小类中。要释放一个块，我们合并并将结果放入适当的空闲链表中。

分离适配方法是生产级分配器（如 C 标准库中的 GNU malloc 包）的常用选择，因为它既快速又内存高效。搜索时间减少，因为搜索被限制在堆的特定部分而不是整个堆。内存利用率可以提高，这得益于一个有趣的事实：对分离空闲链表的简单首次适配搜索近似于对整个堆的最佳适配搜索。

#### 伙伴系统

伙伴系统是分离适配的一种特殊情况，其中每个大小类都是 2 的幂。基本思想是，给定一个由 $2^m$ 个字组成的堆，我们为每个块大小 $2^k$（其中 $0 \leq k \leq m$）维护一个独立的空闲链表。请求的块大小向上取整到最近的 2 的幂。最初，只有一个大小为 $2^m$ 个字的空闲块。

要分配一个大小为 $2^k$ 的块，我们找到第一个大小为 $2^j$ 的可用块，使得 $k \leq j \leq m$。如果 $j = k$，则完成。否则，我们递归地将块对半分割，直到 $j = k$。在执行此分割时，每个剩余的半块（称为**伙伴**）被放入适当的空闲链表中。要释放一个大小为 $2^k$ 的块，我们继续与空闲的伙伴合并。当遇到已分配的伙伴时，停止合并。

关于伙伴系统的一个关键事实是，给定一个块的地址和大小，很容易计算出其伙伴的地址。例如，地址为

$$xxx\cdots x00000$$

的大小为 32 字节的块，其伙伴位于地址

$$xxx\cdots x10000$$

换句话说，一个块及其伙伴的地址恰好在一个位的位置上不同。

伙伴系统分配器的主要优点是快速的搜索和合并。主要缺点是块大小必须为 2 的幂，这可能导致显著的内部碎片。因此，伙伴系统分配器不适合通用工作负载。然而，对于某些特定应用的工作负载（块大小事先已知为 2 的幂），伙伴系统分配器具有一定的吸引力。

## 9.10 垃圾收集

对于使用显式分配器（如 C 的 malloc 包）的情况，应用程序通过调用 malloc 和 free 来分配和释放堆块。释放任何不再需要的已分配块是应用程序的责任。

---

<!-- Page 0891 -->

忘记释放已分配的块是一种常见的编程错误。例如，考虑以下 C 函数，它在处理过程中分配了一块临时存储：

```c
void garbage()
{
    int *p = (int *)malloc(15213);
    return; /* 此时数组 p 是垃圾 */
}
```

由于 `p` 不再被程序使用，它应该在 `garbage` 返回之前被释放。不幸的是，程序员忘记释放这个块了。它在程序的整个生命周期内保持已分配状态，无谓地占用了可以用于满足后续分配请求的堆空间。

**垃圾收集器**（garbage collector）是一种动态存储分配器，它自动释放程序不再需要的已分配块。这些块被称为**垃圾**（故有"垃圾收集器"这一术语）。自动回收堆存储的过程称为**垃圾收集**（garbage collection）。在支持垃圾收集的系统中，应用程序显式分配堆块，但从不显式释放它们。在 C 程序的上下文中，应用程序调用 malloc 但从不调用 free。相反，垃圾收集器定期识别垃圾块，并适当地调用 free 将这些块放回空闲链表。

垃圾收集可以追溯到 20 世纪 60 年代初 John McCarthy 在麻省理工学院开发的 Lisp 系统。它是现代语言系统（如 Java、ML、Perl 和 Mathematica）的重要组成部分，至今仍是一个活跃而重要的研究领域。文献中描述了惊人数量的垃圾收集方法。我们将把讨论限制在 McCarthy 最初的标记和清除（Mark&Sweep）算法上，因为它很有趣——它可以建立在现有的 malloc 包之上，为 C 和 C++ 程序提供垃圾收集。

### 9.10.1 垃圾收集器基础

垃圾收集器将内存视为图 9.49 所示形式的有向可达性图。图的节点被划分为一组**根节点**和一组**堆节点**。每个堆节点对应堆中的一个已分配块。有向边 $p \rightarrow q$ 表示块 $p$ 中的某个位置指向块 $q$ 中的某个位置。根节点对应堆外的位置，这些位置包含指向堆的指针。这些位置可以是寄存器、栈上的变量或虚拟内存读/写数据区中的全局变量。

我们说节点 $p$ 是**可达的**，如果存在从任意根节点到 $p$ 的有向路径。在任意时刻，不可达节点对应于应用程序永远无法再使用的垃圾。垃圾收集器的作用是维护可达性图的某种表示，并通过释放不可达节点并将其返回到空闲链表来周期性地回收它们。

像 ML 和 Java 这类对应用程序如何创建和使用指针进行严格控制的语言，其垃圾收集器可以维护可达性图的精确表示，从而可以回收所有垃圾。然而，C 和 C++ 这类语言的收集器通常无法维护可达性图的精确表示。这类收集器被称为**保守式垃圾收集器**（conservative garbage collectors）。它们是保守的，因为每个可达块都被正确地标识为可达，而某些不可达节点可能被错误地标识为可达。

收集器可以按需提供服务，也可以作为独立线程与应用程序并行运行，持续更新可达性图并回收垃圾。例如，考虑我们如何将 C 程序的保守式收集器集成到现有的 malloc 包中，如图 9.50 所示。

应用程序像往常一样在需要堆空间时调用 malloc。如果 malloc 无法找到合适的空闲块，它就调用垃圾收集器，希望能回收一些垃圾到空闲链表中。收集器识别垃圾块，并通过调用 free 函数将它们返回到堆中。关键思想是收集器而不是应用程序调用 free。当对收集器的调用返回时，malloc 再次尝试找到合适的空闲块。如果还是失败，它可以向操作系统请求额外的内存。最终，malloc 返回指向请求块的指针（如果成功）或 NULL 指针（如果失败）。

### 9.10.2 标记和清除垃圾收集器

标记和清除垃圾收集器由一个**标记阶段**组成，标记阶段标记所有从根节点可达的已分配后代，然后是一个**清除阶段**，清除阶段释放每个未标记的已分配块。通常，块头部的一个备用低位用于指示块是否被标记。

---

<!-- Page 0893 -->

（a）mark 函数

```c
void mark(ptr p) {
    if ((b = isPtr(p)) == NULL)
        return;
    if (blockMarked(b))
        return;
    markBlock(b);
    len = length(b);
    for (i=0; i < len; i++)
        mark(b[i]);
    return;
}
```

（b）sweep 函数

```c
void sweep(ptr b, ptr end) {
    while (b < end) {
        if (blockMarked(b))
            unmarkBlock(b);
            else if (blockAllocated(b))
                free(b);
            b = nextBlock(b);
        }
        return;
}
```

<div style="text-align: center;">图 9.51 mark 和 sweep 函数的伪代码。</div>

我们对标记和清除的描述将假设以下函数，其中 `ptr` 定义为 `typedef void *ptr`：

`ptr isPtr(ptr p)`：如果 `p` 指向某个已分配块中的某个字，则返回指向该块开头的指针 `b`。否则返回 NULL。

`int blockMarked(ptr b)`：如果块 `b` 已被标记则返回真。
`int blockAllocated(ptr b)`：如果块 `b` 已被分配则返回真。
`void markBlock(ptr b)`：标记块 `b`。
`int length(ptr b)`：返回块 `b` 的长度（以字为单位，不包括头部）。
`void unmarkBlock(ptr b)`：将块 `b` 的状态从已标记改为未标记。
`ptr nextBlock(ptr b)`：返回堆中块 `b` 的后继块。

标记阶段对每个根节点调用一次图 9.51(a) 中所示的 mark 函数。如果 `p` 不指向某个已分配且未标记的堆块，mark 函数立即返回。否则，它标记该块并对块中的每个字递归调用自身。每次对 mark 函数的调用都会标记某个根节点的所有未标记且可达的后代。在标记阶段结束时，任何未被标记的已分配块都保证是不可达的，从而是可以在清除阶段回收的垃圾。

清除阶段是对图 9.51(b) 中所示的 sweep 函数的单次调用。sweep 函数遍历堆中的每个块，释放它遇到的任何未标记的已分配块（即垃圾）。

### 9.10.3 C 程序的保守式标记和清除

标记和清除是对 C 程序进行垃圾收集的合适方法，因为它在原地工作而不移动任何块。然而，C 语言为 `isPtr` 函数的实现带来了一些有趣的挑战。

首先，C 语言不会用任何类型信息标记内存位置。因此，`isPtr` 没有明显的方法来确定其输入参数 `p` 是否是指针。其次，即使我们知道 `p` 是指针，也没有明显的方法让 `isPtr` 确定 `p` 是否指向某个已分配块有效载荷中的某个位置。

解决后一个问题的一种方案是将已分配块的集合维护为一棵平衡二叉树，该树保持这样的不变量：左子树中的所有块位于较小的地址处，右子树中的所有块位于较大的地址处。如图 9.53 所示，这需要在每个已分配块的头部中有两个额外的字段（`left` 和 `right`）。每个字段指向某个已分配块的头部。`isPtr(ptr p)` 函数使用该树对已分配块执行二分搜索。在每一步，它依赖于块头部中的大小字段来确定 `p` 是否落在块的范围内。

---

<!-- Page 0895 -->

从这样的意义上说，平衡树方法是正确的：它保证标记所有从根可达的节点。这是一个必要的保证，因为应用程序用户肯定不会希望他们的已分配块被过早地返回到空闲链表。然而，它是保守的，因为它可能错误地标记实际上不可达的块，从而可能无法释放某些垃圾。虽然这不影响应用程序的正确性，但可能导致不必要的外部碎片。

标记和清除 C 程序收集器必须是保守的根本原因是 C 语言不用类型信息标记内存位置。因此，像 int 或 float 这样的标量可以伪装成指针。例如，假设某个可达的已分配块在其有效载荷中包含一个 int，其值恰好对应于另一个已分配块 $b$ 的有效载荷中的某个地址。收集器没有办法推断该数据实际上是 int 而不是指针。因此，分配器必须保守地将块 $b$ 标记为可达，而实际上它可能不可达。

## 9.11 C 程序中常见的内存相关错误

对 C 程序员来说，管理和使用虚拟内存可能是一项困难且容易出错的任务。内存相关的错误是最令人恐惧的，因为它们往往在距离错误源头很远的时间和空间上表现出来。将错误的数据写到错误的位置，程序可能在某个遥远的部分最终失败之前运行数小时。我们以回顾一些常见的内存相关错误来结束对虚拟内存的讨论。

### 9.11.1 间接引用坏指针

正如我们在第 9.7.2 节中学到的，进程的虚拟地址空间中有大片区域未映射到任何有意义的数据。如果我们试图对指向这些空洞之一的指针进行间接引用，操作系统将以段错误异常终止我们的程序。此外，虚拟内存的某些区域是只读的。试图写入这些区域之一会以保护异常终止程序。

间接引用坏指针的一个常见例子是经典的 `scanf` 错误。假设我们想使用 `scanf` 从标准输入读取一个整数到变量中。正确的方法是向 `scanf` 传递格式字符串和变量的地址：

```c
scanf("%d", &val)
```

然而，新的 C 程序员（甚至有经验的程序员！）很容易传递 `val` 的内容而不是其地址：

```c
scanf("%d", val)
```


<!-- Page 0896 -->

在这种情况下，`scanf` 会将 `val` 的内容解释为地址，并尝试向该位置写入一个字。在最好的情况下，程序会立即以异常终止。在最坏的情况下，`val` 的内容对应虚拟内存的某个有效读/写区域，我们会覆盖该内存，通常会在很久之后在程序的某个遥远部分导致灾难性和令人困惑的后果。

### 9.11.2 读取未初始化的内存

虽然 bss 内存位置（例如未初始化的全局 C 变量）总是由加载器初始化为零，但堆内存并非如此。一个常见的错误是假设堆内存已被初始化为零：

```c
/* Return y = Ax */
int *matvec(int **A, int *x, int n)
{
    int i, j;
    int *y = (int *)malloc(n * sizeof(int));
    for (i = 0; i < n; i++)
        for (j = 0; j < n; j++)
            y[i] += A[i][j] * x[j];
    return y;
}
```

在这个例子中，程序员错误地假设向量 `y` 已被初始化为零。正确的实现应显式地将 `y[i]` 清零，或使用 `calloc`。

### 9.11.3 允许栈缓冲区溢出

正如我们在第 3.10.3 节中看到的，如果程序向栈上的目标缓冲区写入数据时不检查输入字符串的大小，就会存在缓冲区溢出错误。例如，下面的函数有一个缓冲区溢出错误，因为 `gets` 函数将任意长度的字符串复制到缓冲区中。要修复这个问题，我们需要使用 `fgets` 函数，它可以限制输入字符串的大小。

```c
void bufoverflow()
{
    char buf[64];

    gets(buf); /* 这里是栈缓冲区溢出错误 */
    return;
}
```

### 9.11.4 假设指针和它们所指向的对象大小相同

一个常见的错误是假设指向对象的指针与它们所指向的对象大小相同：

```c
/* Create an nxm array */
int **makeArray1(int n, int m)
{
    int i;
    int **A = (int **)Malloc(n * sizeof(int));
    for (i = 0; i < n; i++)
        A[i] = (int *)Malloc(m * sizeof(int));
    return A;
}
```

此代码的意图是创建一个 `n` 个指针的数组，每个指针指向一个 `m` 个 `int` 的数组。然而，由于程序员在第 5 行写的是 `sizeof(int)` 而不是 `sizeof(int *)`，代码实际上创建了一个 `int` 数组。

这段代码在 `int` 和指向 `int` 的指针大小相同的机器上运行正常。但如果在像 Core i7 这样指针比 `int` 更大的机器上运行此代码，则第 7–8 行的循环将写到 `A` 数组末尾之后的位置。由于其中一个字可能是已分配块的边界标记尾部，我们可能直到很久之后在程序中释放该块时才发现这个错误，此时分配器中的合并代码将以令人困惑的方式崩溃。这是内存相关编程错误中那种典型的"超距作用"的阴险例子。

### 9.11.5 犯差一错误

差一错误是另一类常见的覆盖错误来源：


这是前一节程序的另一个版本。这里我们在第 5 行创建了一个 `n` 个指针的数组，但随后在第 7 行和第 8 行试图初始化 $n + 1$ 个元素，在这个过程中覆盖了 `A` 数组之后的某些内存。

### 9.11.6 引用指针而不是它所指向的对象

如果我们不仔细注意 C 运算符的优先级和结合性，就可能错误地操作指针本身而不是它所指向的对象。例如，考虑以下函数，其目的是从包含 `*size` 个项目的二叉堆中删除第一项，然后对剩余的 `*size - 1` 项重新堆化：

```c
int *binheapDelete(int **binheap, int *size)
{
    int *packet = binheap[0];
    binheap[0] = binheap[*size - 1];
    *size--; /* This should be (*size)-- */
    heapify(binheap, *size, 0);
    return(packet);
}
```

在第 6 行，意图是对 `size` 指针所指向的整数值进行递减。然而，由于一元 `--` 和 `*` 运算符具有相同的优先级且从右到左结合，第 6 行的代码实际上递减的是指针本身，而不是它所指向的整数值。如果运气好，程序会立即崩溃。但更有可能的是，当程序在其执行的很久之后产生错误答案时，我们会挠头不解。这里的教训是：在对优先级和结合性有任何疑虑时都要使用括号。例如，在第 6 行，我们应该通过使用表达式 `(*size)--` 来明确表达我们的意图。

### 9.11.7 误解指针运算

另一个常见错误是忘记指针上的算术运算以它们所指向对象的大小为单位进行，而不一定是字节。例如，以下函数的意图是扫描一个 `int` 数组并返回指向第一次出现 `val` 的指针：

```c
int *search(int *p, int val)
{
    while (*p && *p != val)
        p += sizeof(int); /* Should be p++ */
    return p;
}
```

然而，由于第 4 行每次循环将指针递增 4（整数的字节数），该函数实际上错误地每隔四个整数扫描一次数组。

### 9.11.8 引用不存在的变量

不了解栈规则的 C 程序员有时会引用不再有效的局部变量，如以下示例：

```c
int *stackref()
{
    int val;
    return &val;
}
```

该函数返回一个指向栈上局部变量的指针（假设为 `p`），然后弹出其栈帧。虽然 `p` 仍然指向一个有效的内存地址，但它不再指向一个有效的变量。当程序稍后调用其他函数时，该内存将被重用于它们的栈帧。之后，如果程序给 `*p` 赋某个值，它实际上可能正在修改另一个函数栈帧中的某个条目，可能造成灾难性和令人困惑的后果。

### 9.11.9 引用已释放堆块中的数据

一个类似的错误是引用已释放的堆块中的数据。考虑以下示例，它在第 6 行分配了一个整数数组 `x`，在第 10 行过早释放了块 `x`，然后在第 14 行再次引用它：

```c
int *heapref(int n, int m)
{
    int i;
    int *x, *y;

    x = (int *)Malloc(n * sizeof(int));
    // Other calls to malloc and free go here

    free(x);

    y = (int *)Malloc(m * sizeof(int));
    for (i = 0; i < m; i++)
        y[i] = x[i]++; /* 0ops! x[i] is a word in a free block */

    return y;
}
```

根据第 6 行到第 10 行之间发生的 malloc 和 free 调用模式，当程序在第 14 行引用 `x[i]` 时，数组 `x` 可能已经是某个其他已分配堆块的一部分，并可能已被覆盖。与许多

### 9.11.10 引入内存泄漏

内存泄漏是一种缓慢的、无声的杀手，当程序员因忘记释放已分配的块而无意中在堆中创建垃圾时就会发生。例如，以下函数分配一个堆块 `x` 然后不释放它就返回：

```c
void leak(int n)
{
    int *x = (int *)malloc(n * sizeof(int));
    return; /* x is garbage at this point */
}
```

如果 `leak` 被频繁调用，堆将逐渐被垃圾填满，在最坏的情况下消耗整个虚拟地址空间。内存泄漏对于守护进程和服务器等程序尤其严重，因为按定义它们永远不会终止。

## 9.12 小结

虚拟内存是对主内存的抽象。支持虚拟内存的处理器使用一种称为虚拟寻址的间接寻址方式来引用主内存。处理器生成一个虚拟地址，在发送到主内存之前被转换为物理地址。地址从虚拟地址空间到物理地址空间的转换需要硬件和软件的紧密协作。专用硬件使用页表来转换虚拟地址，页表的内容由操作系统提供。

虚拟内存提供了三个重要功能。首先，它自动缓存存储在磁盘上的虚拟地址空间中最近使用的内容到主内存中。虚拟内存高速缓存中的块称为页。对磁盘上某页的引用会触发页故障，将控制权转移给操作系统中的故障处理程序。故障处理程序将页从磁盘复制到主内存高速缓存中，必要时写回被驱逐的页。其次，虚拟内存简化了内存管理，进而简化了链接、在进程之间共享数据、为进程分配内存以及程序加载。最后，虚拟内存通过在每个页表条目中加入保护位来简化内存保护。

地址转换过程必须与系统中任何硬件高速缓存的操作集成。大多数页表条目位于 L1 高速缓存中，但从 L1 访问页表条目的成本通常由称为 TLB 的片上页表条目高速缓存消除。

---

<!-- Page 0901 -->

现代系统通过将虚拟内存块与磁盘上的文件块关联来初始化虚拟内存块，这一过程称为内存映射。内存映射提供了一种共享数据、创建新进程和加载程序的高效机制。应用程序可以使用 `mmap` 函数手动创建和删除虚拟地址空间的区域。然而，大多数程序依赖动态内存分配器（如 `malloc`）来管理称为堆的虚拟地址空间区域中的内存。动态内存分配器是具有系统级外观的应用级程序，直接操作内存而几乎不依赖类型系统的帮助。分配器有两种类型：显式分配器要求应用程序显式释放内存块；隐式分配器（垃圾收集器）自动释放任何未使用且不可达的块。

对 C 程序员来说，管理和使用内存是一项困难且容易出错的任务。常见错误的例子包括：间接引用坏指针、读取未初始化内存、允许栈缓冲区溢出、假设指针和它们所指向的对象大小相同、引用指针而不是它所指向的对象、误解指针运算、引用不存在的变量以及引入内存泄漏。

Kilburn 及其同事发表了虚拟内存的第一篇描述 [63]。体系结构教材包含了关于硬件在虚拟内存中作用的更多细节 [46]。操作系统教材包含了关于操作系统在虚拟内存中作用的更多信息 [102, 106, 113]。Bovet 和 Cesati [11] 给出了 Linux 虚拟内存系统的详细描述。Intel 公司在 IA 处理器的 32 位和 64 位地址转换方面提供了详细文档 [52]。
