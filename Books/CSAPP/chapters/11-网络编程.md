网络应用无处不在。每次你浏览 Web、发送电子邮件或玩网络游戏，都在使用网络应用程序。有趣的是，所有网络应用程序都基于相同的基本编程模型，具有相似的整体逻辑结构，并依赖相同的编程接口。

网络应用程序依赖于许多你在系统学习中已经掌握的概念。例如，进程、信号、字节序、内存映射和动态存储分配都扮演着重要角色。还有一些新概念需要掌握。你需要了解基本的客户端-服务器编程模型，以及如何编写使用因特网所提供服务的客户端-服务器程序。最后，我们将通过开发一个小型但功能完整的 Web 服务器来将所有这些思想融会贯通，该服务器能够向真实的 Web 浏览器提供包含文本和图形的静态与动态内容。

## 11.1 客户端-服务器编程模型

每个网络应用程序都基于客户端-服务器模型。在这个模型中，一个应用程序由一个服务器进程和一个或多个客户端进程组成。服务器管理某种资源，并通过操纵该资源为其客户端提供某种服务。例如，Web 服务器管理一组磁盘文件，代表客户端检索和执行这些文件。FTP 服务器管理一组磁盘文件，为客户端存储和检索这些文件。类似地，电子邮件服务器管理一个假脱机文件（spool file），为客户端读取和更新该文件。

客户端-服务器模型中的基本操作是**事务**（图 11.1）。一个客户端-服务器事务由四个步骤组成：

1. 当客户端需要服务时，它通过向服务器发送一个请求来发起一个事务。例如，当 Web 浏览器需要一个文件时，它向 Web 服务器发送一个请求。

2. 服务器收到请求，对其进行解释，并以适当的方式操纵其资源。例如，当 Web 服务器从浏览器收到一个请求时，它读取一个磁盘文件。

3. 服务器向客户端发送一个响应，然后等待下一个请求。例如，Web 服务器将文件发送回客户端。

>**旁注：客户端-服务器事务与数据库事务**
>
>客户端-服务器事务不是数据库事务，不具有数据库事务的任何属性（如原子性）。在本书的语境中，事务只是由客户端和服务器执行的一系列步骤。

4. 客户端收到响应并对其进行处理。例如，在 Web 浏览器从服务器收到一个页面后，它将其显示在屏幕上。

必须认识到，客户端和服务器是进程，而不是机器，或者在这种语境下通常所称的主机。一台主机可以同时运行许多不同的客户端和服务器，而客户端和服务器事务可以在同一台主机上，也可以在不同的主机上。无论客户端和服务器如何映射到主机，客户端-服务器模型都是相同的。

## 11.2 网络

客户端和服务器通常运行在不同的主机上，并使用计算机网络的硬件和软件资源进行通信。网络是复杂的系统，我们只能在这里做一个粗略的介绍。我们的目标是从程序员的角度为你提供一个可操作的思维模型。

插入 I/O 总线扩展槽的适配器提供了到网络的物理接口。从网络接收到的数据从适配器经过 I/O 总线和内存总线被复制到内存中，通常通过 DMA 传输完成。类似地，数据也可以从内存复制到网络。

从物理上看，网络是一个按地理位置组织的层次系统。最低层是局域网（LAN，Local Area Network），它覆盖一栋楼或一个校园。目前最流行的局域网技术是以太网（Ethernet），它于 20 世纪 70 年代中期在施乐帕洛阿尔托研究中心（Xerox PARC）研发。以太网已被证明具有显著的韧性，从最初的 3 Mb/s 演进到了 10 Gb/s。

一个以太网段（Ethernet segment）由一些电线（通常是双绞线）和一个称为集线器（hub）的小盒子组成，如图 11.3 所示。以太网段通常覆盖较小的区域，例如一个房间或楼层。每条电线具有相同的最大位带宽，通常为 100 Mb/s 或 1 Gb/s。电线的一端连接到主机上的适配器，另一端连接到集线器的一个端口。集线器会忠实地将它在每个端口接收到的每一位复制到其他所有端口。因此，每台主机都能看到每一位数据。

每个以太网适配器都有一个全局唯一的 48 位地址，存储在适配器上的非易失性内存中。主机可以向段上的任何其他主机发送一块称为帧（frame）的比特数据。每帧包含固定数量的头部位，用于标识帧的源地址和目的地址以及帧的长度，后面跟着数据位的有效载荷。每个主机适配器都会看到这个帧，但只有目的主机才会真正读取它。

多个以太网段可以通过一组电线和称为网桥（bridge）的小盒子连接成更大的局域网，称为桥接以太网（Bridged Ethernet），如图 11.4 所示。桥接以太网可以覆盖整栋楼或整个校园。在桥接以太网中，一些电线连接网桥与网桥，另一些连接网桥与集线器。这些电线的带宽可以不同。在我们的例子中，网桥-网桥电线的带宽为 1 Gb/s，而四条集线器-网桥电线的带宽为 100 Mb/s。

网桥比集线器更能有效利用可用的电线带宽。网桥使用一种巧妙的分布式算法，随着时间的推移自动学习哪些主机可以从哪些端口到达，然后仅在必要时有选择地将帧从一个端口复制到另一个端口。例如，如果主机 A 向同一段上的主机 B 发送一帧，那么网桥 X 在帧到达其输入端口时会丢弃该帧，从而节省其他段上的带宽。然而，如果主机 A 向不同段上的主机 C 发送一帧，那么网桥 X 只会将帧复制到连接网桥 Y 的端口，而网桥 Y 只会将帧复制到连接主机 C 所在段的端口。

互联网的关键特性是，它可以由具有截然不同且互不兼容的技术的不同局域网和广域网组成。每台主机在物理上与其他所有主机相连，但如何让某个源主机在所有这些不兼容的网络中将数据位发送到另一台目的主机呢？

解决方案是在每台主机和路由器上运行一层协议软件，以消除不同网络之间的差异。该软件实现了一种协议，规定主机和路由器如何协作以传输数据。该协议必须提供两种基本能力：

**命名方案。** 不同的局域网技术有不同且互不兼容的方式来为主机分配地址。互联网协议通过定义统一的主机地址格式来消除这些差异。然后，每台主机被分配至少一个这样的互联网地址，该地址能唯一标识它。

**传输机制。** 不同的网络技术有不同且互不兼容的方式来在电线上编码比特以及将这些比特打包成帧。互联网协议通过定义一种统一的方式将数据位打包成称为数据包（packet）的离散块来消除这些差异。一个数据包由一个头部和一个有效载荷组成，头部包含数据包的大小以及源主机和目的主机的地址，有效载荷包含从源主机发送的数据位。

图 11.7 展示了主机和路由器如何使用互联网协议在不兼容的局域网之间传输数据。示例互联网由通过一台路由器连接的两个局域网组成。运行在主机 A（连接到 LAN1）上的客户端向运行在主机 B（连接到 LAN2）上的服务器发送一系列数据字节。共有八个基本步骤：

1. 主机 A 上的客户端调用一个系统调用，将数据从客户端的虚拟地址空间复制到内核缓冲区。

2. 主机 A 上的协议软件通过在数据前添加一个互联网头部和一个 LAN1 帧头部，创建一个 LAN1 帧。互联网头部的目的地是互联网主机 B，LAN1 帧头部的目的地是路由器。然后，它将帧传递给适配器。注意，LAN1 帧的有效载荷是一个互联网数据包，而该数据包的有效载荷是实际的用户数据。这种封装是互联网络的基本思想之一。

3. LAN1 适配器将帧复制到网络。

6. 路由器的 LAN2 适配器将帧复制到网络。

7. 当帧到达主机 B 时，其适配器从电线上读取帧并将其传递给协议软件。

8. 最终，主机 B 上的协议软件去掉数据包头部和帧头部。当服务器调用读取数据的系统调用时，协议软件最终会将结果数据复制到服务器的虚拟地址空间。

当然，这里我们忽略了许多复杂问题。如果不同的网络有不同的最大帧大小怎么办？路由器如何知道向哪里转发帧？当网络拓扑结构变化时，路由器如何获知？如果数据包丢失怎么办？尽管如此，我们的示例捕捉了互联网思想的本质，而封装是关键。

## 11.3 全球 IP 因特网

全球 IP 因特网是互联网最著名也最成功的实现。它以某种形式存在已有 1969 年至今。虽然因特网的内部架构复杂且不断变化，但客户端-服务器应用程序的组织结构自 20 世纪 80 年代初以来一直保持着显著的稳定性。图 11.8 展示了因特网客户端-服务器应用程序的基本硬件和软件组织结构。

每台因特网主机都运行实现 TCP/IP 协议（传输控制协议/互联网协议，Transmission Control Protocol/Internet Protocol）的软件，几乎所有现代计算机系统都支持该协议。因特网客户端和服务器使用套接字接口函数和 Unix I/O 函数的混合来进行通信（我们将在 11.4 节描述套接字接口）。套接字函数通常被实现为系统调用，陷入内核并调用 TCP/IP 中的各种内核模式函数。

TCP/IP 实际上是一族协议，每种协议提供不同的功能。例如，IP 提供基本的命名方案和一种传输机制，可以将称为数据报（datagram）的数据包从一台因特网主机发送到任何其他主机。IP 机制是不可靠的，因为它不努力恢复网络中丢失或重复的数据报。UDP（不可靠数据报协议，Unreliable Datagram Protocol）对 IP 进行了轻微扩展，使得数据报可以在进程之间传输，而不仅仅是主机之间。TCP 是一种复杂的协议，建立在 IP 之上，为进程之间提供可靠的全双工（双向）连接。为了简化讨论，我们将 TCP/IP 视为一个单一的整体协议。我们不会讨论其内部工作原理，只讨论 TCP 和 IP 为应用程序提供的一些基本功能。我们不会讨论 UDP。

从程序员的角度来看，我们可以把因特网视为一个具有以下属性的全球主机集合：

- 主机集合被映射到一组 32 位 IP 地址。

>**旁注：IPv4 和 IPv6**
>
>原始的因特网协议使用 32 位地址，称为互联网协议第 4 版（IPv4）。1996 年，互联网工程任务组（IETF）提出了一种新版本的 IP，称为互联网协议第 6 版（IPv6），使用 128 位地址，旨在作为 IPv4 的继承者。然而，截至 2015 年，近 20 年后，绝大多数因特网流量仍然通过 IPv4 网络传输。例如，只有 4% 的用户使用 IPv6 访问 Google 服务[42]。
>
>由于其低采用率，我们不会在本书中详细讨论 IPv6，而将专注于 IPv4 背后的概念。当我们谈论因特网时，我们指的是基于 IPv4 的因特网。尽管如此，我们将在本章后面教给你的编写客户端和服务器的技术基于现代接口，独立于任何特定协议。

- IP 地址集合被映射到一组称为因特网域名（Internet domain names）的标识符。

- 一台因特网主机上的进程可以通过连接与任何其他因特网主机上的进程进行通信。

以下各节将更详细地讨论这些基本因特网概念。

### 11.3.1 IP 地址

IP 地址是一个无符号的 32 位整数。网络程序将 IP 地址存储在图 11.9 所示的 IP 地址结构中。

将标量地址存储在结构中是早期套接字接口实现中的一个遗留问题。为 IP 地址定义标量类型会更合理，但由于已安装的应用程序基数庞大，现在改变为时已晚。

由于因特网主机可以有不同的主机字节序，TCP/IP 为在网络上的数据包头部中传输的任何整数数据项（如 IP 地址）定义了统一的网络字节序（大端字节序）。IP 地址结构中的地址始终以（大端）网络字节序存储，即使主机字节序是小端的。Unix 提供以下函数用于在网络字节序和主机字节序之间进行转换。

```c
code/netp/netpfragments.c
/* IP address structure */
struct in_addr {
    uint32_t s_addr; /* Address in network byte order (big-endian) */
};
code/netp/netpfragments.c
```

```c
#include <arpa/inet.h>

uint32_t htonl(uint32_t hostlong);
uint16_t htons(uint16_t hostshort);
返回：网络字节序的值

uint32_t ntohl(uint32_t netlong);
uint16_t ntohs(uint16_t netshort);
返回：主机字节序的值
```

`htonl` 函数将无符号 32 位整数从主机字节序转换为网络字节序。`ntohl` 函数将无符号 32 位整数从网络字节序转换为主机字节序。`htons` 和 `ntohs` 函数对无符号 16 位整数执行相应的转换。注意，没有用于操纵 64 位值的等效函数。

IP 地址通常以一种称为点分十进制表示法（dotted-decimal notation）的形式呈现给人类，其中每个字节由其十进制值表示，并用句点与其他字节分隔。例如，128.2.194.242 是地址 $0x8002c2f2$ 的点分十进制表示。在 Linux 系统上，你可以使用 `hostname` 命令来确定自己主机的点分十进制地址：

```
linux> hostname -i
128.2.210.175
```

应用程序可以使用函数 `inet_pton` 和 `inet_ntop` 在 IP 地址和点分十进制字符串之间进行转换。

```c
#include <arpa/inet.h>
int inet_pton(AF_INET, const char *src, void *dst);
    返回：成功返回 1，src 是无效点分十进制返回 0，出错返回 -1

const char *inet_ntop(AF_INET, const void *src, char *dst,
                   socklen_t size);
    返回：成功返回指向点分十进制字符串的指针，出错返回 NULL
```

在这些函数名中，"n"代表网络（network），"p"代表表示（presentation）。它们可以操纵 32 位 IPv4 地址（`AF_INET`）（如此处所示），或 128 位 IPv6 地址（`AF_INET6`）（我们不讨论后者）。

`inet_pton` 函数将点分十进制字符串（`src`）转换为网络字节序的二进制 IP 地址（`dst`）。如果 `src` 不指向有效的点分十进制字符串，则返回 0。任何其他错误返回 -1 并设置 `errno`。类似地，`inet_ntop` 函数将网络字节序的二进制 IP 地址（`src`）转换为相应的点分十进制表示，并将最多 `size` 字节的结果以空字符结尾的字符串复制到 `dst`。

### 11.3.3 因特网连接

因特网客户端和服务器通过连接发送和接收字节流来进行通信。连接是点对点的，因为它连接的是一对进程。它是全双工的，因为数据可以同时在两个方向上流动。

---

<!-- Page 0953 -->

>**旁注：因特网上有多少台主机？**
>
>自 1987 年起，互联网系统联盟（Internet Systems Consortium）每年两次进行因特网域名调查。该调查通过统计已分配域名的 IP 地址数量来估计因特网主机的数量，揭示了一个惊人的趋势。自 1987 年（当时约有 20,000 台因特网主机）以来，主机数量一直在呈指数级增长。到 2015 年，因特网主机数量已超过 10 亿台！

并且它是可靠的——除非发生某些灾难性故障（例如粗心的挖掘机操作员切断了电缆）——源进程发送的字节流最终以相同的顺序被目的进程接收。

套接字（socket）是连接的端点。每个套接字都有一个对应的套接字地址，由因特网地址和一个 16 位整数端口$^{2}$组成，用 `地址:端口` 表示。

客户端套接字地址中的端口由内核在客户端发出连接请求时自动分配，称为临时端口（ephemeral port）。然而，服务器套接字地址中的端口通常是某个与服务永久关联的知名端口（well-known port）。例如，Web 服务器通常使用端口 80，电子邮件服务器使用端口 25。与每个知名端口相关联的服务都有一个对应的知名服务名称。例如，Web 服务的知名名称是 `http`，电子邮件的知名名称是 `smtp`。知名名称和知名端口之间的映射包含在一个名为 `/etc/services` 的文件中。

连接由其两个端点的套接字地址唯一标识。这对套接字地址称为套接字对（socket pair），用元组表示为：

```
(cliaddr:cliport, servaddr:servport)
```

其中 `cliaddr` 是客户端的 IP 地址，`cliport` 是客户端的端口，`servaddr` 是服务器的 IP 地址，`servport` 是服务器的端口。例如，图 11.11 展示了 Web 客户端和 Web 服务器之间的连接。

在这个例子中，Web 客户端的套接字地址是：

```
128.2.194.242:51213
```

其中端口 51213 是由内核分配的临时端口。Web 服务器的套接字地址是：

```
208.216.181.15:80
```

### 11.4.1 套接字地址结构

从 Linux 内核的角度来看，套接字是通信的端点。从 Linux 程序的角度来看，套接字是一个带有相应描述符的打开文件。

因特网套接字地址存储在类型为 `sockaddr_in` 的 16 字节结构中，如图 11.13 所示。对于因特网应用程序，`sin_family` 字段为 `AF_INET`，`sin_port` 字段是一个 16 位端口号，`sin_addr` 字段包含一个 32 位 IP 地址。IP 地址和端口号始终以网络（大端）字节序存储。

`connect`、`bind` 和 `accept` 函数要求一个指向协议特定套接字地址结构的指针。套接字接口设计者面临的问题是如何定义这些函数以接受任何类型的套接字地址结构。今天，我们会使用通用的 `void *` 指针，但在当时的 C 语言中并不存在。他们的解决方案是将套接字函数定义为接受一个指向通用 `sockaddr` 结构的指针（图 11.13），然后要求应用程序将任何指向协议特定结构的指针强制转换为该通用结构。为了简化代码示例，我们遵循 Stevens 的做法，定义以下类型：

```c
typedef struct sockaddr SA;
```

然后，每当我们需要将协议特定的套接字地址结构强制转换为通用结构时，就使用这个类型。

### 11.4.2 `socket` 函数

客户端和服务器使用 `socket` 函数来创建套接字描述符。

```c
#include <sys/types.h>
#include <sys/socket.h>

int socket(int domain, int type, int protocol);
返回：成功返回非负描述符，出错返回 -1
```

如果我们希望套接字是连接的端点，可以使用以下硬编码参数调用 `socket`：

```c
clientfd = Socket(AF_INET, SOCK_STREAM, 0);
```

其中 `AF_INET` 表示我们使用 32 位 IP 地址，`SOCK_STREAM` 表示套接字将是连接的端点。然而，最佳实践是使用 `getaddrinfo` 函数（第 11.4.7 节）来自动生成这些参数，使代码与协议无关。我们将在第 11.4.8 节展示如何在 `socket` 函数中使用 `getaddrinfo`。

`socket` 返回的 `clientfd` 描述符只是部分打开，尚不能用于读写。我们如何完成套接字的打开取决于我们是客户端还是服务器。下一节将描述如果我们是客户端，如何完成套接字的打开。

### 11.4.3 `connect` 函数

客户端通过调用 `connect` 函数与服务器建立连接。

```c
#include <sys/socket.h>
int connect(int clientfd, const struct sockaddr *addr,
                 socklen_t addrlen);
返回：成功返回 0，出错返回 -1
```

`connect` 函数尝试与套接字地址 `addr` 处的服务器建立因特网连接，其中 `addrlen` 为 `sizeof(sockaddr_in)`。`connect` 函数会阻塞，直到连接成功建立或发生错误。如果成功，`clientfd` 描述符现在可以用于读写，结果连接由套接字对表征：

```
(x:y, addr.sin_addr:addr.sin_port)
```

---

<!-- Page 0958 -->

其中 `x` 是客户端的 IP 地址，`y` 是唯一标识客户端主机上客户端进程的临时端口。与 `socket` 一样，最佳实践是使用 `getaddrinfo` 为 `connect` 提供参数（参见第 11.4.8 节）。

### 11.4.4 `bind` 函数

其余的套接字函数——`bind`、`listen` 和 `accept`——被服务器用来与客户端建立连接。

```c
#include <sys/socket.h>
int bind(int sockfd, const struct sockaddr *addr,
               socklen_t addrlen);
返回：成功返回 0，出错返回 -1
```

`bind` 函数要求内核将 `addr` 中的服务器套接字地址与套接字描述符 `sockfd` 相关联。`addrlen` 参数为 `sizeof(sockaddr_in)`。与 `socket` 和 `connect` 一样，最佳实践是使用 `getaddrinfo` 为 `bind` 提供参数（参见第 11.4.8 节）。

### 11.4.5 `listen` 函数

客户端是主动实体，它们发起连接请求。服务器是被动实体，等待来自客户端的连接请求。默认情况下，内核假定由 `socket` 函数创建的描述符对应于一个活动套接字，该套接字将存在于连接的客户端。服务器调用 `listen` 函数来告诉内核描述符将由服务器而不是客户端使用。

```c
#include <sys/socket.h>
int listen(int sockfd, int backlog);
返回：成功返回 0，出错返回 -1
```

`listen` 函数将 `sockfd` 从活动套接字转换为监听套接字（listening socket），可以接受来自客户端的连接请求。`backlog` 参数是一个提示，表示在内核开始拒绝请求之前应该排队等待的未完成连接请求数量。`backlog` 参数的确切含义需要对 TCP/IP 有超出我们范围的理解。我们通常将其设置为一个较大的值，例如 1,024。

### 11.4.6 `accept` 函数

服务器通过调用 `accept` 函数等待来自客户端的连接请求。

```c
#include <sys/socket.h>
int accept(int listenfd, struct sockaddr *addr, int *addrlen);
返回：成功返回非负已连接描述符，出错返回 -1
```

`accept` 函数等待来自客户端的连接请求到达监听描述符 `listenfd`，然后填写客户端的套接字地址到 `addr` 中，并返回一个已连接描述符（connected descriptor），该描述符可用于使用 Unix I/O 函数与客户端进行通信。

监听描述符和已连接描述符之间的区别让许多同学感到困惑。监听描述符作为客户端连接请求的端点，通常创建一次，在服务器的生命周期内存在。已连接描述符是客户端和服务器之间建立的连接的端点，每次服务器接受连接请求时创建，仅在服务器为客户端提供服务所需的时间内存在。

图 11.14 概述了监听描述符和已连接描述符的角色。在第 1 步，服务器调用 `accept`，等待连接请求到达监听描述符（为具体起见，我们假设是描述符 3）。回想一下，描述符 0–2 保留用于标准文件。

在第 2 步，客户端调用 `connect` 函数，向 `listenfd` 发送连接请求。在第 3 步，`accept` 函数打开一个新的已连接描述符 `connfd`（我们假设是描述符 4），建立 `clientfd` 和 `connfd` 之间的连接，然后将 `connfd` 返回给应用程序。

>**旁注：为何区分监听描述符和已连接描述符？**
>
>你可能想知道为什么套接字接口要区分监听描述符和已连接描述符。乍一看，这似乎是不必要的复杂化。然而，区分这两者实际上非常有用，因为它允许我们构建能同时处理许多客户端连接的并发服务器。例如，每次有连接请求到达监听描述符时，我们可以 `fork` 一个新进程，通过其已连接描述符与客户端通信。你将在第 12 章中了解更多关于并发服务器的内容。

客户端也从 `connect` 返回，从这一点开始，客户端和服务器可以分别通过读写 `clientfd` 和 `connfd` 来来回回地传递数据。

### 11.4.7 主机和服务的转换

Linux 提供了一些强大的函数，称为 `getaddrinfo` 和 `getnameinfo`，用于在二进制套接字地址结构与主机名、主机地址、服务名称和端口号的字符串表示之间进行相互转换。与套接字接口结合使用时，它们允许我们编写独立于任何特定 IP 协议版本的网络程序。

**`getaddrinfo` 函数**

`getaddrinfo` 函数将主机名、主机地址、服务名称和端口号的字符串表示转换为套接字地址结构。它是已过时的 `gethostbyname` 和 `getservbyname` 函数的现代替代品。与这些函数不同，它是可重入的（参见第 12.7.2 节），并适用于任何协议。

```c
                      const struct addrinfo *hints,

    返回：成功返回 0，出错返回非零错误码

    返回：无

    返回：错误信息
```

给定主机和服务（套接字地址的两个组成部分），`getaddrinfo` 返回一个 `result`，指向 `addrinfo` 结构的链表，其中每个结构都指向一个对应于主机和服务的套接字地址结构（图 11.15）。

客户端调用 `getaddrinfo` 后，遍历这个链表，依次尝试每个套接字地址，直到调用 `socket` 和 `connect` 成功并建立连接。类似地，服务器遍历链表，直到调用 `socket` 和 `bind` 成功，描述符绑定到有效的套接字地址。为了避免内存泄漏，应用程序最终必须通过调用 `freeaddrinfo` 来释放链表。如果 `getaddrinfo` 返回非零错误码，应用程序可以调用 `gai_strerror` 将错误码转换为消息字符串。

`getaddrinfo` 的 `host` 参数可以是域名，也可以是数字地址（例如，点分十进制 IP 地址）。`service` 参数可以是服务名称（例如 `http`），也可以是十进制端口号。如果我们不想将主机名转换为地址，可以将 `host` 设置为 `NULL`，`service` 同理。但是，至少必须指定其中一个。

可选的 `hints` 参数是一个 `addrinfo` 结构（图 11.16），它提供对 `getaddrinfo` 返回的套接字地址列表的更精细控制。当作为 `hints` 参数传递时，只能设置 `ai_family`、`ai_socktype`、`ai_protocol` 和 `ai_flags` 字段，其他字段必须设置为零（或 `NULL`）。在实践中，我们使用 `memset` 将整个结构清零，然后设置几个选定的字段：

- 默认情况下，`getaddrinfo` 可以返回 IPv4 和 IPv6 套接字地址。将 `ai_family` 设置为 `AF_INET` 可将列表限制为 IPv4 地址，设置为 `AF_INET6` 则限制为 IPv6 地址。

```c
    int     ai_socktype;    /* Second arg to socket function */
```

<div style="text-align: center;">图 11.16 `getaddrinfo` 使用的 `addrinfo` 结构。</div>

- 默认情况下，对于与主机相关联的每个唯一地址，`getaddrinfo` 函数最多可以返回三个 `addrinfo` 结构，每个结构具有不同的 `ai_socktype` 字段：一个用于连接，一个用于数据报（不介绍），一个用于原始套接字（不介绍）。将 `ai_socktype` 设置为 `SOCK_STREAM` 可将列表限制为每个唯一地址最多一个 `addrinfo` 结构，其套接字地址可用作连接的端点。这是我们所有示例程序的所需行为。

- `ai_flags` 字段是一个位掩码，进一步修改默认行为。通过对各种值进行位或运算来创建它。以下是一些我们认为有用的值：

  `AI_ADDRCONFIG`：如果你使用连接，推荐使用此标志[34]。它要求 `getaddrinfo` 仅在本地主机配置了 IPv4 时才返回 IPv4 地址，IPv6 同理。

  `AI_CANONNAME`：默认情况下，`ai_canonname` 字段为 `NULL`。如果设置此标志，它会指示 `getaddrinfo` 将列表中第一个 `addrinfo` 结构的 `ai_canonname` 字段指向主机的规范（官方）名称（参见图 11.15）。

  `AI_NUMERICSERV`：默认情况下，`service` 参数可以是服务名称或端口号。此标志强制 `service` 参数为端口号。

  `AI_PASSIVE`：默认情况下，`getaddrinfo` 返回可供客户端用作活动套接字调用 `connect` 的套接字地址。此标志指示它返回可供服务器用作监听套接字的套接字地址。在这种情况下，`host` 参数应为 `NULL`。结果套接字地址结构中的地址字段将是通配符地址，告诉内核此服务器将接受对该主机任何 IP 地址的请求。这是我们所有示例服务器的所需行为。

当 `getaddrinfo` 在输出列表中创建一个 `addrinfo` 结构时，它会填写除 `ai_flags` 之外的每个字段。`ai_addr` 字段指向一个套接字地址结构，`ai_addrlen` 字段给出该套接字地址结构的大小，`ai_next` 字段指向列表中的下一个 `addrinfo` 结构。其他字段描述了套接字地址的各种属性。

`getaddrinfo` 的一个优雅之处在于 `addrinfo` 结构中的字段是不透明的（opaque），即它们可以直接传递给套接字接口中的函数，而无需应用程序代码进行任何进一步的操作。例如，`ai_family`、`ai_socktype` 和 `ai_protocol` 可以直接传递给 `socket`；`ai_addr` 和 `ai_addrlen` 可以直接传递给 `connect` 和 `bind`。这种强大的特性使我们能够编写独立于任何特定 IP 协议版本的客户端和服务器。

**`getnameinfo` 函数**

`getnameinfo` 函数是 `getaddrinfo` 的逆函数。它将套接字地址结构转换为相应的主机和服务名称字符串。它是已过时的 `gethostbyaddr` 和 `getservbyport` 函数的现代替代品，与那些函数不同，它是可重入且与协议无关的。

```c
#include <sys/socket.h>
#include <netdb.h>

int getnameinfo(const struct sockaddr *sa, socklen_t salen, char *host,
                size_t hostlen, char *service, size_t servlen, int flags);
返回：成功返回 0，出错返回非零错误码
```

`sa` 参数指向大小为 `salen` 字节的套接字地址结构，`host` 指向大小为 `hostlen` 字节的缓冲区，`service` 指向大小为 `servlen` 字节的缓冲区。`getnameinfo` 函数将套接字地址结构 `sa` 转换为相应的主机和服务名称字符串，并将它们复制到 `host` 和 `service` 缓冲区中。如果 `getnameinfo` 返回非零错误码，应用程序可以通过调用 `gai_strerror` 将其转换为字符串。

如果我们不想要主机名，可以将 `host` 设置为 `NULL`，`hostlen` 设置为零，`service` 字段同理。但是，两者中必须有一个被设置。

`flags` 参数是一个位掩码，用于修改默认行为。通过对各种值进行位或运算来创建它。以下是几个有用的值：

`NI_NUMERICHOST`：默认情况下，`getnameinfo` 尝试在 `host` 中返回域名。设置此标志将使其返回数字地址字符串。

`NI_NUMERICSERV`：默认情况下，`getnameinfo` 会在 `/etc/services` 中查找，并在可能的情况下返回服务名称而不是端口号。设置此标志强制它跳过查找，直接返回端口号。

### 11.4.8 套接字接口的辅助函数

当你第一次学习 `getaddrinfo` 函数和套接字接口时，它们可能显得有些令人望而生畏。我们发现，将它们包装在更高层次的辅助函数中会很方便，这些函数称为 `open_clientfd` 和 `open_listenfd`，客户端和服务器在相互通信时可以使用这些函数。

**`open_clientfd` 函数**

客户端通过调用 `open_clientfd` 与服务器建立连接。

```c
#include "csapp.h"
int open_clientfd(char *hostname, char *port);
返回：成功返回描述符，出错返回 -1
```

`open_clientfd` 函数与在主机 `hostname` 上运行并在端口号 `port` 上监听连接请求的服务器建立连接。它返回一个打开的套接字描述符，可立即使用 Unix I/O 函数进行输入和输出。图 11.18 展示了 `open_clientfd` 的代码。

我们调用 `getaddrinfo`，它返回一个 `addrinfo` 结构列表，每个结构都指向一个适合与在 `hostname` 上运行并在 `port` 上监听的服务器建立连接的套接字地址结构。

---

<!-- Page 0966 -->

```c
int open_clientfd(char *hostname, char *port) {
    int clientfd;
    struct addrinfo hints, *listp, *p;

    /* Get a list of potential server addresses */
    memset(&hints, 0, sizeof(struct addrinfo));
    hints.ai_socktype = SOCK_STREAM; /* Open a connection */
    hints.ai_flags = AI_NUMERICSERV; /*... using a numeric port arg. */
    hints.ai_flags |= AI_ADDRCONFIG; /* Recommended for connections */
    Getaddrinfo(hostname, port, &hints, &listp);

    /* Walk the list for one that we can successfully connect to */
    for (p = listp; p; p = p->ai_next) {
        /* Create a socket descriptor */
        if ((clientfd = socket(p->ai_family, p->ai_socktype, p->ai_protocol)) < 0)
            continue; /* Socket failed, try the next */

        /* Connect to the server */
        if (connect(clientfd, p->ai_addr, p->ai_addrlen) != -1)
            break; /* Success */
        Close(clientfd); /* Connect failed, try another */
    }

    /* Clean up */
    Freeaddrinfo(listp);
    if (!p) /* All connects failed */
        return -1;
    else    /* The last connect succeeded */
        return clientfd;
}
```

<div style="text-align: center;">图 11.18 `open_clientfd`：建立与服务器连接的辅助函数，可重入且与协议无关。</div>

然后我们遍历列表，依次尝试每个条目，直到 `socket` 和 `connect` 的调用成功。如果 `connect` 失败，我们会小心地在尝试下一个条目之前关闭套接字描述符。如果 `connect` 成功，我们释放列表内存，并将套接字描述符返回给客户端，客户端随即可以使用 Unix I/O 与服务器通信。

注意在整个代码中没有对任何特定 IP 版本的依赖。`socket` 和 `connect` 的参数由 `getaddrinfo` 自动为我们生成，使我们的代码简洁且可移植。

**`open_listenfd` 函数**


`open_listenfd` 函数返回一个监听描述符，该描述符准备好接收端口 `port` 上的连接请求。图 11.19 展示了 `open_listenfd` 的代码。

风格类似于 `open_clientfd`。我们调用 `getaddrinfo`，然后遍历结果列表，直到 `socket` 和 `bind` 的调用成功。注意在第 20 行，我们使用 `setsockopt` 函数（这里不详细介绍）来配置服务器，使其可以被终止、重启并立即开始接受连接请求。默认情况下，重启的服务器大约会拒绝客户端连接请求 30 秒，这严重妨碍了调试。

### 11.4.9 回显客户端和服务器示例

学习套接字接口的最佳方式是研究示例代码。图 11.20 展示了回显客户端的代码。与服务器建立连接后，客户端进入一个循环，该循环反复从标准输入读取文本行，将文本行发送到服务器，从服务器读取回显行，并将结果打印到标准输出。当 `fgets` 遇到标准输入上的 EOF 时，循环终止，可能是因为用户在键盘上输入了 Ctrl+D，或者是因为它已经处理完重定向输入文件中的所有文本行。

循环终止后，客户端关闭描述符。这会向服务器发送 EOF 通知，服务器在其 `rio_readlineb` 函数返回零时检测到这一点。关闭描述符后，客户端终止。由于客户端的内核在进程终止时会自动关闭所有打开的描述符，因此第 24 行的 `close` 不是必要的。但是，显式关闭你已打开的任何描述符是良好的编程习惯。

图 11.21 展示了回显服务器的主例程。打开监听描述符后，它进入一个无限循环。每次迭代等待来自客户端的连接请求，打印已连接客户端的域名和端口，然后调用为客户端服务的 `echo` 函数。`echo` 例程返回后，

```c
int open_listenfd(char *port)
{
    struct addrinfo hints, *listp, *p;
    int listenfd, optval=1;

    /* Get a list of potential server addresses */
    memset(&hints, 0, sizeof(struct addrinfo));
    hints.ai_socktype = SOCK_STREAM; /* Accept connections */
    hints.ai_flags = AI_PASSIVE | AI_ADDRCONFIG; /*... on any IP address */
    hints.ai_flags |= AI_NUMERICSERV; /*... using port number */
    Getaddrinfo(NULL, port, &hints, &listp);

    /* Walk the list for one that we can bind to */
    for (p = listp; p; p = p->ai_next) {
        /* Create a socket descriptor */
        if ((listenfd = socket(p->ai_family, p->ai_socktype, p->ai_protocol)) < 0)
            continue; /* Socket failed, try the next */

        /* Eliminates "Address already in use" error from bind */
        Setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR,
                          (const void *)&optval, sizeof(int));

        /* Bind the descriptor to the address */
        if (bind(listenfd, p->ai_addr, p->ai_addrlen) == 0)
            break; /* Success */
        Close(listenfd); /* Bind failed, try the next */
    }

    /* Clean up */
    Freeaddrinfo(listp);
    if (!p) /* No address worked */
        return -1;

    /* Make it a listening socket ready to accept connection requests */
    if (listen(listenfd, LISTENQ) < 0) {
        Close(listenfd);
        return -1;
    }
    return listenfd;
}
```

## 11.5 Web 服务器

到目前为止，我们在一个简单的回显服务器的上下文中讨论了网络编程。在本节中，我们将向你展示如何使用网络编程的基本思想来构建你自己的小型但功能齐全的 Web 服务器。

### 11.5.1 Web 基础

Web 客户端和服务器使用一种基于文本的应用层协议进行交互，该协议称为 HTTP（超文本传输协议，Hypertext Transfer Protocol）。HTTP 是一个简单的协议。Web 客户端（即浏览器）向服务器打开一个 Internet 连接并请求某些内容。服务器响应请求的内容，然后关闭连接。浏览器读取内容并在屏幕上显示它。

Web 服务与传统文件检索服务（如 FTP）有何区别？主要区别在于 Web 内容可以用一种称为 HTML（超文本标记语言，Hypertext Markup Language）的语言编写。HTML 程序（页面）包含指令（标签），告诉浏览器如何在页面中显示各种文本和图形对象。例如，代码

```html
<b> Make me bold! </b>
```

告诉浏览器以粗体打印 `<b>` 和 `</b>` 标签之间的文本。然而，HTML 真正的强大之处在于页面可以包含指向存储在任何 Internet 主机上的内容的指针（超链接）。例如，一行这种形式的 HTML：

```html
<a href="http://www.cmu.edu/index.html">Carnegie Mellon</a>
```

告诉浏览器高亮显示文本对象 Carnegie Mellon，并创建一个指向存储在 CMU Web 服务器上名为 `index.html` 的 HTML 文件的超链接。如果用户点击高亮显示的文本对象，浏览器会从 CMU 服务器请求相应的 HTML 文件并显示它。

### 11.5.2 Web 内容

对于 Web 客户端和服务器而言，内容是具有关联 MIME（多用途互联网邮件扩展，Multipurpose Internet Mail Extensions）类型的字节序列。图 11.23 展示了一些常见的 MIME 类型。

Web 服务器以两种不同的方式向客户端提供内容：

- 获取磁盘文件并将其内容返回给客户端。磁盘文件称为**静态内容**，将文件返回给客户端的过程称为**提供静态内容**。
- 运行可执行文件并将其输出返回给客户端。可执行文件在运行时产生的输出称为**动态内容**，运行程序并将其输出返回给客户端的过程称为**提供动态内容**。

Web 服务器返回的每一段内容都与它管理的某个文件相关联。这些文件中的每一个都有一个称为 URL（统一资源定位符，Universal Resource Locator）的唯一名称。例如，URL

```
http://www.google.com:80/index.html
```

---

<!-- Page 0973 -->

标识了 Internet 主机 `www.google.com` 上名为 `/index.html` 的 HTML 文件，该文件由监听端口 80 的 Web 服务器管理。端口号是可选的，默认为众所周知的 HTTP 端口 80。可执行文件的 URL 可以在文件名后面包含程序参数。`?` 字符将文件名与参数分隔，每个参数用 `&` 字符分隔。例如，URL

```
http://bluefish.ics.cs.cmu.edu:8000/cgi-bin/adder?15000&213
```

标识了一个名为 `/cgi-bin/adder` 的可执行文件，它将用两个参数字符串 `15000` 和 `213` 被调用。客户端和服务器在事务期间使用 URL 的不同部分。例如，客户端使用前缀

```
http://www.google.com:80
```

来确定联系什么类型的服务器、服务器在哪里以及它在监听哪个端口。服务器使用后缀

```
/index.html
```

来查找其文件系统上的文件，并确定请求的是静态内容还是动态内容。

关于服务器如何解释 URL 后缀，有几点需要理解：

- 没有确定 URL 是指静态内容还是动态内容的标准规则。每个服务器都有其自己的规则来管理文件。一种经典（旧式）方法是标识一组目录，例如 `cgi-bin`，所有可执行文件必须驻留在其中。
- 后缀中的初始 `/` 不表示 Linux 根目录。相反，它表示正在请求的内容类型的主目录。例如，服务器可能配置为所有静态内容存储在目录 `/usr/httpd/html` 中，所有动态内容存储在目录 `/usr/httpd/cgi-bin` 中。
- 最小 URL 后缀是 `/` 字符，所有服务器都将其扩展为某个默认主页，例如 `/index.html`。这解释了为什么只需在浏览器中键入域名即可获取站点主页。浏览器将缺少的 `/` 附加到 URL 并将其传递给服务器，服务器将 `/` 展开为某个默认文件名。

#### HTTP 请求

HTTP 请求由一个请求行（第 5 行）组成，后跟零个或多个请求头（第 6 行），后跟一个终止头列表的空文本行（第 7 行）。请求行的形式为

```
method URI version
```

HTTP 支持许多不同的方法，包括 GET、POST、OPTIONS、HEAD、PUT、DELETE 和 TRACE。我们只讨论主力 GET 方法，它占了大多数 HTTP 请求。GET 方法指示服务器生成并返回由 URI 标识的内容。

---

<!-- Page 0975 -->

（统一资源标识符，Uniform Resource Identifier）。URI 是相应 URL 的后缀，包括文件名和可选参数。$^3$

请求行中的 `version` 字段指示请求所遵循的 HTTP 版本。最新的 HTTP 版本是 HTTP/1.1 [37]。HTTP/1.0 是 1996 年发布的早期更简单的版本 [6]。HTTP/1.1 定义了额外的头，提供对高级功能（如缓存和安全性）的支持，以及允许客户端和服务器通过同一持久连接执行多个事务的机制。实际上，这两个版本是兼容的，因为 HTTP/1.0 客户端和服务器只需忽略未知的 HTTP/1.1 头。

总而言之，第 5 行中的请求行要求服务器获取并返回 HTML 文件 `/index.html`。它还通知服务器请求的其余部分将采用 HTTP/1.1 格式。

请求头向服务器提供附加信息，例如浏览器的品牌名称或浏览器理解的 MIME 类型。请求头的形式为

```
header-name: header-data
```

对于我们的目的，唯一需要关注的头是 `Host` 头（第 6 行），它在 HTTP/1.1 请求中是必需的，但在 HTTP/1.0 请求中不是必需的。`Host` 头由代理缓存使用，代理缓存有时充当浏览器和管理所请求文件的源服务器之间的中间人。多个代理可以存在于客户端和源服务器之间，形成所谓的代理链。`Host` 头中的数据标识源服务器的域名，允许代理链中间的代理确定它是否可能有请求内容的本地缓存副本。

继续图 11.24 中的示例，第 7 行中的空文本行（通过在键盘上按回车键生成）终止头，并指示服务器发送请求的 HTML 文件。

```

```

`version` 字段描述响应所遵循的 HTTP 版本。`status-code` 是一个三位正整数，表示请求的处置情况。`status-message` 给出错误码的英文等价文本。图 11.25 列出了一些常见的状态码及其相应的消息。

### 11.5.4 提供动态内容

```c
#include "csapp.h"

int main(void) {
    char *buf, *p;
    char arg1[MAXLINE], arg2[MAXLINE], content[MAXLINE];
    int n1=0, n2=0;

    /* Extract the two arguments */
    if ((buf = getenv("QUERY_STRING")) != NULL) {
        p = strchr(buf, '&');
        *p = '\0';
        strcpy(arg1, buf);
        strcpy(arg2, p+1);
        n1 = atoi(arg1);
        n2 = atoi(arg2);
    }

    /* Make the response body */
    sprintf(content, "QUERY_STRING=%s", buf);
    sprintf(content, "Welcome to add.com: ");
    sprintf(content, "%s THE Internet addition portal.\r\n<p>", content);
    sprintf(content, "%s The answer is: %d + %d = %d\r\n<p>", content, n1, n2, n1 + n2);
    sprintf(content, "%s Thanks for visiting!\r\n", content);

    /* Generate the HTTP response */
    printf("Connection: close\r\n");
    printf("Content-length: %d\r\n", (int)strlen(content));
    printf("Content-type: text/html\r\n\r\n");
    printf("%s", content);
    fflush(stdout);

    exit(0);
}
```

```c
int parse_uri(char *uri, char *filename, char *cgiargs)
{
    char *ptr;

    if (!strstr(uri, "cgi-bin")) { /* Static content */
        strcpy(cgiargs, "");
        strcpy(filename, ".");
        strcat(filename, uri);
        if (uri[strlen(uri)-1] == '/')
            strcat(filename, "home.html");
        return 1;
    }
    else { /* Dynamic content */
        ptr = index(uri, '?');
        if (ptr) {
            strcpy(cgiargs, ptr+1);
            *ptr = '\0';
        }
        else
            strcpy(cgiargs, "");
        strcpy(filename, ".");
        strcat(filename, uri);
        return 0;
    }
}
```

TINY 通过派生子进程，然后在子进程的上下文中运行 CGI 程序来提供任何类型的动态内容。

```c
void serve_dynamic(int fd, char *filename, char *cgiargs)
{
    char buf[MAXLINE], *emptylist[] = { NULL };

    /* Return first part of HTTP response */
    sprintf(buf, "HTTP/1.0 200 OK\r\n");
    Rio_writen(fd, buf, strlen(buf));
    sprintf(buf, "Server: Tiny Web Server\r\n");
    Rio_writen(fd, buf, strlen(buf));

    if (Fork() == 0) { /* Child */
        /* Real server would set all CGI vars here */
        setenv("QUERY_STRING", cgiargs, 1);
        Dup2(fd, STDOUT_FILENO); /* Redirect stdout to client */
        Execve(filename, emptylist, environ); /* Run CGI program */
    }
    Wait(NULL); /* Parent waits for and reaps child */
}
```

> **旁注：处理过早关闭的连接**
>
> 虽然 Web 服务器的基本功能非常简单，但我们不想给你留下编写真实 Web 服务器很容易的错误印象。构建一个能长时间运行而不崩溃的健壮 Web 服务器是一项困难的任务，需要比我们在这里学到的更深入地理解 Linux 系统编程。例如，如果服务器向客户端已经关闭的连接写入（比如因为你点击了浏览器上的"停止"按钮），那么第一次写入会正常返回，但第二次写入会导致传递一个 `SIGPIPE` 信号，其默认行为是终止进程。如果 `SIGPIPE` 信号被捕获或忽略，则第二次写入操作返回 `-1`，`errno` 被设置为 `EPIPE`。`strerror` 和 `perror` 函数将 `EPIPE` 错误报告为"Broken pipe"，这是一个让历代学生困惑的晦涩消息。底线是，健壮的服务器必须捕获这些 `SIGPIPE` 信号并检查写入函数调用中的 `EPIPE` 错误。

接下来，子进程将子进程的标准输出重定向到已连接的文件描述符（第 14 行），然后加载并运行 CGI 程序（第 15 行）。由于 CGI 程序在子进程的上下文中运行，它可以访问在调用 `execve` 函数之前存在的相同打开文件和环境变量。因此，CGI 程序写入标准输出的所有内容都直接传输到客户端进程，无需父进程的任何干预。与此同时，父进程在 `wait` 调用中阻塞，等待子进程终止时回收它（第 17 行）。

## 11.7 小结

每个网络应用程序都基于客户端-服务器模型。在这个模型中，应用程序由一个服务器和一个或多个客户端组成。服务器管理资源，通过以某种方式操纵资源为客户端提供服务。客户端-服务器模型中的基本操作是客户端-服务器事务，它由客户端的请求，以及服务器的响应组成。

客户端和服务器通过一个称为 Internet 的全球网络进行通信。从程序员的角度来看，我们可以将 Internet 视为具有以下属性的全球主机集合：（1）每个 Internet 主机都有一个称为其 IP 地址的唯一 32 位名称。（2）IP 地址集合被映射到一组 Internet 域名。（3）不同 Internet 主机上的进程可以通过连接相互通信。

客户端和服务器使用套接字接口建立连接。套接字是以文件描述符形式呈现给应用程序的连接端点。套接字接口提供了打开和关闭套接字描述符的函数。客户端和服务器通过读写这些描述符相互通信。

---

<!-- Page 0988 -->

Web 服务器及其客户端（如浏览器）使用 HTTP 协议相互通信。浏览器从服务器请求静态或动态内容。对静态内容的请求通过从服务器磁盘获取文件并将其返回给客户端来服务。对动态内容的请求通过在服务器上的子进程上下文中运行程序并将其输出返回给客户端来服务。CGI 标准提供了一组规则，规定了客户端如何将程序参数传递给服务器、服务器如何将这些参数和其他信息传递给子进程，以及子进程如何将其输出发送回客户端。一个能提供静态和动态内容的简单但功能完整的 Web 服务器可以用几百行 C 代码实现。

**练习题 11.4 解答（第 978 页）**

以下是一个解决方案。注意使用 `inet_ntop` 有多困难，它需要繁琐的类型转换和深层结构引用。而 `getnameinfo` 函数则简单得多，因为它为我们完成了所有这些工作。

```c
#include "csapp.h"

int main(int argc, char **argv)
{
    struct addrinfo *p, *listp, hints;
    struct sockaddr_in *sockp;
    char buf[MAXLINE];
    int rc;

    if (argc != 2) {
        fprintf(stderr, "usage: %s <domain name>\n", argv[0]);
        exit(0);
    }

    /* Get a list of addrinfo records */
    memset(&hints, 0, sizeof(struct addrinfo));
    hints.ai_family = AF_INET;       /* IPv4 only */
    hints.ai_socktype = SOCK_STREAM; /* Connections only */
    if ((rc = getaddrinfo(argv[1], NULL, &hints, &listp)) != 0) {
        fprintf(stderr, "getaddrinfo error: %s\n", gai_strerror(rc));
        exit(1);
    }

    /* Walk the list and display each associated IP address */
    for (p = listp; p; p = p->ai_next) {
        sockp = (struct sockaddr_in *)p->ai_addr;
        Inet_ntop(AF_INET, &(sockp->sin_addr), buf, MAXLINE);
        printf("%s\n", buf);
    }

    /* Clean up */
    Freeaddrinfo(listp);
    exit(0);
}
```
