编写程序的首要目标必须是使其在所有可能的条件下都能正确工作。运行快速但给出错误结果的程序没有任何实用价值。程序员必须编写清晰简洁的代码，不仅要让自己能够理解，还要让其他人在代码审查和后续修改时能够阅读和理解代码。

另一方面，在许多情况下，让程序快速运行也是一个重要考虑因素。如果程序必须实时处理视频帧或网络数据包，那么运行缓慢的程序将无法提供所需的功能。当计算任务要求极高，需要数天或数周才能执行时，让它运行快 20% 就可以产生重大影响。在本章中，我们将探索如何通过几种不同类型的程序优化来使程序运行得更快。

编写高效程序需要几种类型的活动。首先，我们必须选择一组合适的算法和数据结构。其次，我们必须编写编译器能够有效优化的源代码，以生成高效的可执行代码。对于第二部分，理解优化编译器的能力和局限性很重要。程序编写方式的看似微小的变化可能会对编译器优化程度产生很大差异。某些编程语言比其他语言更容易优化。C 的某些特性，例如执行指针算术和类型转换的能力，使得编译器难以对其进行优化。程序员通常可以通过使编译器更容易生成高效代码的方式来编写程序。处理特别苛刻的计算的第三种技术是将任务划分为可以在多个核心和多个处理器的某种组合上并行计算的部分。我们将把性能增强的这一方面推迟到第 12 章。即使在利用并行性时，每个并行线程以最高性能执行也很重要，因此本章的材料在任何情况下都保持相关性。

在进行程序开发和优化时，我们必须考虑代码将如何使用以及哪些关键因素影响它。一般来说,程序员必须在程序的实现和维护难易程度与运行速度之间做出权衡。在算法层面，一个简单的插入排序可以在几分钟内编程完成，而一个高效的排序例程可能需要一天或更长时间来实现和优化。在编码层面，许多低级优化往往会降低代码的可读性和模块化，使程序更容易出现错误，更难修改或扩展。对于将在性能关键环境中重复执行的代码，广泛的优化可能是合适的。一个挑战是在进行广泛转换的同时保持代码的某种程度的优雅性和可读性。

我们描述了许多提高代码性能的技术。理想情况下，编译器应该能够接受我们编写的任何代码，并生成具有指定行为的最高效的机器级程序。现代编译器采用复杂的分析和优化形式，并且它们不断改进。然而，即使是最好的编译器也可能被优化阻碍因素所挫败——程序行为的某些方面强烈依赖于执行

## 5.1 优化编译器的能力和局限性

现代编译器采用复杂的算法来确定程序中计算了哪些值以及如何使用它们。然后，它们可以利用机会来简化表达式、在多个不同的地方使用单个计算，以及减少必须执行给定计算的次数。大多数编译器，包括 GCC，为用户提供对应用哪些优化的一些控制。如第 3 章所述，最简单的控制是指定优化级别。例如，使用命令行选项 -0g 调用 GCC 指定它应该应用一组基本的优化。

使用选项 -01 或更高（例如 -02 或 -03）调用 GCC 将导致它应用更广泛的优化。这些可以进一步提高程序性能，但它们可能会扩大程序大小，并且可能使使用标准调试工具调试程序变得更加困难。在我们的演示中，我们主要考虑使用优化级别 -01 编译的代码，尽管级别 -02 已成为使用 GCC 的大多数软件项目的公认标准。我们故意限制优化级别，以演示用 C 编写函数的不同方式如何影响编译器生成的代码的效率。我们将发现，我们可以编写 C 代码，当只使用选项 -01 编译时，其性能远远超过使用最高可能优化级别编译的更幼稚的版本。

编译器必须小心地只对程序应用安全的优化，这意味着对于程序可能遇到的所有可能情况，生成的程序将具有与未优化版本完全相同的行为，直到 C 语言标准提供的保证的限制。约束

编译器仅执行安全的优化消除了不良运行时行为的可能来源，但这也意味着程序员必须更加努力地以编译器可以转换为高效机器级代码的方式编写程序。为了理解决定哪些程序转换是安全的挑战，请考虑以下两个过程：

```c
1 void twiddle1(long *xp, long *yp)
2 {
3     *xp += *yp;
4     *xp += *yp;
5 }
6
7 void twiddle2(long *xp, long *yp)
8 {
9     *xp += 2* *yp;
10 }
```

乍一看，这两个过程似乎具有相同的行为。它们都将指针 yp 指定的位置存储的值的两倍加到 xp 指定的位置。另一方面，函数 twiddle2 更高效。它只需要三次内存引用（读 *xp、读 *yp、写 *xp），而 twiddle1 需要六次（两次读 *xp、两次读 *yp 和两次写 *xp）。因此，如果给编译器提供过程 twiddle1 来编译，人们可能会认为它可以基于 twiddle2 执行的计算生成更高效的代码。

然而，考虑 xp 和 yp 相等的情况。那么函数 twiddle1 将执行以下计算：

```c
3 *xp += *xp; /* Double value at xp */
4 *xp += *xp; /* Double value at xp */
```

结果将是 xp 处的值将增加 4 倍。另一方面，函数 twiddle2 将执行以下计算：

```c
*xp += 2* *xp; /* Triple value at xp */
```

结果将是 xp 处的值将增加 3 倍。编译器对 twiddle1 将如何调用一无所知，因此它必须假设参数 xp 和 yp 可能相等。因此，它不能生成 twiddle2 风格的代码作为 twiddle1 的优化版本。

两个指针可能指定相同内存位置的情况称为内存别名 (memory aliasing)。在仅执行安全优化时，编译器必须假设不同的指针可能是别名的。作为另一个例子，对于具有指针变量 p 和 q 的程序，考虑以下代码序列：

```c
x = 1000; y = 3000;
*q = y; /* 3000 */
*p = x; /* 1000 */
t1 = *q; /* 1000 or 3000 */
```

## 5.2 表达程序性能

我们引入了每元素周期数 (cycles per element) 的度量，缩写为 CPE，以一种可以指导我们改进代码的方式表达程序性能。CPE 测量帮助我们在详细层面理解迭代程序的循环性能。它适用于执行重复计算的程序，例如处理图像中的像素或计算矩阵乘积中的元素。

处理器的活动排序由提供某个频率的规则信号的时钟控制，通常以千兆赫兹 (GHz)，即每秒数十亿个周期表示。例如，当产品文献将系统描述为"4 GHz"处理器时，这意味着处理器时钟以 $4.0 \times 10^{9}$ 周期/秒的速度运行。每个时钟周期所需的时间由时钟频率的倒数给出。这些通常以纳秒（1 纳秒是 $10^{-9}$ 秒）或皮秒（1 皮秒是 $10^{-12}$ 秒）表示。例如，4 GHz 时钟的周期可以表示为 0.25 纳秒或 250 皮秒。从程序员的角度来看，用时钟周期而不是纳秒或皮秒来表示测量更具指导意义。这样，测量表示正在执行多少条指令，而不是时钟运行的速度。

许多过程包含一个迭代一组元素的循环。例如，图 5.1 中的函数 psum1 和 psum2 都计算长度为 n 的向量的前缀和。对于向量 $\vec{a} = \langle a_0, a_1, \ldots, a_{n-1} \rangle$，前缀和 $\vec{p} = \langle p_0, p_1, \ldots, p_{n-1} \rangle$ 定义为

$$\begin{aligned}&p_{0}=a_{0}\\&p_{i}=p_{i-1}+a_{i},\quad1\leq i<n\\ \end{aligned}$$

函数 psum1 每次迭代计算结果向量的一个元素。函数 psum2 使用一种称为循环展开的技术每次迭代计算两个元素。我们将在本章后面探讨循环展开的好处。（有关分析和优化前缀和计算的更多信息，请参见问题 5.11、5.12 和 5.19。）

此类过程所需的时间可以表征为常数加上与处理的元素数量成比例的因子。例如，图 5.2 显示了这两个函数对于 n 的一系列值所需的时钟周期数的图。使用最小二乘拟合，我们发现 psum1 和 psum2 的运行时间（以时钟周期为单位）可以分别由方程 $368 + 9.0n$ 和 $368 + 6.0n$ 近似。这些方程表明由于计时代码和启动过程、设置循环和完成所需的 368 个周期的开销

/* Compute prefix sum of vector a */
void psum1(float a[], float p[], long n)
{
    long i;
    p[0] = a[0];
    for (i = 1; i < n; i++)
        p[i] = p[i-1] + a[i];

{
    long i;
    p[0] = a[0];

        p[i] = mid_val;
        p[i+1] = mid_val + a[i+1];

    /* For even n, finish remaining element */
    if (i < n)

}

>**旁注 什么是最小二乘拟合？**
>
>对于一组数据点 $(x_{1}, y_{1}), \ldots (x_{n}, y_{n})$，我们经常尝试绘制一条最能近似这些数据所代表的 X-Y 趋势的直线。通过最小二乘拟合，我们寻找形式为 $y = mx + b$ 的直线，该直线最小化以下误差度量：
>
>$$E(m,b)=\sum_{i=1,n}(mx_{i}+b-y_{i})^{2}$$
>
>可以通过找到 $E(m, b)$ 关于 m 和 b 的导数并将其设置为 0 来推导计算 m 和 b 的算法。

## 5.7 理解现代处理器

到目前为止，我们应用的优化不依赖于目标机器的任何特性。它们只是减少了过程调用的开销并消除了一些导致优化编译器困难的关键"优化阻碍因素"。当我们寻求进一步提高性能时，我们必须考虑利用处理器微架构的优化——也就是处理器执行指令的底层系统设计。获得最后一点性能需要对程序进行详细分析以及针对目标处理器调整的代码生成。尽管如此，我们可以应用一些基本优化，这些优化将在大类处理器上产生整体性能改进。我们在这里报告的详细性能结果可能不适用于其他机器，但操作和优化的一般原理适用于各种各样的机器。

为了理解提高性能的方法，我们需要对现代处理器的微架构有基本的了解。由于可以集成到单个芯片上的大量晶体管，现代微处理器采用复杂的硬件来尝试最大化程序性能。其结果是，它们的实际操作与通过查看机器级程序所感知的视图大不相同。在代码层面，似乎指令是一次执行一条的，其中每条指令涉及从寄存器或内存中获取值、执行操作以及将结果存储回寄存器或内存位置。在实际处理器中，许多指令

---

<!-- Page 0546 -->

被同时评估，这种现象称为指令级并行性 (instruction-level parallelism)。在某些设计中，可能有 100 条或更多指令"正在执行中"。采用复杂的机制来确保这种并行执行的行为准确捕获机器级程序所需的顺序语义模型。这是现代微处理器的显著成就之一：它们采用复杂而奇特的微架构，其中多条指令可以并行执行，同时呈现简单的顺序指令执行的操作视图。

尽管现代微处理器的详细设计远远超出了本书的范围，但对其操作原理有一个大致的了解就足以理解它们如何实现指令级并行性。我们将发现两个不同的下界表征了程序的最大性能。当一系列操作必须按严格顺序执行时，会遇到延迟界限 (latency bound)，因为在下一个操作开始之前需要一个操作的结果。当代码中的数据依赖性限制了处理器利用指令级并行性的能力时，此界限可能限制程序性能。吞吐量界限 (throughput bound) 表征了处理器功能单元的原始计算能力。此界限成为程序性能的最终限制。

### 5.7.1 整体操作

图 5.11 显示了现代微处理器的非常简化的视图。我们的假设处理器设计松散地基于最近英特尔处理器的结构。这些处理器在行业中被描述为超标量 (superscalar)，这意味着它们可以在每个时钟周期执行多个操作，并且是乱序执行 (out of order)，这意味着指令执行的顺序不需要对应于它们在机器级程序中的顺序。整体设计有两个主要部分：指令控制单元 (ICU, instruction control unit)，负责从内存中读取指令序列并从这些指令中生成一组要对程序数据执行的原始操作，以及执行单元 (EU, execution unit)，然后执行这些操作。与我们在第 4 章中研究的简单顺序流水线相比，乱序处理器需要更多更复杂的硬件，但它们更擅长实现更高程度的指令级并行性。

控制执行单元之间操作数通信的最常见机制称为寄存器重命名 (register renaming)。当更新寄存器 r 的指令被解码时，会生成一个标签 t，为操作的结果提供唯一标识符。将条目 $(r, t)$ 添加到维护程序寄存器 r 与操作标签 t 之间关联的表中，该操作将更新此寄存器。当使用寄存器 r 作为操作数的后续指令被解码时，发送到执行单元的操作将包含 t 作为操作数值的源。当某个执行单元完成第一个操作时，它生成一个结果 $(v, t)$，表示标签为 t 的操作产生了值 v。等待 t 作为源的任何操作然后将使用 v 作为源值，这是一种数据转发形式。通过这种机制，值可以直接从一个操作转发到另一个操作，而不是写入和从寄存器文件读取，使第二个操作能够在第一个操作完成后立即开始。重命名表仅包含具有待处理写操作的寄存器的条目。当解码的指令需要寄存器 r 并且没有与该寄存器关联的标签时，操作数直接从寄存器文件中检索。通过寄存器重命名，可以推测性地执行整个操作序列，即使寄存器仅在处理器确定分支结果之后才更新。

### 5.7.2 功能单元性能

图 5.12 记录了我们英特尔 Core i7 Haswell 参考机器的一些算术操作的性能，这些性能是通过测量和参考英特尔文献 [49] 确定的。这些时序对于其他处理器也是典型的。每个操作的特征在于其延迟 (latency)，即执行操作所需的总时间，发射时间 (issue time)，即相同类型的两个独立操作之间的最小时钟周期数，以及容量 (capacity)，表示能够执行该操作的功能单元数量。

我们看到从整数到浮点操作，延迟增加。我们还看到加法和乘法操作的发射时间都为 1，这意味着处理器可以在每个时钟周期启动这些操作中的一个新操作。这种短发射时间是通过使用流水线 (pipelining) 来实现的。流水线功能单元实现为一系列阶段，每个阶段执行操作的一部分。例如，典型的浮点加法器包含三个阶段（因此有三个周期的延迟）：一个处理指数值，一个加分数，一个对结果进行舍入。算术操作可以依次通过各个阶段，而不是等待一个操作完成后才开始下一个操作。只有存在要执行的连续、逻辑独立的操作时，才能利用此功能。发射时间为 1 个周期的功能单元称为完全流水线化 (fully pipelined)：它们可以在每个时钟周期启动一个新操作。容量大于 1 的操作是由于多个功能单元的能力，如前面对参考机器的描述。

我们还看到除法器（用于整数和浮点除法以及浮点平方根）不是流水线化的——其发射时间等于其延迟。这意味着除法器必须执行完整的除法才能开始新的除法。我们还看到除法的延迟和发射时间以范围形式给出，因为某些被除数和除数的组合比其他组合需要更多步骤。除法的长延迟和发射时间使其成为相对昂贵的操作。

表达发射时间的更常见方式是指定单元的最大吞吐量 (maximum throughput)，定义为发射时间的倒数。完全流水线化的功能单元的最大吞吐量为每时钟周期 1 个操作，而发射时间较高的单元具有较低的最大吞吐量。拥有多个功能单元可以进一步提高吞吐量。对于容量为 C 且发射时间为 I 的操作，处理器可能实现每时钟周期 C/I 个操作的吞吐量。例如，我们的参考机器能够以每时钟周期 2 个的速率执行浮点乘法操作。我们将看到如何利用此功能来提高程序性能。

电路设计人员可以创建具有广泛性能特性的功能单元。创建具有短延迟或流水线化的单元需要更多硬件，特别是对于更复杂的功能（如乘法和浮点操作）。由于微处理器芯片上这些单元的空间有限，CPU 设计人员必须仔细平衡功能单元的数量及其各自的性能以实现最佳整体性能。他们评估许多不同的基准程序，并将最多资源用于最关键的操作。如图 5.12 所示，在 Core i7 Haswell 处理器的设计中，整数乘法和浮点乘法和加法被认为是重要的操作，尽管需要大量硬件才能实现所示的低延迟和高流水线化程度。另一方面，除法相对不频繁，难以用短延迟或完全流水线化来实现。

## 其他性能因素

另一方面，对于整数加法的情况，我们对 combine4 的测量显示 CPE 为 1.27，慢于我们基于图 5.15 图的左侧或右侧形成的依赖链预测的 CPE 1.00。这说明了数据流表示中的关键路径仅提供程序需要多少周期的下界的原则。其他因素也可能限制性能，包括可用功能单元的总数以及在任何给定步骤中可以在功能单元之间传递的数据值的数量。对于整数加法作为组合操作的情况，数据操作足够快，以至于其余操作无法足够快地提供数据。确定程序每个元素需要 1.27 个周期的确切原因需要比公开可用的硬件设计更详细的知识。

总结我们对 combine4 的性能分析：我们的程序操作的抽象数据流表示表明 combine4 具有长度为 $L \cdot n$ 的关键路径，由程序值 acc 的连续更新引起，此路径将 CPE 限制为至少 L。这确实是我们为除整数加法之外的所有情况测量的 CPE，整数加法的测量 CPE 为 1.27，而不是我们从关键路径长度预期的 CPE 1.00。

似乎延迟界限对我们的组合操作可以执行的速度形成了基本限制。我们的下一个任务将是重构操作以增强指令级并行性。我们希望以这样的方式转换程序，使我们唯一的限制成为吞吐量界限，产生低于或接近 1.00 的 CPE。

## 5.8 循环展开

循环展开 (loop unrolling) 是一种程序转换，通过增加每次迭代计算的元素数量来减少循环的迭代次数。我们在函数 psum2（图 5.1）中看到了这方面的例子，其中每次迭代计算前缀和的两个元素，从而将所需的迭代总数减半。循环展开可以通过两种方式提高性能。首先，它减少了不直接对程序结果做出贡献的操作数量，例如循环索引和条件分支。其次，它揭示了我们可以进一步转换代码以减少整体计算关键路径中操作数量的方法。在本节中，我们将检查简单的循环展开，不进行任何进一步的转换。

图 5.16 显示了我们的组合代码的一个版本，使用我们将称之为"2 × 1 循环展开"的方法。第一个循环每次跨越数组两个元素。也就是说，循环索引 i 在每次迭代中递增 2，并且组合操作应用于单次迭代中的数组元素 i 和 $i + 1$。

一般来说，向量长度不会是 2 的倍数。我们希望我们的代码对任意向量长度都能正确工作。我们通过两种方式考虑此要求。首先，我们确保第一个循环不会超出数组边界。对于长度为 n 的向量，我们将循环限制设置为 n - 1。然后我们确保循环仅在循环索引 i 满足 i < n - 1 时执行，因此最大数组索引 i + 1 将满足 $i + 1 < (n - 1) + 1 = n$。

我们可以将这个想法推广到按任何因子 k 展开循环，产生 $k \times 1$ 循环展开。为此，我们将上限设置为 $n - k + 1$，并在循环内对元素 i 到 $i + k - 1$ 应用组合操作。循环索引 i 在每次迭代中递增 k。最大数组索引 $i + k - 1$ 然后将小于 n。我们包括第二个循环以逐一遍历向量的最后几个元素。此循环的主体将被执行 0 到 k - 1 次。对于 k = 2，我们可以使用简单的条件语句

---

```c
/* 2 x 1 loop unrolling */
void combine5(vec_ptr v, data_t *dest)
{
    long i;
    long length = vec_length(v);
    long limit = length-1;
    data_t *data = get_vec_start(v);
    data_t acc = IDENT;

    /* Combine 2 elements at a time */
    for (i = 0; i < limit; i+=2) {
        acc = (acc_OP_data[i]) OP_data[i+1];

    /* Finish any remaining elements */
    for (; i < length; i++) {
        acc = acc_OP_data[i];
    }
    *dest = acc;
}
```

### 5.9 增强并行性

此时，我们的函数受到算术单元延迟施加的界限的限制。然而，正如我们所指出的，执行加法和乘法的功能单元都是完全流水线化的，这意味着它们可以在每个时钟周期启动新操作，并且某些操作可以由多个功能单元执行。硬件有能力以更高的速率执行乘法和加法，但我们的代码无法利用此功能，即使使用循环展开，因为我们将值累积为单个变量 acc。我们无法计算 acc 的新值，直到前一个计算完成。即使计算 acc 新值的功能单元可以在每个时钟周期启动新操作，它也只会每 L 个周期启动一个，其中 L 是组合操作的延迟。我们现在将研究打破这种顺序依赖性并获得优于延迟界限的性能的方法。

### 5.9.1 多个累加器

对于可结合和可交换的组合操作，例如整数加法或乘法，我们可以通过将组合操作集分成两个或更多部分并在最后组合结果来提高性能。例如，设 $P_n$ 表示元素 $a_0, a_1, \ldots, a_{n-1}$ 的乘积：

$$P_{n}=\prod_{i=0}^{n-1}a_{i}$$

假设 $n$ 是偶数，我们也可以将其写为 $P_n = PE_n \times PO_n$，其中 $PE_n$ 是偶数索引元素的乘积，$PO_n$ 是奇数索引元素的乘积：

$$PE_{n}=\prod_{i=0}^{n/2-1}a_{2i}$$

$$P O_{n}=\prod_{i=0}^{n/2-1}a_{2i+1}$$

图 5.21 显示了使用此方法的代码。它同时使用双向循环展开来每次迭代组合更多元素，以及双向并行性，在变量 acc0 中累积偶数索引的元素，在变量 acc1 中累积奇数索引的元素。因此，我们将此称为"2 × 2 循环展开"。与之前一样，我们包括第二个循环来累积向量长度不是 2 的倍数的情况下的任何剩余数组元素。然后我们对 acc0 和 acc1 应用组合操作以计算最终结果。

将单独的循环展开与双向并行性循环展开进行比较，我们获得以下性能：

---

```c
/* 2 x 2 loop unrolling */
void combine6(vec_ptr v, data_t *dest)
{
    long i;
    long length = vec_length(v);
    long limit = length-1;
    data_t *data = get_vec_start(v);
    data_t acc0 = IDENT;
    data_t acc1 = IDENT;

    /* Combine 2 elements at a time */
    for (i = 0; i < limit; i+=2) {
        acc0 = acc0_OP_data[i];
        acc1 = acc1_OP_data[i+1];
    }

    /* Finish any remaining elements */
    for (; i < length; i++) {
        acc0 = acc0_OP_data[i];
    }

    *dest = acc0_OP_acc1;
}
```

### 5.9.2 重结合转换

我们现在探索另一种打破顺序依赖性从而将性能提高到延迟界限之外的方法。我们看到 combine5 的 $k \times 1$ 循环展开没有改变组合向量元素以形成其和或积时执行的操作集。然而，通过对代码的非常小的更改，我们可以从根本上改变组合的执行方式，也大大提高程序性能。

图 5.26 显示了一个函数 combine7，它与 combine5 的展开代码（图 5.16）的不同之处仅在于内部循环中元素的组合方式。在 combine5 中，组合由语句执行

$$\begin{array}{r l r}{12}&{{}}&{\mathrm{a c c~=~(a c c~O P~d a t a[i])~O P~d a t a[i+1]~;}}\end{array}$$

$$\mathrm{~a~c~c~}=\mathrm{~a~c~c~}\mathrm{~O~P~}\mathrm{~(d a t a~[~i~]~}\mathrm{~O~P~}\mathrm{~d~a~t a~[~i+1~]~}\mathrm{~};$$

>
>如第 3.1 节所述，英特尔在 1999 年引入了 SSE 指令，其中 SSE 是"流式 SIMD 扩展"的首字母缩写，而 SIMD（发音为"sim-dee"）又是"单指令多数据"的首字母缩写。SSE 功能经历了多代，最新版本被命名为高级向量扩展 (AVX, advanced vector extensions)。SIMD 执行模型涉及在单个指令内对整个数据向量进行操作。这些向量保存在一组特殊的向量寄存器中，命名为 %ymm0-%ymm15。当前 AVX 向量寄存器长 32 字节，因此每个可以容纳八个 32 位数字或四个 64 位数字，其中数字可以是整数或浮点值。然后 AVX 指令可以对这些寄存器执行向量操作，例如并行添加或乘以八组或四组值。例如，如果 YMM 寄存器 %ymm0 包含八个单精度浮点数，我们表示为 $a_{0}, \ldots, a_{7}$，%rcx 包含八个单精度浮点数序列的内存地址，我们表示为 $b_{0}, \ldots, b_{7}$，则指令
>
>```asm
>vmulps (%rcs), %ymm0, %ymm1
>```
>
>将从内存中读取八个值并并行执行八次乘法，计算 $a_i \leftarrow a_i \cdot b_i$，对于 $0 \leq i \leq 7$，并将得到的八个乘积存储在向量寄存器 %ymm1 中。我们看到单个指令能够对多个数据值生成计算，因此称为"SIMD"。

## 5.11 一些限制因素

我们已经看到，程序的数据流图表示中的关键路径指示了执行程序所需时间的基本下界。也就是说，如果程序中存在某条数据依赖链，其中沿该链的所有延迟之和等于 T，那么程序将需要至少 T 个周期才能执行。

我们还看到，功能单元的吞吐量界限也对程序的执行时间施加了下界。也就是说，假设程序需要对某个操作进行总共 N 次计算，微处理器有 C 个能够执行该操作的功能单元，并且这些单元的发射时间为 I。那么程序将需要至少 $N \cdot I/C$ 个周期才能执行。

在本节中，我们将考虑限制实际机器上程序性能的一些其他因素。

### 5.11.2 分支预测和错误预测惩罚

我们通过第 3.6.6 节中的实验证明，当分支预测逻辑没有正确预测分支是否会被采纳时，条件分支可能会导致显著的错误预测惩罚。现在我们已经了解了处理器的操作方式，我们可以理解这种惩罚产生的原因。

现代处理器在当前执行的指令之前工作得很好，从内存中读取新指令并解码它们以确定对哪些操作数执行哪些操作。只要指令遵循简单的序列，这种指令流水线就能很好地工作。当遇到分支时，处理器必须猜测分支将走哪条路。对于条件跳转的情况，这意味着预测分支是否会被采纳。对于诸如间接跳转（如我们在跳转到跳转表条目指定的地址的代码中看到的）或过程返回等指令，这意味着预测目标地址。在此讨论中，我们关注条件分支。

在采用推测执行的处理器中，处理器开始执行预测分支目标处的指令。它以一种避免修改任何实际寄存器或内存位置的方式执行此操作，直到确定实际结果。如果预测正确，处理器然后可以

---

<!-- Page 0578 -->

"提交"推测执行指令的结果，将它们存储在寄存器或内存中。如果预测不正确，处理器必须丢弃所有推测执行的结果，并在正确位置重新启动指令获取过程。错误预测惩罚是在执行此操作时产生的，因为必须重新填充指令流水线才能生成有用的结果。

我们在第 3.6.6 节中看到，x86 处理器的最新版本，包括所有能够执行 x86-64 程序的处理器，都有条件移动指令。在编译条件语句和表达式时，GCC 可以生成使用这些指令的代码，而不是基于条件控制转移的更传统实现。条件移动的基本思想是计算条件表达式或语句的两个分支的值，然后使用条件移动来选择所需的值。我们在第 4.5.7 节中看到，条件移动指令可以作为普通指令的流水线处理的一部分来实现。不需要猜测条件是否成立，因此猜测错误没有惩罚。

那么，C 程序员如何确保分支错误预测惩罚不会妨碍程序的效率？鉴于我们为参考机器测量的 19 个周期的错误预测惩罚，风险非常高。这个问题没有简单的答案，但以下一般原则适用。

## 编写适合使用条件移动实现的代码

分支预测仅对规律模式可靠。程序中的许多测试完全不可预测，取决于数据的任意特征，例如数字是负数还是正数。对于这些本质上不可预测的情况，如果编译器能够使用条件数据传输而不是条件控制传输生成代码，程序性能可以大大增强。这不能由 C 程序员直接控制，但表达条件行为的某些方式可以比其他方式更直接地转换为条件移动。

我们发现 GCC 能够为以更"函数式"风格编写的代码生成条件移动，其中我们使用条件操作来计算

值，然后用这些值更新程序状态，而不是使用更"命令式"风格，其中我们使用条件来选择性地更新程序状态。

这两种风格没有严格的规则，因此我们用一个例子来说明。假设我们有两个整数数组 a 和 b，并且在每个位置 i，我们希望将 a[i] 设置为 a[i] 和 b[i] 的最小值，将 b[i] 设置为最大值。

实现此函数的命令式风格是在每个位置 i 检查并在它们乱序时交换两个元素：

```c
/* Rearrange two vectors so that for each i, b[i] >= a[i] */
void minmax1(long a[], long b[], long n) {
    long i;
    for (i = 0; i < n; i++) {
        if (a[i] > b[i]) {
            long t = a[i];
            a[i] = b[i];
            b[i] = t;
        }
    }
}
```

我们对此函数的测量显示，对于随机数据，CPE 约为 13.5，对于可预测数据，CPE 为 2.5-3.5，这表明错误预测惩罚约为 20 个周期。

实现此函数的函数式风格是在每个位置 i 计算最小值和最大值，然后分别将这些值分配给 a[i] 和 b[i]：

```c
/* Rearrange two vectors so that for each i, b[i] >= a[i] */
void minmax2(long a[], long b[], long n) {
    long i;
    for (i = 0; i < n; i++) {
        long min = a[i] < b[i]? a[i] : b[i];
        long max = a[i] < b[i]? b[i] : a[i];
        a[i] = min;
        b[i] = max;
    }
}
```

我们对此函数的测量显示，无论数据是任意的还是可预测的，CPE 都约为 4.0。（我们还检查了生成的汇编代码以确保它确实使用条件移动。）

如第 3.6.6 节所述，并非所有条件行为都可以用条件数据传输实现，因此不可避免地存在程序员无法避免编写代码的情况，这些代码将导致条件分支，处理器对其分支预测表现不佳。但是，正如我们所展示的，程序员的一点巧思有时可以使代码更适合转换为条件数据传输。这需要一定量

## 5.12 理解内存性能

到目前为止我们编写的所有代码，以及我们运行的所有测试，都访问相对少量的内存。例如，组合例程是在长度小于 1,000 个元素的向量上测量的，需要不超过 8,000 字节的数据。所有现代处理器都包含一个或多个高速缓存内存，以提供对如此少量内存的快速访问。在本节中，我们将进一步研究涉及加载（从内存读取到寄存器）和存储（从寄存器写入内存）操作的程序的性能，仅考虑所有数据都保存在高速缓存中的情况。在第 6 章中，我们将更详细地介绍高速缓存的工作方式、它们的性能特性以及如何编写最佳利用高速缓存的代码。

---

<!-- Page 0582 -->

如图 3.11 所示，现代处理器有专用的功能单元来执行加载和存储操作，这些单元有内部缓冲区来保存未完成的内存操作请求集。例如，我们的参考机器有两个加载单元，每个单元可以保存多达 72 个待处理的读取请求。它有一个单一的存储单元，带有一个包含多达 42 个写入请求的存储缓冲区。这些单元中的每一个都可以在每个时钟周期启动 1 个操作。

### 5.12.1 加载性能

包含加载操作的程序的性能取决于加载单元的流水线能力和延迟。在我们使用参考机器进行组合操作的实验中，我们看到，对于数据类型和组合操作的任何组合，CPE 从未低于 0.50，除非使用 SIMD 操作。限制我们示例 CPE 的一个因素是它们都需要为计算的每个元素从内存中读取一个值。使用两个加载单元，每个单元最多每个时钟周期启动 1 个加载操作，CPE 不能小于 0.50。对于我们必须为计算的每个元素加载 k 个值的应用程序，我们永远无法实现低于 k/2 的 CPE（例如，参见问题 5.15）。

到目前为止，在我们的示例中，我们还没有看到由于加载操作的延迟而产生的任何性能影响。我们的加载操作的地址仅取决于循环索引 i，因此加载操作不构成性能限制关键路径的一部分。

要确定机器上加载操作的延迟，我们可以设置一个具有一系列加载操作的计算，其中一个的结果确定下一个的地址。例如，考虑图 5.31 中的函数 list_len，它计算链表的长度。在此函数的循环中，变量 ls 的每个连续值都取决于指针引用 ls->next 读取的值。我们的测量显示函数 list_len 有

### 5.12.2 存储性能

到目前为止，在我们所有的示例中，我们只分析了主要使用加载操作引用内存的函数，从内存位置读取到寄存器中。它的对应物，存储操作，将寄存器值写入内存。此操作的性能，特别是与加载操作的交互，涉及几个微妙的问题。

与加载操作一样，在大多数情况下，存储操作可以以完全流水线化的模式运行，每个周期开始一个新的存储。例如，考虑图 5.32 所示的函数，它将长度为 n 的数组 dest 的元素设置为零。我们的测量显示 CPE 为 1.0。这是我们在具有单个存储功能单元的机器上可以实现的最佳结果。

要了解处理器如何区分这两种情况以及为什么一个比另一个运行得慢，我们必须更详细地查看加载和存储执行单元，如图 5.34 所示。存储单元包括一个存储缓冲区，其中包含已发送到存储单元但尚未完成的存储操作的地址和数据，其中完成涉及更新数据高速缓存。提供此缓冲区以便可以执行一系列存储操作，而无需等待每个操作更新高速缓存。当发生加载操作时，它必须检查存储缓冲区中的条目以查找匹配的地址。如果找到匹配（意味着正在写入的任何字节与正在读取的任何字节具有相同的地址），它将检索相应的数据条目作为加载操作的结果。

src 在 %rdi，dst 在 %rsi，val 在 %rax
```asm

    movq     %rax, (%rsi)    Write val to dst
    movq     (%rdi), %rax    t = *src
    addq     $1, %rax    val = t+1
    subq     $1, %rdx    cnt--
    jne    .L3     If!= 0, goto loop
```

## 5.13 现实世界：性能改进技术

尽管我们只考虑了有限的一组应用程序，但我们可以从中汲取关于如何编写高效代码的重要经验。我们描述了优化程序性能的一些基本策略：

**高级设计**。为手头的问题选择适当的算法和数据结构。特别要警惕避免产生渐近性能差的算法或编码技术。

**基本编码原则**。避免优化阻碍因素，以便编译器可以生成高效的代码。

■ 消除过多的函数调用。尽可能将计算移出循环。考虑选择性地牺牲程序模块化以获得更高的效率。

---

<!-- Page 0590 -->

■ 消除不必要的内存引用。引入临时变量来保存中间结果。仅在计算出最终值时才将结果存储在数组或全局变量中。

**低级优化**。构建代码以利用硬件能力。

■ 展开循环以减少开销并启用进一步的优化。

■ 通过诸如多累加器和重结合等技术找到增加指令级并行性的方法。

■ 以函数式风格重写条件操作，以启用通过条件数据传输进行编译。

对读者的最后建议是，在为提高效率而重写程序时要警惕避免引入错误。在引入新变量、更改循环边界和使代码整体更复杂时很容易出错。一种有用的技术是使用检查代码在优化时测试函数的每个版本，以确保在此过程中不引入错误。检查代码对函数的新版本应用一系列测试，并确保它们产生与原始版本相同的结果。测试用例集必须随着高度优化的代码变得更加广泛，因为有更多的情况需要考虑。例如，使用循环展开的检查代码需要测试许多不同的循环边界，以确保它处理结尾所需的所有不同可能数量的单步迭代。

## 5.14 识别和消除性能瓶颈

到目前为止，我们只考虑了优化小程序，其中程序中有一些明确的地方限制其性能，因此应该是我们优化工作的重点。在处理大型程序时，即使知道将优化工作集中在哪里也可能很困难。在本节中，我们描述如何使用代码分析器 (code profiler)，即在程序执行时收集程序性能数据的分析工具。我们还讨论代码优化的一些一般原则，包括第 1.9.1 节中介绍的阿姆达尔定律的含义。

### 5.14.1 程序分析

程序分析涉及运行程序的一个版本，其中已合并仪器代码以确定程序的不同部分需要多少时间。它对于识别我们应该在优化工作中关注的程序部分非常有用。分析的一个优势是它可以在实际程序在真实基准数据上运行时执行。

Unix 系统提供分析程序 GPROF。此程序生成两种形式的信息。首先，它确定程序中每个函数花费了多少 CPU 时间。其次，它计算每个函数被调用的次数，按执行调用的函数分类。这两种形式的信息都可能非常有用。时序提供了

不同函数在确定整体运行时间中的相对重要性的感觉。调用信息允许我们理解程序的动态行为。

使用 GPROF 进行分析需要三个步骤，如 C 程序 prog.c 所示，它使用命令行参数 file.txt 运行：

1. 程序必须编译和链接以进行分析。使用 GCC（和其他 C 编译器），这只需在命令行上包含运行时标志 -pg。重要的是确保编译器不尝试通过内联替换执行任何优化，否则对函数的调用可能无法准确制表。我们使用优化标志 -0g，保证函数调用将被正确跟踪。

GPROF 的一些属性值得注意：

- 时序不是很精确。它基于一个简单的间隔计数方案，其中编译后的程序为每个函数维护一个计数器，记录执行该函数所花费的时间。操作系统使程序以某个规则的时间间隔 $\delta$ 中断。$\delta$ 的典型值在 1.0 到 10.0 毫秒之间。然后它确定程序在中断发生时正在执行的函数，并将该函数的计数器递增 $\delta$。当然，可能会发生这样的情况：此函数刚刚开始执行并且很快就会完成，但由于自上次中断以来，它被分配了完整的执行成本。某些其他函数可能在两次中断之间运行，因此根本不收取任何时间。

在很长一段时间内，该方案效果相当不错。从统计上讲，每个函数都应该根据执行它所花费的相对时间收费。然而，对于运行时间不到约 1 秒的程序，这些数字应该被视为仅粗略估计。

- 调用信息相当可靠，假设没有执行内联替换。编译后的程序为每个调用者和被调用者的组合维护一个计数器。每次调用过程时，相应的计数器就会递增。

• 默认情况下，不显示库函数的时序。相反，这些时间被合并到调用函数的时间中。

随着排序的改进，我们现在发现列表扫描成为瓶颈。认为效率低下是由于函数的递归结构，我们将其替换为迭代函数，显示为"Iter first"。令人惊讶的是，运行时间增加到约 7.5 秒。经过更仔细的研究，我们发现两个列表函数之间存在微妙的差异。递归版本在列表末尾插入新元素，而迭代版本在前面插入它们。为了最大化性能，我们希望最频繁的 n-gram 出现在列表的开头附近。这样，函数将快速定位常见情况。假设 n-gram 在整个文档中均匀分布，我们会期望频繁的 n-gram 的第一次出现在不太频繁的 n-gram 之前。通过在末尾插入新 n-gram，第一个函数倾向于按频率的降序对 n-gram 进行排序，而第二个函数倾向于做相反的事情。因此，我们创建了第三个列表扫描函数，该函数使用迭代但在此列表末尾插入新元素。使用此版本，显示为"Iter last"，时间下降到约 5.3 秒，略好于递归版本。这些测量表明，作为优化工作的一部分，对程序运行实验的重要性。我们最初假设将递归代码转换为迭代代码会提高其性能，并没有考虑添加到列表末尾或开头之间的区别。严格按顺序乘以元素不太可能比独立乘以两组然后将这些乘积相乘在一起提供根本上更好的准确性。对于大多数应用程序，实现 $2 \times$ 的性能提升超过了为奇怪数据模式产生不同结果的风险。尽管如此，程序开发人员应该与潜在用户核实，看看是否存在可能导致修订算法不可接受的特殊条件。大多数编译器不会尝试使用浮点代码进行此类转换，因为它们无法判断引入可能改变程序行为的转换的风险，无论多么小。

接下来，我们考虑哈希表结构。初始版本只有 1,021 个桶（通常，桶的数量被选择为素数以增强哈希函数在桶中均匀分布键的能力）。对于具有 363,039 个条目的表，这将意味着 363,039/1,021 = 355.6 的平均负载。这解释了为什么如此多的时间花费在执行列表操作上——搜索涉及测试大量候选 n-gram。它还解释了为什么性能对列表排序如此敏感。然后我们将桶的数量增加到 199,999，将平均负载减少到 1.8。然而，奇怪的是，我们的总运行时间仅下降到 5.1 秒，差异仅为 0.2 秒。

通过这个练习，我们已经展示了代码分析可以帮助将简单应用程序所需的时间从 3.5 分钟下降到 0.2 秒，产生约 $1,000 \times$ 的性能提升。分析器帮助我们将注意力集中在程序最耗时的部分，并提供有关过程调用结构的有用信息。我们代码中的一些瓶颈，例如使用二次排序例程，很容易预料到，而其他瓶颈，例如是附加到列表的开头还是结尾，只有通过仔细分析才会出现。

我们可以看到，分析是工具箱中拥有的有用工具，但它不应该是唯一的工具。时序测量不完美，特别是对于较短（少于 1 秒）的运行时间。更重要的是，结果仅适用于测试的特定数据。例如，如果我们在由较少数量的较长字符串组成的数据上运行原始函数，我们会发现小写转换例程是主要的性能瓶颈。更糟糕的是，如果它只分析具有短单词的文档，我们可能永远不会检测到隐藏的瓶颈，例如 lower1 的二次性能。一般来说，分析可以帮助我们针对典型情况进行优化，假设我们在代表性数据上运行程序，但我们还应该确保程序对所有可能的情况都具有良好的性能。这主要涉及避免产生较差渐近性能的算法（如插入排序）和不良编程实践（如 lower1）。

第 1.9.1 节中描述的阿姆达尔定律提供了关于通过针对性优化可以获得的性能提升的一些额外见解。对于我们的 n-gram 代码，当我们用快速排序替换插入排序时，我们看到总执行时间从 209.0 秒下降到 5.4 秒。初始版本在其 209.0 秒中花费了 203.7 秒执行插入排序，给出 $\alpha = 0.974$，即受加速影响的时间分数。使用快速排序，排序时间变得可以忽略不计，产生预测加速 $209/\alpha = 39.0$，接近测量的加速 38.5。我们能够获得大的加速，因为排序构成了整体执行时间的很大一部分。然而，当一个瓶颈被消除时，就会出现一个新的瓶颈，因此获得额外的加速需要关注程序的其他部分。

## 5.15 总结

尽管大多数关于代码优化的演示描述了编译器如何生成高效代码，但应用程序程序员可以做很多事情来帮助编译器完成此任务。没有编译器可以用好的算法或数据替换低效的算法或数据

---

<!-- Page 0597 -->

结构，因此程序设计的这些方面应该仍然是程序员的主要关注点。我们还看到，优化阻碍因素（如内存别名和过程调用）严重限制了编译器执行广泛优化的能力。程序员必须承担消除这些的主要责任。这些应该简单地被视为良好编程实践的一部分，因为它们有助于消除不需要的工作。

超越基本级别的性能调整需要对处理器的微架构有一定的了解，描述处理器实现其指令集架构的底层机制。对于乱序处理器的情况，仅了解有关功能单元的操作、能力、延迟和发射时间的一些信息就可以为预测程序性能建立基线。

我们研究了一系列技术——包括循环展开、创建多个累加器和重结合——可以利用现代处理器提供的指令级并行性。当我们深入优化时，研究生成的汇编代码并尝试理解机器如何执行计算变得很重要。通过识别程序中数据依赖性确定的关键路径，特别是在循环的不同迭代之间，可以获得很多收益。我们还可以计算计算的吞吐量界限，基于必须计算的操作数量以及执行这些操作的单元的数量和发射时间。

涉及条件分支或与内存系统的复杂交互的程序比我们首先考虑的简单循环程序更难分析和优化。基本策略是尝试使分支更可预测或使它们适合使用条件数据传输实现。我们还必须注意存储和加载操作之间的交互。将值保存在局部变量中，允许它们存储在寄存器中，通常会有所帮助。

在处理大型程序时，将优化工作集中在消耗最多时间的部分变得很重要。代码分析器和相关工具可以帮助我们系统地评估和改进程序性能。我们描述了 GPROF，一个标准的 Unix 分析工具。更复杂的分析器可用，例如来自英特尔的 VTUNE 程序开发系统，以及在 Linux 系统上通常可用的 VALGRIND。这些工具可以将执行时间分解到过程级别以下，以估计程序每个基本块的性能。（基本块是一系列指令，其中间没有控制转移，因此块总是完整执行。）

库函数 memset 具有以下原型：

```c

```

此函数用 c 的低位字节的副本填充从 s 开始的内存区域的 n 个字节。例如，它可以通过为 c 提供参数 0 来将内存区域清零，但其他值也是可能的。

以下是 memset 的直接实现：

```c
/* Basic implementation of memset */
void *basic_memset(void *s, int c, size_t n)
{
    size_t cnt = 0;
    unsigned char *schar = s;
    while (cnt < n) {
        *schar++ = (unsigned char) c;
        cnt++;
    }
    return s;
}
```

• 你不得调用任何库函数。

- 你的代码应该适用于 n 的任意值，包括当它不是 K 的倍数时。你可以以类似于我们完成循环展开的最后几次迭代的方式来做到这一点。

- 你应该编写代码，使其在任何机器上编译和正确运行，无论 K 的值如何。使用 sizeof 操作来做到这一点。

- 在某些机器上，未对齐的写入可能比对齐的写入慢得多。（在某些非 x86 机器上，它们甚至可能导致分段错误。）编写代码，使其以字节级写入开始，直到目标地址是 K 的倍数，然后执行字级写入，然后（如有必要）以字节级写入完成。

此汇编代码演示了 GCC 检测到的巧妙优化机会。值得仔细研究此代码以更好地理解代码优化的微妙之处。

A. 在优化较少的代码中，寄存器 %xmm0 只是用作临时值，在每次循环迭代中设置和使用。在优化更多的代码中，它更多地以 combine4 中变量 acc 的方式使用，累积向量元素的乘积。然而，与 combine4 的不同之处在于，位置 dest 在每次迭代中由第二个 vmovsd 指令更新。

我们可以看到此优化版本的操作非常类似于以下 C 代码：

```c
/* Make sure dest updated on each iteration */
void combine3w(vec_ptr v, data_t *dest)
{
    long i;
    long length = vec_length(v);
    data_t *data = get_vec_start(v);
    data_t acc = IDENT;

    /* Initialize in event length <= 0 */
    *dest = acc;

    for (i = 0; i < length; i++) {
        acc = acc OP data[i];
        *dest = acc;
    }
}
```

B. combine3 的两个版本将具有相同的功能，即使有内存别名。

C. 此转换可以在不改变程序行为的情况下进行，因为除了第一次迭代外，在每次迭代开始时从 dest 读取的值将是在上一次迭代结束时写入此寄存器的相同值。

### 练习题 5.12 答案（第 597 页）

这是该函数的修订版本：

```c
void psum1a(float a[], float p[], long n)
{
    long i;
    /* last_val holds p[i-1]; val holds p[i] */
    float last_val, val;
    last_val = p[0] = a[0];
    for (i = 1; i < n; i++) {
        val = last_val + a[i];
        p[i] = val;
        last_val = val;
    }
}
```

---

<!-- Page 0606 -->

我们引入一个局部变量 last_val。在迭代 i 开始时，它保存 p[i-1] 的值。然后我们计算 val 为 p[i] 的值并为 last_val 的新值。

此版本编译为以下汇编代码：

psum1a 的内部循环
a 在 %rdi，i 在 %rax，cnt 在 %rdx，last_val 在 %xmm0
```asm
1.L16: loop:
2 vaddss (%rdi,%rax,4), %xmm0, %xmm0 last_val = val = last_val + a[i]
3 vmovss %xmm0, (%rsi,%rax,4) Store val in p[i]
4 addq $1, %rax Increment i
5 cmpq %rdx, %rax Compare i:cnt
6 jne.L16 If!=, goto loop
```

此代码将 last_val 保存在 %xmm0 中，避免了需要从内存中读取 p[i-1]，从而消除了 psum1 中看到的写/读依赖性。
