编写程序的首要目标必须是使其在所有可能的条件下都能正确工作。运行快速但给出错误结果的程序没有任何实用价值。程序员必须编写清晰简洁的代码，不仅要让自己能够理解，还要让其他人在代码审查和后续修改时能够阅读和理解代码。

另一方面，在许多情况下，让程序快速运行也是一个重要考虑因素。如果程序必须实时处理视频帧或网络数据包，那么运行缓慢的程序将无法提供所需的功能。当计算任务要求极高，需要数天或数周才能执行时，让它运行快 20% 就可以产生重大影响。在本章中，我们将探索如何通过几种不同类型的程序优化来使程序运行得更快。

编写高效程序需要几种类型的活动。首先，我们必须选择一组合适的算法和数据结构。其次，我们必须编写编译器能够有效优化的源代码，以生成高效的可执行代码。对于第二部分，理解优化编译器的能力和局限性很重要。程序编写方式的看似微小的变化可能会对编译器优化程度产生很大差异。某些编程语言比其他语言更容易优化。C 的某些特性，例如执行指针算术和类型转换的能力，使得编译器难以对其进行优化。程序员通常可以通过使编译器更容易生成高效代码的方式来编写程序。处理特别苛刻的计算的第三种技术是将任务划分为可以在多个核心和多个处理器的某种组合上并行计算的部分。我们将把性能增强的这一方面推迟到第 12 章。即使在利用并行性时，每个并行线程以最高性能执行也很重要，因此本章的材料在任何情况下都保持相关性。

在进行程序开发和优化时，我们必须考虑代码将如何使用以及哪些关键因素影响它。一般来说，程序员必须在程序的实现、维护难易程度与运行速度之间做出权衡。在算法层面，一个简单的插入排序可以在几分钟内编程完成，而一个高效的排序例程可能需要一天或更长时间来实现和优化。在编码层面，许多低级优化往往会降低代码的可读性和模块化，使程序更容易出现错误，更难修改或扩展。对于将在性能关键环境中重复执行的代码，广泛的优化可能是合适的。一个挑战是在进行广泛转换的同时保持代码的某种程度的优雅性和可读性。

我们描述了许多提高代码性能的技术。理想情况下，编译器应该能够接受我们编写的任何代码，并生成具有指定行为的最高效的机器级程序。现代编译器采用复杂的分析和优化形式，并且它们不断改进。然而，即使是最好的编译器也可能被优化阻碍因素所挫败——程序行为的某些方面强烈依赖于执行环境。程序员必须通过编写易于优化的代码来帮助编译器。

<!-- Page 0525 -->

优化程序的第一步是消除不必要的工作，使代码尽可能高效地执行其预期任务。这包括消除不必要的函数调用、条件测试和内存引用。这些优化不依赖于目标机器的任何特定属性。

为了最大化程序的性能，程序员和编译器都需要一个目标机器的模型，指定指令如何处理以及不同操作的时序特性。例如，编译器必须知道时序信息才能决定是否应该使用乘法指令或某种移位和加法的组合。现代计算机使用复杂的技术来处理机器级程序，并行执行许多指令，并可能以与它们在程序中出现的顺序不同的顺序执行。程序员必须了解这些处理器的工作原理，才能调整他们的程序以获得最大速度。我们基于英特尔和 AMD 处理器的最新设计提出了这样一台机器的高级模型。我们还设计了一种图形数据流符号来可视化处理器执行指令的过程，通过它我们可以预测程序性能。

通过对处理器操作的理解，我们可以在程序优化中采取第二步，利用处理器提供指令级并行性的能力，同时执行多条指令。我们涵盖了几种程序转换，这些转换减少了计算不同部分之间的数据依赖性，提高了它们可以执行的并行度。

我们通过讨论与优化大型程序相关的问题来结束本章。我们描述了代码性能分析器的使用——测量程序不同部分性能的工具。这种分析可以帮助找到代码中的低效率并识别程序中应该集中优化工作的部分。

在本次演示中，我们让代码优化看起来像是按特定顺序对代码应用一系列转换的简单线性过程。实际上，这项任务远非如此简单。需要大量的试错实验。这在我们接近后期优化阶段时尤其如此，在这些阶段，看似很小的变化可能会导致性能的重大变化，而某些非常有前途的技术被证明是无效的。正如我们将在下面的示例中看到的，很难准确解释为什么特定的代码序列具有特定的执行时间。性能可能取决于处理器设计的许多详细特性，对于这些特性我们的文档或理解相对较少。这是尝试许多不同变化和技术组合的另一个原因。

研究程序的汇编代码表示是获得对编译器和生成代码如何运行的理解的最有效方法之一。一个好的策略是从仔细查看内部循环的代码开始，识别降低性能的属性，如过多的内存引用和寄存器的不良使用。从汇编代码开始，我们还可以预测哪些操作将并行执行以及它们将如何充分利用处理器资源。正如我们将看到的，我们通常可以通过识别关键路径来确定执行循环所需的时间（或至少是时间的下限），关键路径是在循环的重复执行期间形成的数据依赖链。然后我们可以返回并修改源代码，试图引导编译器朝着更高效的实现方向发展。

---

<!-- Page 0526 -->

大多数主要的编译器，包括 GCC，都在不断更新和改进，尤其是在优化能力方面。一个有用的策略是只对程序进行足够的重写，使其达到编译器可以生成高效代码的程度。通过这种方式，我们避免像使用能力最小的编译器那样损害代码的可读性、模块化和可移植性。同样，通过测量和检查生成的汇编代码来迭代修改代码和分析其性能是有帮助的。

对于初学者程序员来说，为了诱导编译器生成高效代码而不断修改源代码可能看起来很奇怪，但这确实是许多高性能程序的编写方式。与用汇编语言编写代码的替代方案相比，这种间接方法的优点是生成的代码仍然可以在其他机器上运行，尽管可能不是以峰值性能。

## 5.1 优化编译器的能力和局限性

现代编译器采用复杂的算法来确定程序中计算了哪些值以及如何使用它们。然后，它们可以利用机会来简化表达式、在多个不同的地方使用单个计算，以及减少必须执行给定计算的次数。大多数编译器，包括 GCC，为用户提供对应用哪些优化的一些控制。如第 3 章所述，最简单的控制是指定优化级别。例如，使用命令行选项 `-Og` 调用 GCC 指定它应该应用一组基本的优化。

使用选项 `-O1` 或更高（例如 `-O2` 或 `-O3`）调用 GCC 将导致它应用更广泛的优化。这些可以进一步提高程序性能，但它们可能会扩大程序大小，并且可能使使用标准调试工具调试程序变得更加困难。在我们的演示中，我们主要考虑使用优化级别 `-O1` 编译的代码，尽管级别 `-O2` 已成为使用 GCC 的大多数软件项目的公认标准。我们故意限制优化级别，以演示用 C 编写函数的不同方式如何影响编译器生成的代码的效率。我们将发现，我们可以编写 C 代码，当只使用选项 `-O1` 编译时，其性能远远超过使用最高可能优化级别编译的更幼稚的版本。

编译器必须小心地只对程序应用安全的优化，这意味着对于程序可能遇到的所有可能情况，生成的程序将具有与未优化版本完全相同的行为，直到 C 语言标准提供的保证的限制。限制编译器仅执行安全优化，可消除潜在的异常运行时行为来源，但这也意味着程序员必须付出更多努力，以编写出能被编译器转换为高效机器级代码的程序。为了理解决定哪些程序转换是安全的挑战，请考虑以下两个过程：

第二个优化阻碍因素是由于函数调用。作为一个例子，考虑以下两个过程：

```c
long f();

long func1() {
    return f() + f() + f() + f();
}

long func2() {
    return 4 * f();
}
```

乍一看，两者似乎计算相同的结果，但 func2 只调用 f 一次，而 func1 调用它四次。当给定 func1 作为源时，很容易生成 func2 风格的代码。

然而，考虑 f 的以下代码：

```c
long counter = 0;

long f() {
    return counter++;
}
```

这个函数有副作用——它修改了全局程序状态的某些部分。改变它被调用的次数会改变程序行为。特别是，调用 func1 将返回 $0 + 1 + 2 + 3 = 6$，而调用 func2 将返回 $4 \cdot 0 = 0$，假设两者都从全局变量 counter 设置为零开始。

>**旁注 通过内联替换优化函数调用**
>
>涉及函数调用的代码可以通过称为内联替换（或简称"内联"）的过程进行优化，其中函数调用被函数体的代码替换。例如，我们可以通过替换函数 f 的四个实例化来扩展 func1 的代码：
>
>```c
>/* Result of inlining f in func1 */
>long func1in() {
>    long t = counter++; /* +0 */
>    t += counter++;    /* +1 */
>    t += counter++;    /* +2 */
>    t += counter++;    /* +3 */
>    return t;
>}
>```
>
>这种转换既减少了函数调用的开销，又允许对扩展代码进行进一步优化。例如，编译器可以合并 func1in 中全局变量 counter 的更新以生成函数的优化版本：
>
>```c
>/* Optimization of inclined code */
>long func1opt() {
>    long t = 4 * counter + 6;
>    counter += 4;
>    return t;
>}
>```
>
>对于 f 的这个特定定义，此代码忠实地再现了 func1 的行为。
>
>最近版本的 GCC 尝试这种形式的优化，无论是在使用命令行选项 `-finline` 时，还是对于优化级别 `-O1` 及更高级别。不幸的是，GCC 只尝试对单个文件中定义的函数进行内联。这意味着它不会应用于常见情况，即在一个文件中定义一组库函数但在其他文件中的函数调用它们。
>
>有时最好防止编译器执行内联替换。一种情况是当使用符号调试器（如 GDB，如第 3.10.2 节所述）评估代码时。如果函数调用通过内联替换被优化掉，则任何跟踪或为该调用设置断点的尝试都将失败。第二种情况是通过性能分析评估程序性能时，如第 5.14.1 节所述。通过内联替换消除的函数调用将不会被正确分析。



大多数编译器不会尝试确定函数是否没有副作用，因此是诸如 func2 中尝试的优化的候选者。相反，编译器假设最坏的情况并保持函数调用完整。

## 5.2 表达程序性能

我们引入了每元素周期数 (cycles per element) 的度量，缩写为 CPE，以一种可以指导我们改进代码的方式表达程序性能。CPE 测量帮助我们在详细层面理解迭代程序的循环性能。它适用于执行重复计算的程序，例如处理图像中的像素或计算矩阵乘积中的元素。

处理器的活动排序由提供某个频率的规则信号的时钟控制，通常以千兆赫兹 (GHz)，即每秒数十亿个周期表示。例如，当产品文献将系统描述为"4 GHz"处理器时，这意味着处理器时钟以 $4.0 \times 10^{9}$ 周期/秒的速度运行。每个时钟周期所需的时间由时钟频率的倒数给出。这些通常以纳秒（1 纳秒是 $10^{-9}$ 秒）或皮秒（1 皮秒是 $10^{-12}$ 秒）表示。例如，4 GHz 时钟的周期可以表示为 0.25 纳秒或 250 皮秒。从程序员的角度来看，用时钟周期而不是纳秒或皮秒来表示测量更具指导意义。这样，测量表示正在执行多少条指令，而不是时钟运行的速度。

许多过程包含一个迭代一组元素的循环。例如，图 5.1 中的函数 psum1 和 psum2 都计算长度为 n 的向量的前缀和。对于向量 $\vec{a} = \langle a_0, a_1, \ldots, a_{n-1} \rangle$，前缀和 $\vec{p} = \langle p_0, p_1, \ldots, p_{n-1} \rangle$ 定义为

$$\begin{aligned}&p_{0}=a_{0}\\&p_{i}=p_{i-1}+a_{i},\quad1\leq i<n \tag{5.1}
\end{aligned}$$

函数 psum1 每次迭代计算结果向量的一个元素。函数 psum2 使用一种称为循环展开的技术每次迭代计算两个元素。我们将在本章后面探讨循环展开的好处。（有关分析和优化前缀和计算的更多信息，请参见问题 5.11、5.12 和 5.19。）

此类过程所需的时间可以表征为常数加上与处理的元素数量成比例的因子。例如，图 5.2 显示了这两个函数对于 n 的一系列值所需的时钟周期数的图。使用最小二乘拟合，我们发现 psum1 和 psum2 的运行时间（以时钟周期为单位）可以分别由方程 $368 + 9.0n$ 和 $368 + 6.0n$ 近似。这些方程表明由于计时代码和启动过程、设置循环和完成所需的 368 个周期的开销过程，加上每元素 6.0 或 9.0 个周期的线性因子。对于较大的 n 值（比如大于 200），运行时间将由线性因子主导。我们将这些项中的系数称为有效的每元素周期数。我们更喜欢测量每元素的周期数而不是每次迭代的周期数，因为诸如循环展开之类的技术允许我们使用更少的迭代来完成计算，但我们的最终关注点是程序对于给定向量长度运行的速度。我们将努力集中在最小化计算的 CPE 上。通过这个度量，CPE 为 6.0 的 psum2 优于 CPE 为 9.0 的 psum1。

>**旁注 什么是最小二乘拟合？**
>
>对于一组数据点 $(x_{1}, y_{1}), \ldots (x_{n}, y_{n})$，我们经常尝试绘制一条最能近似这些数据所代表的 X-Y 趋势的直线。通过最小二乘拟合，我们寻找形式为 $y = mx + b$ 的直线，该直线最小化以下误差度量：
>
>$$E(m,b)=\sum_{i=1,n}(mx_{i}+b-y_{i})^{2}$$
>
>可以通过找到 $E(m, b)$ 关于 m 和 b 的导数并将其设置为 0 来推导计算 m 和 b 的算法。

## 5.4 消除循环低效率

观察图 5.5 所示的过程 combine1，它调用函数 vec_length 作为 for 循环的测试条件。回想我们关于如何将包含循环的代码翻译成机器级程序的讨论（第 3.6.7 节），测试条件必须在循环的每次迭代中进行评估。另一方面，向量的长度在循环进行时不会改变。因此，我们可以只计算一次向量长度并在测试条件中使用此值。

图 5.6 显示了一个名为 combine2 的修改版本。它在开头调用 vec_length 并将结果分配给局部变量 length。这种转换对某些数据类型和操作的整体性能有明显影响，而对其他数据类型和操作的影响最小甚至没有。无论如何，这种转换是消除低效率所必需的，这些低效率在我们尝试进一步优化时会成为瓶颈。

这种优化是一类称为代码移动 (code motion) 的通用优化的实例。它们涉及识别执行多次的计算（例如，在循环内），但计算结果不会改变。因此，我们可以将计算移动到代码的早期部分，该部分不会被如此频繁地评估。在这种情况下，我们将对 vec_length 的调用从循环内移动到循环之前。

这个例子说明了编写程序中的一个常见问题，其中看似微不足道的代码具有隐藏的渐近低效率。人们不会期望小写转换例程成为程序性能的限制因素。通常，程序在小数据集上进行测试和分析，对于这些数据集，lower1 的性能是足够的。然而，当程序最终部署时，该过程完全有可能应用于超过一百万个字符的字符串。突然之间，这段良性的代码成为了主要的性能瓶颈。相比之下，lower2 的性能对于任意长度的字符串都是足够的。关于这类问题发生在主要编程项目中的故事比比皆是。有能力的程序员的部分工作是避免引入这种渐近低效率。

## 5.7 理解现代处理器

到目前为止，我们应用的优化不依赖于目标机器的任何特性。它们只是减少了过程调用的开销并消除了一些导致优化编译器困难的关键"优化阻碍因素"。当我们寻求进一步提高性能时，我们必须考虑利用处理器微架构的优化——也就是处理器执行指令的底层系统设计。要榨尽每一丝性能，需要对程序进行深入剖析，同时针对目标处理器优化代码生成过程。尽管如此，我们可以应用一些基本优化，这些优化将在大类处理器上产生整体性能改进。我们在这里报告的详细性能结果可能不适用于其他机器，但操作和优化的一般原理适用于各种各样的机器。

为了理解提高性能的方法，我们需要对现代处理器的微架构有基本的了解。由于可以集成到单个芯片上的大量晶体管，现代微处理器采用复杂的硬件来尝试最大化程序性能。其结果是，它们的实际操作与通过查看机器级程序所感知的视图大不相同。在代码层面，似乎指令是一次执行一条的，其中每条指令涉及从寄存器或内存中获取值、执行操作以及将结果存储回寄存器或内存位置。在实际处理器中，许多指令被同时评估，这种现象称为指令级并行性 (instruction-level parallelism)。在某些设计中，可能有 100 条或更多指令"正在执行中"。采用复杂的机制来确保这种并行执行的行为准确捕获机器级程序所需的顺序语义模型。这是现代微处理器的显著成就之一：它们采用复杂而奇特的微架构，其中多条指令可以并行执行，同时呈现简单的顺序指令执行的操作视图。

---

<!-- Page 0546 -->

尽管现代微处理器的详细设计远远超出了本书的范围，但对其操作原理有一个大致的了解，就足以理解它们如何实现指令级并行性。我们将看到，有两个不同的下界刻画了程序的最大性能。当一系列操作必须按严格顺序执行时，会遇到**延迟界限**（*latency bound*），因为下一个操作必须等待前一个操作的结果。当代码中的数据依赖限制了处理器利用指令级并行性的能力时，这一界限就会成为性能瓶颈。另一方面，**吞吐量界限**（*throughput bound*）刻画了处理器功能单元的原始计算能力。当不存在关键的数据依赖时，吞吐量界限将成为程序性能的最终限制。

### 5.7.1 整体操作

图 5.11 展示了现代微处理器的一个高度简化视图。我们假设的处理器设计大致参考了近期英特尔处理器的结构。这类处理器通常被称为**超标量**（*superscalar*），即每个时钟周期可以执行多个操作；同时也是**乱序执行**（*out of order*）的，即指令的实际执行顺序不必与其在机器级程序中的顺序一致。

整体设计包含两个主要部分：

* **指令控制单元（ICU, Instruction Control Unit）**：负责从内存中读取指令序列，并将其转换为一组对程序数据执行的原始操作。
* **执行单元（EU, Execution Unit）**：负责执行这些操作。

与第 4 章讨论的简单顺序流水线相比，乱序处理器需要更多、更复杂的硬件支持，但能够实现更高程度的指令级并行性。

ICU 从**指令高速缓存**（*instruction cache*）中读取指令——这是一种存放最近访问指令的高速存储器。通常，ICU 会在当前执行位置之前提前取指，以便有足够时间完成解码，并将操作发送到 EU。

然而，当程序遇到分支时，程序可能沿两个不同方向继续执行。分支可能被采纳（*taken*），控制流跳转至分支目标；也可能不被采纳（*not taken*），控制流继续顺序执行下一条指令。

现代处理器采用**分支预测**（*branch prediction*）技术来猜测分支是否会被采纳，并预测其目标地址。通过**推测执行**（*speculative execution*），处理器在尚未确认分支结果之前，就开始获取、解码并执行预测路径上的指令。如果后来发现预测错误，处理器会将状态恢复到分支点，并沿正确路径重新执行。

图中标记为“取指控制”的模块包含分支预测逻辑，用于决定接下来应获取哪些指令。

指令解码逻辑将程序指令转换为一组原始操作（也称为微操作，*micro-operations*）。每个微操作执行一个简单计算任务，例如加法、内存读取或写入。

在具有复杂指令集的体系结构（例如 x86）中，一条指令可能被解码为多个微操作。具体的解码方式在不同处理器之间存在差异，并通常属于厂商的专有技术。幸运的是，我们无需了解底层实现细节，也可以对程序进行有效优化。

---

<!-- Page 0548 -->

在典型的 x86 实现中，仅对寄存器进行操作的指令，例如：

```asm
addq %rax,%rdx
```

通常会被转换为单个微操作。

而涉及内存访问的指令，例如：

```asm
addq %rax,8(%rdx)
```

则会被拆分为多个微操作，将内存访问与算术计算分离。例如，该指令会被解码为三个操作：

1. 从内存加载数据；
2. 将加载值与寄存器 `%rax` 中的值相加；
3. 将结果写回内存。

这种拆分使不同的专用硬件单元可以分工协作，从而并行执行多条指令的不同部分。

EU 从 ICU 接收操作，通常每个时钟周期可以接收多个操作。这些操作被分派至一组**功能单元**（*functional units*），每类单元专门处理特定类型的操作。

* **加载单元（load unit）**：负责从内存读取数据，并包含用于地址计算的加法器。
* **存储单元（store unit）**：负责将数据写入内存，同样包含地址计算逻辑。

加载和存储单元通过**数据高速缓存**（*data cache*）访问内存。

在推测执行过程中，操作会被执行，但其最终结果在确认分支预测正确之前，不会写入程序寄存器或内存。若预测错误，EU 将丢弃分支点之后的所有计算结果，并通知分支单元重新取指。正如第 3.6.6 节所述，错误预测会带来显著的性能损失，因为重新取指、解码和分发操作需要时间。

图 5.11 还显示，不同功能单元被设计为支持不同类型的操作。标记为“算术操作”的单元通常支持整数与浮点操作的不同组合。随着晶体管数量的增加，新一代处理器不断扩展功能单元的数量、支持的操作种类以及执行性能。

功能单元通常被设计为支持多种操作类型，以适应不同程序的需求。例如，有的程序主要执行整数运算，而有的程序则以浮点运算为主。若功能单元类型过于单一，将无法充分利用硬件资源。

---

<!-- Page 0549 -->

例如，我们的参考机器——Intel Core i7 Haswell——包含 8 个功能单元（编号 0–7），部分功能如下：

0. 整数算术、浮点乘法、整数和浮点除法、分支
1. 整数算术、浮点加法、整数乘法、浮点乘法
2. 加载、地址计算
3. 加载、地址计算
4. 存储
5. 整数算术
6. 整数算术、分支
7. 存储地址计算

其中，“整数算术”包括加法、位运算和移位等基本操作；乘除法需要更专用的硬件资源。可以看到，存储操作需要两个功能单元：一个用于地址计算，另一个用于实际数据写入。

这种配置允许多个同类型操作并行执行。例如：

* 4 个单元可执行整数运算；
* 2 个单元可执行加载操作；
* 2 个单元可执行浮点乘法。

这些资源数量将直接影响程序可达到的最大吞吐量。

在 ICU 内部，**退役单元**（*retirement unit*）负责维护程序的顺序语义。图中寄存器文件（包括整数、浮点、SSE 和 AVX 寄存器）受退役单元控制。

当指令被解码时，其相关信息被放入一个先进先出队列。随后会发生两种情况之一：

* 若指令执行完成，且相关分支预测正确，则该指令**退役**，其结果写入程序寄存器；
* 若相关分支预测错误，则该指令被刷新，已计算结果被丢弃。

这种机制确保错误预测不会影响程序状态。

> **旁注：乱序处理的历史**
>
> 乱序执行最早出现在 1964 年的 CDC 6600 处理器中，该处理器拥有 10 个独立功能单元，主频为 10 MHz，当时被视为科学计算领域的顶级机器。
>
> 1966 年，IBM 在 360/91 处理器中引入乱序执行（仅用于浮点指令）。此后约 25 年间，该技术主要用于高性能计算机。
>
> 1990 年，IBM 在 RS/6000 系列中重新引入乱序处理，其设计成为 PowerPC 架构的基础。1993 年发布的 601 型号成为首个采用乱序执行的单芯片微处理器。1995 年，英特尔在 Pentium Pro 中引入乱序执行，其微架构与本节讨论的参考机器类似。

如前所述，程序寄存器的更新仅在指令退役时发生，且必须确认相关分支预测正确。

为加快指令间结果传递，大量数据在执行单元之间直接交换（图中标为“操作结果”）。执行单元之间可以直接转发结果，这是一种比第 4.5.5 节所述数据转发更为精细的实现方式。

控制执行单元之间操作数通信的关键机制称为**寄存器重命名**（*register renaming*）。

当一条更新寄存器 $r$ 的指令被解码时，会生成一个唯一标签 $t$ 作为该操作结果的标识。系统将条目 $(r, t)$ 添加到映射表中，用于记录寄存器与操作标签之间的对应关系。

当后续指令使用寄存器 $r$ 作为操作数时，其微操作将以标签 $t$ 作为数据来源。若某执行单元完成操作并产生结果 $(v, t)$，表示标签为 $t$ 的操作得到值 $v$，则所有等待标签 $t$ 的操作即可直接使用 $v$ 作为源操作数。

这种机制允许结果在执行单元之间直接转发，而无需写回寄存器文件后再读取，从而使后续操作能够在前一操作完成后立即开始。

重命名表仅记录存在待写操作的寄存器。若某指令使用寄存器 $r$ 且当前没有对应标签，则其操作数直接从寄存器文件中读取。

借助寄存器重命名机制，处理器可以对整个操作序列进行推测执行，即使程序寄存器的实际更新要等到分支结果确认之后才发生。

### 5.7.2 功能单元性能

图 5.12 展示了英特尔 Core i7 Haswell 参考机器上一些算术操作的性能数据。这些数据通过测量并参考英特尔文献 [49] 获得，对其他处理器也具有代表性。每个操作由三个特征参数描述：

* **延迟（latency）**：完成一次操作所需的总时钟周期数
* **发射时间（issue time）**：两个相同类型的独立操作之间的最小时钟周期数
* **容量（capacity）**：能够执行该操作的功能单元数量

可以看到，从整数运算到浮点运算，延迟逐渐增加。同时，加法和乘法操作的发射时间均为 1，意味着处理器可以在每个时钟周期启动一个新的同类操作。

这种短发射时间得益于**流水线（pipelining）**技术。流水线功能单元由多个阶段构成，每个阶段完成操作的一部分。例如，典型的浮点加法器包含三个阶段（因此延迟为 3 个周期）：

1. 处理指数
2. 执行尾数加法
3. 对结果进行舍入

操作可以在不同阶段中重叠执行，而不必等待前一个操作完全结束。只有当存在连续且逻辑独立的操作时，才能充分利用这一特性。

发射时间为 1 的功能单元称为**完全流水线化**（fully pipelined）单元——它们能够在每个时钟周期启动一个新操作。容量大于 1 则表示存在多个相同功能单元。

我们还注意到，用于整数除法、浮点除法以及浮点平方根的除法器**不是流水线化的**——其发射时间等于延迟。这意味着一个除法必须完全执行完毕，才能开始下一次除法。

此外，除法的延迟和发射时间以范围形式给出，因为某些被除数与除数的组合需要更多计算步骤。除法较长的延迟与发射时间，使其成为相对昂贵的操作。

---

<!-- Page 0552 -->

表达发射时间的另一种常见方式是使用**最大吞吐量（maximum throughput）**，其定义为发射时间的倒数。

* 完全流水线化单元的最大吞吐量为：每周期 1 次操作
* 发射时间更高的单元具有更低的最大吞吐量

多个功能单元可进一步提高吞吐量。若某操作容量为 $C$，发射时间为 $I$，则处理器理论上可以达到每周期 $ \frac{C}{I} $ 次操作的吞吐量。

例如，我们的参考机器能够以每周期 2 次的速率执行浮点乘法。

电路设计者可以构建具有不同性能特性的功能单元。实现更短延迟或流水线化通常需要更多硬件资源，尤其对于乘法和浮点运算等复杂操作。

由于芯片面积有限，CPU 设计者必须在功能单元数量与性能之间取得平衡。他们通过评估大量基准程序，将更多资源分配给关键操作。如图 5.12 所示，在 Core i7 Haswell 的设计中，整数乘法以及浮点乘法和加法被认为是关键操作，因此为其提供了低延迟与高度流水线化的实现。而除法较少使用且难以优化，因此性能相对较弱。

这些操作的延迟、发射时间和容量会影响组合函数的性能。我们可以用两个基本界限来描述其对 CPE（Cycles Per Element）的影响：

![page-552-1.png](../figures/ch05/page-552-1.png)

* **延迟界限（latency bound）**：必须严格顺序执行的操作链所决定的最小 CPE
* **吞吐量界限（throughput bound）**：由功能单元的最大结果产生速率所决定的最小 CPE

例如：

* 只有一个整数乘法器，且发射时间为 1，因此最多每周期 1 次乘法
* 有四个整数加法单元，因此理论上可达到每周期 4 次加法

然而，从内存加载数据也会形成额外的吞吐量限制。两个加载单元限制为每周期最多读取 2 个数据值，对应吞吐量界限 0.50。

我们将在不同版本的组合函数中展示延迟界限与吞吐量界限的影响。

### 寄存器分类

**只读（Read-only）**
在循环中仅作为源操作数使用，不被修改。此处为 `%rax`。

**只写（Write-only）**
仅作为目标寄存器。本例中无。

**本地（Local）**
在循环内部更新与使用，但不跨迭代传递。条件码寄存器属于此类。

跨迭代传递值，既作为源又作为目标。本例中为 `%rdx` 与 `%xmm0`，分别对应 `data+i` 与 `acc`。

当计算每个 `acc` 的新值时，该结果必须等待 5 个周期后才能用于下一次乘法运算，因此形成了长度为 $5n$ 的关键路径。

**其他性能因素**

另一方面，对于整数加法的情况，我们测得 `combine4` 的 CPE 为 1.27，慢于根据图 5.15 左右两条依赖链所预测的 1.00。这说明：数据流图中的关键路径仅给出了程序执行周期数的下界。

实际性能还可能受到其他因素的限制，例如：

* 可用功能单元的数量；
* 每个周期功能单元之间可传递的数据量。

在整数加法作为组合操作的情况下，数据操作速度足够快，以至于其他操作无法及时提供所需数据。要精确解释为何每个元素需要 1.27 个周期，必须掌握比公开资料更为详细的硬件设计信息。

总结对 `combine4` 的性能分析：其抽象数据流表示表明存在一条长度为 $L \cdot n$ 的关键路径，该路径由 `acc` 的连续更新形成，因此 CPE 至少为 $L$。这一结论与除整数加法外的测量结果一致；对于整数加法，测得的 CPE 为 1.27，而非关键路径预测的 1.00。

这表明延迟界限对组合操作的执行速度构成了根本限制。接下来的任务是通过重构程序以增强指令级并行性，使性能限制由吞吐量界限决定，从而获得低于或接近 1.00 的 CPE。

## 5.8 循环展开

循环展开（loop unrolling）是一种程序变换技术，通过在每次迭代中处理多个元素来减少循环的总迭代次数。我们在函数 `psum2`（图 5.1）中已经见过这种方法：每次迭代计算两个前缀和元素，从而将迭代次数减半。

循环展开可通过两种方式提升性能：

1. 减少不直接贡献于最终结果的操作数量，例如循环索引更新与条件分支；
2. 暴露更多优化机会，从而缩短整体关键路径。

本节仅讨论简单的循环展开，而不涉及进一步的代码变换。

图 5.16 展示了组合代码的一个版本，采用“$2 \times 1$ 循环展开”方式。第一个循环每次跨越数组中的两个元素：循环索引 $i$ 每次递增 2，在单次迭代中对元素 $i$ 和 $i+1$ 应用组合操作。

通常，向量长度未必是 2 的倍数，因此必须保证代码对任意长度都能正确工作。为此：

* 将循环上界设置为 $n - 1$；
* 仅当 $i < n - 1$ 时执行循环。

这样最大访问索引 $i+1$ 满足：

$$
i + 1 < (n - 1) + 1 = n
$$

这一思想可推广到按任意因子 $k$ 展开循环，即形成 $k \times 1$ 循环展开。具体做法如下：

* 将循环上界设置为 $n - k + 1$；
* 在每次迭代中对元素 $i$ 到 $i + k - 1$ 应用组合操作；
* 循环索引 $i$ 每次递增 $k$。

此时最大访问索引 $i + k - 1 < n$。

此外，还需使用第二个循环处理剩余的元素，该循环将执行 0 到 $k - 1$ 次。对于 $k = 2$，可以用简单条件语句处理最后一次迭代；但对于 $k > 2$，使用循环更为通用。因此，即便在 $k = 2$ 时，我们也采用统一的循环形式。

这种变换称为“$k \times 1$ 循环展开”，因为我们按因子 $k$ 展开循环，但仍在单个变量 `acc` 中累积结果。

## 5.9 增强并行性

到目前为止，我们的函数性能受限于算术单元的延迟界限。然而，正如前文所述，执行加法和乘法的功能单元都是完全流水线化的，这意味着它们可以在每个时钟周期启动一个新操作，并且某些操作还可以由多个功能单元并行执行。硬件本身具备以更高速率执行乘法和加法的能力，但我们的代码却无法利用这一点——即使进行了循环展开——因为我们将结果累积到单一变量 `acc` 中。只有在前一次计算完成之后，才能计算 `acc` 的新值。

即便用于计算 `acc` 的功能单元能够在每个时钟周期启动新操作，它实际上也只能每 $L$ 个周期启动一次，其中 $L$ 是组合操作的延迟。下面我们将探讨如何打破这种顺序依赖关系，从而获得优于延迟界限的性能。

### 5.9.1 多个累加器

对于满足结合律和交换律的组合操作（例如整数加法或乘法），我们可以将操作集合划分为两个或更多部分，分别计算后再合并结果，从而提高性能。

例如，设 $P_n$ 表示元素 $a_0, a_1, \ldots, a_{n-1}$ 的乘积：

$$
P_n = \prod_{i=0}^{n-1} a_i
$$

假设 $n$ 为偶数，则可以将其写为：

$$
P_n = PE_n \times PO_n
$$

其中，$PE_n$ 是偶数下标元素的乘积，$PO_n$ 是奇数下标元素的乘积：

$$
PE_n = \prod_{i=0}^{n/2-1} a_{2i}
$$

$$
PO_n = \prod_{i=0}^{n/2-1} a_{2i+1}
$$

图 5.21 展示了采用该方法的代码实现。该实现同时使用了双向循环展开（每次迭代处理更多元素）以及双路并行，在变量 `acc0` 中累积偶数下标元素，在变量 `acc1` 中累积奇数下标元素。因此，我们将其称为 “$2 \times 2$ 循环展开”。

与之前一样，我们还包含了第二个循环，用于处理向量长度不是 2 的倍数时的剩余元素。最后，再对 `acc0` 和 `acc1` 应用组合操作以计算最终结果。

一般而言，只有当程序能够使所有可执行该操作的功能单元始终保持流水线满载时，才能达到操作的吞吐量界限。对于延迟为 $L$、容量为 $C$ 的操作，这意味着展开因子必须满足

$$

例如，浮点乘法的 $C = 2$、$L = 5$，因此需要 $k \geq 10$。浮点加法的 $C = 1$、$L = 3$，当 $k \geq 3$ 时即可实现最大吞吐量。

在执行 $k \times k$ 展开转换时，必须考虑是否保持了原始函数的语义。我们在第 2 章中已经看到，二进制补码算术满足交换律和结合律，即使发生溢出也是如此。因此，对于整数数据类型，combine6 的计算结果在所有情况下都与 combine5 相同。优化编译器可能首先通过循环展开将 combine4 中的代码转换为类似 combine5 的双向展开形式，然后再通过引入并行性转换为类似 combine6 的代码。一些编译器确实会执行这种或类似的转换，以提升整数运算的性能。

然而，浮点乘法和加法并不满足结合律。因此，combine5 和 combine6 可能因舍入误差或溢出而产生不同结果。例如，设想一种乘积计算：所有偶数索引元素的绝对值非常大，而奇数索引元素非常接近 0.0。在这种情况下，乘积 $PE_n$ 可能发生溢出，或 $PO_n$ 可能发生下溢，即使整体乘积 $P_n$ 的顺序计算是正常的。

不过，在大多数实际应用中，这种模式出现的可能性较低。由于大多数物理现象是连续的，数值数据通常较为平滑且表现良好。即便存在不连续性，也通常不会形成导致上述极端情况的周期性模式。严格按顺序相乘不太可能比先分别计算两组乘积再相乘在准确性上有本质优势。对于大多数应用而言，获得 $2 \times$ 的性能提升远比因特殊数据模式而产生不同结果的风险更有价值。

尽管如此，程序开发者仍应与潜在用户确认，是否存在可能使修改后算法不可接受的特殊情况。由于编译器无法判断这种行为改变所带来的风险（哪怕极小），大多数编译器不会对浮点代码进行此类转换。

### 5.9.2 重结合转换

现在我们探讨另一种打破顺序依赖、从而将性能提升至延迟界限之外的方法。我们已经看到，combine5 的 $k \times 1$ 循环展开并未改变用于组合向量元素形成和或积的操作集合。然而，只需对代码做出极小修改，就可以从根本上改变组合方式，并显著提升程序性能。

图 5.26 展示了函数 combine7。它与 combine5 的展开代码（图 5.16）唯一的区别在于内部循环中元素的组合方式。

在 combine5 中，组合由下列语句完成：

```

```

>
> 如第 3.1 节所述，英特尔于 1999 年引入了 SSE 指令。SSE 是 “Streaming SIMD Extensions”（流式 SIMD 扩展）的缩写，而 SIMD（发音为 “sim-dee”）则是 “Single Instruction, Multiple Data”（单指令多数据）的缩写。SSE 经历了多代发展，最新版本称为高级向量扩展（AVX, Advanced Vector Extensions）。
>
> SIMD 执行模型是在单条指令中对整个数据向量进行操作。这些向量保存在一组专用向量寄存器中，命名为 %ymm0–%ymm15。当前 AVX 向量寄存器长度为 32 字节，因此每个寄存器可以容纳 8 个 32 位数字或 4 个 64 位数字，这些数字既可以是整数，也可以是浮点数。

## 5.11 一些限制因素

我们已经看到，程序数据流图中的关键路径为程序执行时间给出了一个基本下界。也就是说，如果程序中存在一条数据依赖链，其总延迟为 $T$，那么程序至少需要 $T$ 个周期才能完成执行。

我们还看到，功能单元的吞吐量上界同样会对执行时间施加约束。也就是说，假设某种操作总共需要执行 $N$ 次，微处理器中有 $C$ 个可执行该操作的功能单元，每个单元的发射间隔为 $I$，那么程序至少需要

$$
\frac{N \cdot I}{C}
$$

个周期才能完成执行。

在本节中，我们将讨论其他一些限制实际机器上程序性能的因素。

### 5.11.1 寄存器溢出

循环并行性的收益受限于汇编代码中可表达计算的能力。如果程序的并行度 $P$ 超过可用寄存器数量，编译器就不得不进行寄存器溢出（spilling），将部分临时变量存储到内存中，通常是在运行时栈上分配空间。例如，下面的测量结果比较了将 `combine6` 的多累加器策略扩展到 $k=10$ 与 $k=20$ 时的表现：

更新 $20\times20$ 展开中的累加器 acc0


此时累加器作为局部变量存储在栈上，位于栈指针偏移 40 字节处。程序必须先从内存读取累加器的值以及 `data[i]`，进行乘法运算后，再将结果写回内存。

一旦编译器不得不进行寄存器溢出，维护多个累加器所带来的优势很可能会丧失。幸运的是，x86-64 提供了相对充足的寄存器资源，因此大多数循环在发生寄存器溢出之前，通常已经受限于吞吐量瓶颈。

### 5.11.2 分支预测与错误预测惩罚

我们在第 3.6.6 节通过实验证明，当分支预测逻辑未能正确预测分支是否被采纳时，条件分支可能会导致显著的错误预测惩罚。现在，在理解了处理器的工作机制之后，我们可以更清楚地解释这一惩罚产生的原因。

现代处理器能够超前工作，在当前指令执行之前就从内存中读取并解码后续指令，从而确定操作类型与操作数。只要指令按照顺序执行，指令流水线便能高效运行。

当遇到分支指令时，处理器必须猜测程序将走哪条路径。对于条件跳转，需要预测分支是否被采纳；对于间接跳转（例如跳转表）或过程返回，则需要预测目标地址。本节重点关注条件分支。

在采用推测执行（speculative execution）的处理器中，处理器会开始执行预测路径上的指令，但在确认实际结果之前，不会真正修改寄存器或内存。一旦预测被验证为正确，处理器就会“提交”这些推测执行的结果；若预测错误，则必须丢弃所有推测结果，并从正确位置重新开始取指。这一过程需要重新填充指令流水线，从而产生错误预测惩罚。

---

<!-- Page 0578 -->

我们在第 3.6.6 节中提到，所有支持 x86-64 的现代 x86 处理器都提供条件移动（conditional move）指令。在编译条件语句或表达式时，GCC 可以生成基于条件移动的代码，而不是传统的基于控制转移的实现方式。

条件移动的基本思想是：先计算条件表达式两个分支的结果，然后使用条件移动指令选择所需的值。正如第 4.5.7 节所述，条件移动指令可以作为普通指令流水线的一部分执行，不需要预测分支是否成立，因此也不会产生错误预测惩罚。

那么，C 程序员应如何避免分支错误预测对性能造成影响？在我们参考机器上，错误预测惩罚高达 19 个周期，代价极为显著。虽然没有简单的统一答案，但以下原则通常适用。

**不要过度关注可预测分支**

尽管错误预测可能代价高昂，但这并不意味着所有分支都会降低程序性能。事实上，现代处理器的分支预测机制能够很好地识别规律性模式和长期趋势。例如，在组合例程中，循环结束分支通常会被预测为“被采纳”，因此仅在最后一次迭代时发生一次错误预测。

在整数加法情况下，带边界检查的版本略慢，但在其他三种情形下性能相同。这些情况的性能受组合操作延迟限制。执行边界检查所需的额外计算可以与组合操作并行完成。由于分支高度可预测，它们不会对关键路径上的指令获取与执行产生显著影响。

**编写易于使用条件移动实现的代码**

分支预测仅对规律性模式可靠。程序中许多测试本质上不可预测，例如依赖数据特征（数值正负等）。对于此类不可预测情况，如果编译器能够使用条件数据传输而非条件控制转移生成代码，性能将显著提升。

虽然 C 程序员无法直接控制这一点，但某些表达条件行为的方式更容易被编译为条件移动指令。

我们发现，GCC 更容易为“函数式”风格代码生成条件移动指令——即先计算值，再根据条件更新状态；相比之下，“命令式”风格代码——根据条件选择性地更新状态——更容易生成分支。

## 5.12 理解内存性能

到目前为止，我们编写的所有代码以及运行的所有测试都只访问了相对较少的内存。例如，组合（combine）例程是在长度小于 1,000 个元素的向量上测量的，所需数据不超过 8,000 字节。所有现代处理器都包含一个或多个高速缓存（cache），用于提供对少量数据的高速访问。

在本节中，我们将进一步研究涉及加载（load：从内存读入寄存器）和存储（store：从寄存器写入内存）操作的程序性能，并假设所有数据均保存在高速缓存中。第 6 章将更详细地介绍高速缓存的工作原理、性能特性，以及如何编写能够充分利用高速缓存的代码。

---

<!-- Page 0582 -->

如图 5.11 所示，现代处理器配备了专用的加载和存储功能单元。这些单元内部带有缓冲区，用于保存尚未完成的内存操作请求。例如，我们的参考机器具有两个加载单元，每个单元最多可容纳 72 个未完成的读取请求；此外，它还有一个存储单元，配备一个最多可容纳 42 个写请求的存储缓冲区。每个功能单元都可以在每个时钟周期启动 1 次操作。

### 5.12.1 加载性能

包含加载操作的程序性能取决于加载单元的流水线能力和访问延迟。

在我们使用参考机器进行组合操作的实验中发现，对于任意数据类型和组合运算，只要未使用 SIMD 指令，CPE 从未低于 0.50。限制 CPE 的一个关键因素在于：每计算一个元素都需要从内存中读取一个值。由于存在两个加载单元，且每个单元每个时钟周期最多启动 1 次加载操作，因此 CPE 不可能低于 0.50。

对于必须为每个元素加载 $k$ 个值的应用程序，其 CPE 不可能低于 $ \frac{k}{2} $（例如参见问题 5.15）。

在此前的示例中，我们尚未观察到加载延迟对性能的影响。这是因为加载地址仅依赖于循环索引 $i$，因此加载操作不构成关键路径的一部分。

为了确定机器上加载操作的延迟，可以构造一段加载链，其中一次加载的结果决定下一次加载的地址。例如，考虑图 5.31 中的函数 `list_len`，它用于计算链表长度。在该函数的循环中，变量 `ls` 的每一个新值都依赖于对指针 `ls->next` 的加载结果。

### 5.12.2 存储性能

在此前所有示例中，我们主要分析了以加载操作为主的函数，即从内存读取数据到寄存器。与之对应的是存储操作，它将寄存器中的值写入内存。存储操作的性能，尤其是其与加载操作之间的交互，涉及若干微妙问题。

与加载操作类似，在大多数情况下，存储操作也可以完全流水线化运行，即每个周期启动一次存储操作。例如，图 5.32 中的函数将长度为 $n$ 的数组 `dest` 的所有元素设为 0。测量结果显示其 CPE 为 1.0，这是在具有单一存储单元的机器上可以达到的最佳性能。

与此前分析的其他操作不同，存储操作不会影响寄存器值。因此，从本质上讲，一系列存储操作本身不会形成数据依赖链。只有加载操作可能受到存储操作的影响，因为只有加载操作会读取先前写入内存的数据。

## 5.13 现实世界：性能改进技术

尽管我们只考虑了有限的一组应用程序，但我们可以从中汲取关于如何编写高效代码的重要经验。我们描述了优化程序性能的一些基本策略：

**高级设计**。为手头的问题选择适当的算法和数据结构。特别要警惕避免产生渐近性能差的算法或编码技术。

**基本编码原则**。避免优化阻碍因素，以便编译器可以生成高效的代码。

    - 消除过多的函数调用。尽可能将计算移出循环。考虑选择性地牺牲程序模块化以获得更高的效率。

---

<!-- Page 0590 -->

    - 消除不必要的内存引用。引入临时变量来保存中间结果。仅在计算出最终值时才将结果存储在数组或全局变量中。

**低级优化**。构建代码以利用硬件能力。

    - 展开循环以减少开销并启用进一步的优化。

    - 通过诸如多累加器和重结合等技术找到增加指令级并行性的方法。

    - 以函数式风格重写条件操作，以启用通过条件数据传输进行编译。

对读者的最后建议是，在为提高效率而重写程序时要警惕避免引入错误。在引入新变量、更改循环边界和使代码整体更复杂时很容易出错。一种有用的技术是使用检查代码在优化时测试函数的每个版本，以确保在此过程中不引入错误。检查代码对函数的新版本应用一系列测试，并确保它们产生与原始版本相同的结果。测试用例集必须随着高度优化的代码变得更加广泛，因为有更多的情况需要考虑。例如，使用循环展开的检查代码需要测试许多不同的循环边界，以确保它处理结尾所需的所有不同可能数量的单步迭代。

## 5.14 识别和消除性能瓶颈

到目前为止，我们只考虑了优化小程序，其中程序中有一些明确的地方限制其性能，因此应该是我们优化工作的重点。在处理大型程序时，即使知道将优化工作集中在哪里也可能很困难。在本节中，我们描述如何使用代码分析器 (code profiler)，即在程序执行时收集程序性能数据的分析工具。我们还讨论代码优化的一些一般原则，包括第 1.9.1 节中介绍的阿姆达尔定律的含义。

### 5.14.1 程序分析

程序分析涉及运行程序的一个版本，其中已合并仪器代码以确定程序的不同部分需要多少时间。它对于识别我们应该在优化工作中关注的程序部分非常有用。分析的一个优势是它可以在实际程序在真实基准数据上运行时执行。

Unix 系统提供分析程序 GPROF。此程序生成两种形式的信息。首先，它确定程序中每个函数花费了多少 CPU 时间。其次，它计算每个函数被调用的次数，按执行调用的函数分类。这两种形式的信息都可能非常有用。这些时间数据揭示了不同功能模块在决定总运行时间中的相对重要性。调用信息允许我们理解程序的动态行为。

---

使用 GPROF 进行分析需要三个步骤，如 C 程序 prog.c 所示，它使用命令行参数 file.txt 运行：

1. 程序必须编译和链接以进行分析。使用 GCC（和其他 C 编译器），这只需在命令行上包含运行时标志 -pg。重要的是确保编译器不尝试通过内联替换执行任何优化，否则对函数的调用可能无法准确制表。我们使用优化标志 -Og，保证函数调用将被正确跟踪。

    ```bash
    linux> gcc -Og -pg prog.c -o prog
    ```

2. 然后程序像往常一样执行：

    ```bash
    linux>./prog file.txt
    ```

    它运行得稍慢（约 2 倍），但除此之外，唯一的区别是它生成一个文件 gmon.out。

3. 调用 GPROF 来分析 gmon.out 中的数据：

    ```bash
    linux> gprof prog
    ```

从这些调用数据中，我们通常可以推断出有关程序行为的有用信息。例如，函数 find_ele_rec 是一个递归过程，它扫描哈希桶的链表以查找特定字符串。对于此函数，将递归调用次数与顶级调用次数进行比较可提供有关这些列表遍历长度的统计信息。鉴于它们的比率为 164.4:1，我们可以推断程序每次平均扫描约 164 个元素。

GPROF 的一些属性值得注意：

- 时序不是很精确。它基于一个简单的间隔计数方案，其中编译后的程序为每个函数维护一个计数器，记录执行该函数所花费的时间。操作系统使程序以某个规则的时间间隔 $\delta$ 中断。$\delta$ 的典型值在 1.0 到 10.0 毫秒之间。然后它确定程序在中断发生时正在执行的函数，并将该函数的计数器递增 $\delta$。当然，可能会发生这样的情况：此函数刚刚开始执行并且很快就会完成，但由于自上次中断以来，它被分配了完整的执行成本。某些其他函数可能在两次中断之间运行，因此根本不收取任何时间。

    在很长一段时间内，该方案效果相当不错。从统计上讲，每个函数都应该根据执行它所花费的相对时间收费。然而，对于运行时间不到约 1 秒的程序，这些数字应该被视为仅粗略估计。

- 调用信息相当可靠，假设没有执行内联替换。编译后的程序为每个调用者和被调用者的组合维护一个计数器。每次调用过程时，相应的计数器就会递增。

- 默认情况下，不显示库函数的时序。相反，这些时间被合并到调用函数的时间中。

### 5.14.2 使用分析工具指导优化

作为使用分析器指导程序优化的示例，我们创建了一个涉及几个不同任务和数据结构的应用程序。此应用程序分析文本文档的 n-gram 统计信息，其中 n-gram 是文档中出现的 n 个单词的序列。对于 n = 1，我们收集单个单词的统计信息，对于 n = 2 收集单词对的统计信息，依此类推。对于给定的 n 值，我们的程序读取文本文件，创建一个唯一 n-gram 表及其每个出现的次数，然后按出现的降序对 n-gram 进行排序。

作为基准，我们在一个包含威廉·莎士比亚全集的文件上运行它，总共 965,028 个单词，其中 23,706 个是唯一的。我们发现对于 n = 1，即使是编写不佳的分析程序也可以在不到 1 秒内轻松处理整个文件，因此我们设置 n = 2 以使事情更具挑战性。对于 n = 2 的情况，n-gram 被称为 bigram（发音为"bye-grams"）。我们确定莎士比亚的作品包含 363,039 个唯一的 bigram。最常见的是"I am"，出现 1,892 次。也许他最著名的 bigram，"to be"，出现 1,020 次。完全有 266,018 个 bigram 只出现一次。

我们的程序由以下部分组成。我们创建了多个版本，从不同部分的简单算法开始，然后用更复杂的算法替换它们：

1. 每个单词从文件中读取并转换为小写。我们的初始版本使用函数 lower1（图 5.7），我们知道由于重复调用 strlen 而具有二次运行时间。

3. 每个哈希桶组织为链表。程序扫描此列表以查找匹配的条目。如果找到一个，则增加此 n-gram 的频率。否则，创建一个新的列表元素。我们的初始版本递归执行此操作，在列表末尾插入新元素。

随着排序的改进，我们现在发现列表扫描成为瓶颈。认为效率低下是由于函数的递归结构，我们将其替换为迭代函数，显示为"Iter first"。令人惊讶的是，运行时间增加到约 7.5 秒。经过更仔细的研究，我们发现两个列表函数之间存在微妙的差异。递归版本在列表末尾插入新元素，而迭代版本在前面插入它们。为了最大化性能，我们希望最频繁的 n-gram 出现在列表的开头附近。这样，函数将快速定位常见情况。假设 n-gram 在整个文档中均匀分布，我们会期望频繁的 n-gram 的第一次出现在不太频繁的 n-gram 之前。通过在末尾插入新 n-gram，第一个函数倾向于按频率的降序对 n-gram 进行排序，而第二个函数倾向于做相反的事情。因此，我们创建了第三个列表扫描函数，该函数使用迭代但在此列表末尾插入新元素。使用此版本，显示为"Iter last"，时间下降到约 5.3 秒，略好于递归版本。这些测量表明，作为优化工作的一部分，对程序运行实验的重要性。我们最初假设将递归代码转换为迭代代码会提高其性能，并没有考虑添加到列表末尾或开头之间的区别。严格按顺序乘以元素不太可能比独立乘以两组然后将这些乘积相乘在一起提供根本上更好的准确性。对于大多数应用程序，实现 $2 \times$ 的性能提升超过了为奇怪数据模式产生不同结果的风险。尽管如此，程序开发人员应该与潜在用户核实，看看是否存在可能导致修订算法不可接受的特殊条件。大多数编译器不会尝试使用浮点代码进行此类转换，因为它们无法判断引入可能改变程序行为的转换的风险，无论多么小。

接下来，我们考虑哈希表结构。初始版本只有 1,021 个桶（通常，桶的数量被选择为素数以增强哈希函数在桶中均匀分布键的能力）。对于具有 363,039 个条目的表，这将意味着 363,039/1,021 = 355.6 的平均负载。这解释了为什么如此多的时间花费在执行列表操作上——搜索涉及测试大量候选 n-gram。它还解释了为什么性能对列表排序如此敏感。然后我们将桶的数量增加到 199,999，将平均负载减少到 1.8。然而，奇怪的是，我们的总运行时间仅下降到 5.1 秒，差异仅为 0.2 秒。

经过进一步检查，我们可以看到使用较大表的最小性能提升是由于哈希函数的选择不佳。简单地对字符串的字符代码求和不会产生非常宽的值范围。特别是，字母的最大代码值为 122，因此 n 个字符的字符串将生成最多 122n 的总和。我们文档中最长的 bigram，"honorificabilitudinitatibus thou" 总和仅为 3,371，因此我们哈希表中的大多数桶将未使用。此外，可交换的哈希函数（如加法）不区分字符串中字符的不同可能排序。例如，单词"rat"和"tar"将生成相同的总和。

我们切换到使用移位和异或操作的哈希函数。使用此版本，显示为"Better hash"，时间下降到 0.6 秒。更系统的方法是更仔细地研究键在桶中的分布，确保它接近如果哈希函数具有均匀输出分布时所期望的结果。

最后，我们已将运行时间减少到大部分时间花费在 strlen 中的点，并且 strlen 的大部分调用作为小写转换的一部分发生。我们已经看到函数 lower1 具有二次性能，特别是对于长字符串。此文档中的单词足够短，可以避免二次性能的灾难性后果；最长的 bigram 只有 32 个字符。尽管如此，切换到 lower2，显示为"Linear lower"，产生了显著的改进，总时间下降到约 0.2 秒。

通过这个练习，我们已经展示了代码分析可以帮助将简单应用程序所需的时间从 3.5 分钟下降到 0.2 秒，产生约 $1,000 \times$ 的性能提升。分析器帮助我们将注意力集中在程序最耗时的部分，并提供有关过程调用结构的有用信息。我们代码中的一些瓶颈，例如使用二次排序例程，很容易预料到，而其他瓶颈，例如是附加到列表的开头还是结尾，只有通过仔细分析才会出现。

我们可以看到，分析是工具箱中拥有的有用工具，但它不应该是唯一的工具。时序测量不完美，特别是对于较短（少于 1 秒）的运行时间。更重要的是，结果仅适用于测试的特定数据。例如，如果我们在由较少数量的较长字符串组成的数据上运行原始函数，我们会发现小写转换例程是主要的性能瓶颈。更糟糕的是，如果它只分析具有短单词的文档，我们可能永远不会检测到隐藏的瓶颈，例如 lower1 的二次性能。一般来说，分析可以帮助我们针对典型情况进行优化，假设我们在代表性数据上运行程序，但我们还应该确保程序对所有可能的情况都具有良好的性能。这主要涉及避免产生较差渐近性能的算法（如插入排序）和不良编程实践（如 lower1）。

第 1.9.1 节中描述的阿姆达尔定律提供了关于通过针对性优化可以获得的性能提升的一些额外见解。对于我们的 n-gram 代码，当我们用快速排序替换插入排序时，我们看到总执行时间从 209.0 秒下降到 5.4 秒。初始版本在其 209.0 秒中花费了 203.7 秒执行插入排序，给出 $\alpha = 0.974$，即受加速影响的时间分数。使用快速排序，排序时间变得可以忽略不计，产生预测加速 $209/\alpha = 39.0$，接近测量的加速 38.5。我们能够获得大的加速，因为排序构成了整体执行时间的很大一部分。然而，当一个瓶颈被消除时，就会出现一个新的瓶颈，因此获得额外的加速需要关注程序的其他部分。

## 5.15 总结

尽管大多数关于代码优化的演示描述了编译器如何生成高效代码，但应用程序程序员可以做很多事情来帮助编译器完成此任务。没有编译器可以用好的算法或数据替换低效的算法或数据结构，因此程序设计的这些方面应该仍然是程序员的主要关注点。我们还看到，优化阻碍因素（如内存别名和过程调用）严重限制了编译器执行广泛优化的能力。程序员必须承担消除这些的主要责任。这些应该简单地被视为良好编程实践的一部分，因为它们有助于消除不需要的工作。

---

<!-- Page 0597 -->

超越基本级别的性能调整需要对处理器的微架构有一定的了解，描述处理器实现其指令集架构的底层机制。对于乱序处理器的情况，仅了解有关功能单元的操作、能力、延迟和发射时间的一些信息就可以为预测程序性能建立基线。

我们研究了一系列技术——包括循环展开、创建多个累加器和重结合——可以利用现代处理器提供的指令级并行性。当我们深入优化时，研究生成的汇编代码并尝试理解机器如何执行计算变得很重要。通过识别程序中数据依赖性确定的关键路径，特别是在循环的不同迭代之间，可以获得很多收益。我们还可以计算计算的吞吐量界限，基于必须计算的操作数量以及执行这些操作的单元的数量和发射时间。

涉及条件分支或与内存系统的复杂交互的程序比我们首先考虑的简单循环程序更难分析和优化。基本策略是尝试使分支更可预测或使它们适合使用条件数据传输实现。我们还必须注意存储和加载操作之间的交互。将值保存在局部变量中，允许它们存储在寄存器中，通常会有所帮助。

在处理大型程序时，将优化工作集中在消耗最多时间的部分变得很重要。代码分析器和相关工具可以帮助我们系统地评估和改进程序性能。我们描述了 GPROF，一个标准的 Unix 分析工具。更复杂的分析器可用，例如来自英特尔的 VTUNE 程序开发系统，以及在 Linux 系统上通常可用的 VALGRIND。这些工具可以将执行时间分解到过程级别以下，以估计程序每个基本块的性能。（基本块是一系列指令，其中间没有控制转移，因此块总是完整执行。）
