从你第一次给处理器上电直到关闭电源，程序计数器（PC）会假定一系列的值

$$a_0, a_1, \cdots, a_{n-1}$$

其中每个 $a_k$ 是某条对应指令 $I_k$ 的地址。从 $a_k$ 到 $a_{k+1}$ 的每次转换称为控制转移（control transfer）。这样的控制转移序列称为处理器的控制流（flow of control，或 control flow）。

最简单的控制流是一种"平滑"的序列，其中每个 $I_k$ 和 $I_{k+1}$ 在内存中是相邻的。通常，对这种平滑流的突然改变——$I_{k+1}$ 不与 $I_k$ 相邻——是由我们熟悉的程序指令（如跳转、调用和返回）引起的。这类指令是允许程序对由程序变量表示的内部程序状态变化做出反应的必要机制。

但是，系统还必须能够对无法被内部程序变量捕获、且不一定与程序执行相关的系统状态变化做出反应。例如，硬件定时器以固定间隔发出信号，必须加以处理。数据包到达网络适配器，必须存储到内存中。程序从磁盘请求数据，然后休眠，直到被通知数据已就绪。创建子进程的父进程必须在子进程终止时被通知。

现代系统通过对控制流进行突然改变来响应这些情况。通常，我们将这些突然改变称为异常控制流（Exceptional Control Flow，ECF）。ECF 发生在计算机系统的所有层次。例如，在硬件层，由硬件检测到的事件触发对异常处理程序的突然控制转移。在操作系统层，内核通过上下文切换将控制权从一个用户进程转移到另一个。在应用层，一个进程可以向另一个进程发送信号，使接收方突然将控制权转移到信号处理程序。单个程序可以通过绕过通常的栈规则、向其他函数中的任意位置进行非本地跳转来对错误做出反应。

作为程序员，理解 ECF 有以下几个重要原因：

- **理解 ECF 有助于理解重要的系统概念。** ECF 是操作系统用来实现 I/O、进程和虚拟内存的基本机制。在真正理解这些重要思想之前，你需要理解 ECF。

- **理解 ECF 有助于理解应用程序如何与操作系统交互。** 应用程序通过使用一种称为陷阱（trap）或系统调用的 ECF 形式向操作系统请求服务。例如，向磁盘写入数据、从网络读取数据、创建新进程和终止当前进程，都是通过应用程序调用系统调用来完成的。理解基本的系统调用机制将帮助你理解这些服务是如何提供给应用程序的。

- **理解 ECF 将帮助你编写有趣的新应用程序。** 操作系统为应用程序提供强大的 ECF

机制，用于创建新进程、等待进程终止、向其他进程通知系统中的异常事件，以及检测和响应这些事件。如果你理解这些 ECF 机制，就可以用它们编写有趣的程序，例如 Unix shell 和 Web 服务器。

- **理解 ECF 有助于理解并发。** ECF 是在计算机系统中实现并发的基本机制。以下都是并发的实例：中断应用程序执行的异常处理程序；执行在时间上重叠的进程和线程；中断应用程序执行的信号处理程序。理解 ECF 是理解并发的第一步。我们将在第 12 章中更详细地学习并发。

- **理解 ECF 有助于理解软件异常的工作原理。** C++ 和 Java 等语言通过 `try`、`catch` 和 `throw` 语句提供软件异常机制。软件异常允许程序在响应错误条件时进行非本地跳转（即违反通常的调用/返回栈规则的跳转）。非本地跳转是应用级 ECF 的一种形式，在 C 语言中通过 `setjmp` 和 `longjmp` 函数提供。理解这些底层函数将帮助你理解如何实现更高层次的软件异常。

在你对系统的学习中，到目前为止你已经学习了应用程序如何与硬件交互。本章是关键，因为你将开始学习应用程序如何与操作系统交互。有趣的是，这些交互都围绕着 ECF 展开。我们描述了计算机系统各个层次存在的各种形式的 ECF。从处于硬件与操作系统交叉点的异常开始，还讨论了系统调用（为应用程序提供进入操作系统入口点的异常）。然后上升一个抽象层次，描述处于应用程序与操作系统交叉点的进程和信号。最后，讨论非本地跳转——这是应用级 ECF 的一种形式。

## 8.1 异常

异常（exception）是一种异常控制流形式，部分由硬件实现，部分由操作系统实现。由于部分由硬件实现，其细节因系统而异。然而，每个系统的基本思路是相同的。本节的目标是给你一个对异常和异常处理的总体理解，帮助揭开通常令人困惑的现代计算机系统的神秘面纱。

异常是响应某种处理器状态变化而发生的控制流的突然改变。图 8.1 展示了基本思路。

在图中，处理器正在执行某条当前指令 $I_{curr}$，此时处理器状态发生了重大变化。状态被编码在处理器内部的各种位和信号中。状态的这种变化称为事件（event）。

事件可能与当前指令的执行直接相关。例如，发生了虚拟内存缺页、算术溢出，或者某指令试图除以零。另一方面，事件可能与当前指令的执行无关。例如，系统定时器发出信号，或者 I/O 请求完成。

在任何情况下，当处理器检测到事件发生时，它通过一个称为异常表（exception table）的跳转表进行间接过程调用（即异常），调用专门设计用于处理此类特定事件的操作系统子程序（异常处理程序）。当异常处理程序完成处理后，根据导致异常的事件类型，会发生以下三种情况之一：

1. 处理程序将控制权返回给 $I_{curr}$，即事件发生时正在执行的指令。

2. 处理程序将控制权返回给 $I_{next}$，即如果没有发生异常本会执行的下一条指令。

3. 处理程序中止被中断的程序。

8.1.2 节将进一步讨论这些可能性。

在系统启动时（计算机被复位或上电时），操作系统分配并初始化一个称为异常表的跳转表，使条目 k 包含异常 k 的处理程序的地址。图 8.2 展示了异常表的格式。

在运行时（当系统正在执行某个程序时），处理器检测到事件已发生并确定对应的异常编号 k。然后处理器通过异常表的条目 k 进行间接过程调用，触发异常，调用相应的处理程序。图 8.3 展示了处理器如何使用异常表来形成适当异常处理程序的地址。异常编号是异常表的索引，异常表的起始地址保存在一个称为异常表基址寄存器（exception table base register）的特殊 CPU 寄存器中。

- 与过程调用一样，处理器在跳转到处理程序之前将返回地址压入栈。然而，根据异常的类别，返回地址要么是当前指令（事件发生时

正在执行的指令），要么是下一条指令（如果没有发生事件，当前指令之后本该执行的指令）。

- 处理器还将一些额外的处理器状态压入栈，当处理程序返回时，这些状态对于重启被中断的程序是必要的。例如，x86-64 系统将包含当前条件码的 EFLAGS 寄存器（以及其他内容）压入栈。

- 当控制权从用户程序转移到内核时，所有这些内容都被压入内核栈，而不是用户栈。

- 异常处理程序运行在内核模式（8.2.4 节）下，这意味着它们对所有系统资源具有完全访问权。

#### 陷阱和系统调用

陷阱（trap）是执行指令的结果而发生的有意异常。与中断处理程序一样，陷阱处理程序将控制权返回给下一条指令。陷阱最重要的用途是提供用户程序和内核之间类似过程的接口，称为系统调用（system call）。

用户程序通常需要向内核请求服务，如读取文件（`read`）、创建新进程（`fork`）、加载新程序（`execve`）和终止当前进程（`exit`）。为了允许对这些内核服务的受控访问，处理器提供了一条特殊的 `syscall n` 指令，用户程序可以在希望请求服务 n 时执行它。执行 `syscall` 指令会导致陷阱到一个异常处理程序，该处理程序解码参数并调用相应的内核例程。图 8.6 概述了系统调用的处理过程。

#### 故障

故障（fault）是由处理程序可能能够纠正的错误条件引起的。当故障发生时，处理器将控制权转移给故障处理程序。如果处理程序能够纠正错误条件，它将控制权返回给故障指令，从而重新执行它。否则，处理程序返回到内核中的中止例程，该例程终止导致故障的应用程序。图 8.7 概述了故障的处理过程。

故障的一个典型例子是缺页（page fault）异常，当指令引用虚拟地址时，其对应的页面不在内存中，必须从磁盘检索，就会发生缺页异常。正如我们将在第 9 章中看到的，页面是虚拟内存的一个连续块（通常为 4 KB）。缺页处理程序从磁盘加载适当的页面，然后将控制权返回给导致故障的指令。当指令再次执行时，适当的页面现在已在内存中，指令能够正常运行完成，不再产生故障。

#### 中止

中止（abort）是由不可恢复的致命错误引起的，通常是硬件错误，例如 DRAM 或 SRAM 位损坏时发生的奇偶校验错误。中止处理程序从不将控制权返回给应用程序。如图 8.8 所示，处理程序将控制权返回给终止应用程序的中止例程。

### 8.1.3 Linux/x86-64 系统中的异常

为了使讨论更具体，让我们看看为 x86-64 系统定义的一些异常。共有多达 256 种不同的异常类型 [50]。编号范围从 0 到 31 的异常由 Intel 架构师定义，因此在任何 x86-64 系统上都是相同的。编号范围从 32 到 255 的异常对应于由操作系统定义的中断和陷阱。图 8.9 展示了一些示例。

#### Linux/x86-64 的故障和中止

**除法错误。** 当应用程序尝试除以零，或除法指令的结果对目标操作数来说太大时，会发生除法错误（异常 0）。Unix 不尝试从除法错误中恢复，而是选择中止程序。Linux shell 通常将除法错误报告为"Floating exception"。

**一般保护故障。** 臭名昭著的一般保护故障（异常 13）由多种原因引起，通常是因为程序引用了虚拟内存的未定义区域，或者程序尝试写入只读文本段。Linux 不尝试从此故障中恢复。Linux shell 通常将一般保护故障报告为"Segmentation fault"（段错误）。

**缺页。** 缺页（异常 14）是一个故障指令被重新启动的异常示例。处理程序将虚拟内存在磁盘上的适当页面映射到物理内存的一个页面，然后重新启动故障指令。我们将在第 9 章中详细了解缺页的工作原理。

**机器检查。** 机器检查（异常 18）是在执行故障指令期间检测到致命硬件错误时发生的。机器检查处理程序从不将控制权返回给应用程序。

## 8.2 进程

异常是操作系统内核提供进程（process）概念的基本构件，进程是计算机科学中最深刻且最成功的思想之一。

当我们在现代系统上运行程序时，会感觉好像我们的程序是系统中当前唯一运行的程序。我们的程序似乎独占使用处理器和内存。处理器似乎不间断地逐条执行我们程序中的指令。最后，我们程序的代码和数据似乎是系统内存中唯一的对象。这些幻觉是由进程的概念带给我们的。

进程的经典定义是一个正在执行的程序的实例。系统中每个程序都运行在某个进程的上下文中。上下文由程序正确运行所需的状态组成。该状态包括存储在内存中的程序代码和数据、程序栈、通用寄存器的内容、程序计数器、环境变量以及已打开文件描述符的集合。

每次用户通过向 shell 输入一个可执行目标文件的名称来运行程序时，shell 都会创建一个新进程，然后在这个新进程的上下文中运行该可执行目标文件。应用程序也可以创建新进程，并在新进程的上下文中运行自己的代码或其他应用程序。

详细讨论操作系统如何实现进程超出了我们的范围。相反，我们将关注进程提供给应用程序的两个关键抽象：

- 一个独立的逻辑控制流，它提供一种假象：我们的程序独占使用处理器。

- 一个私有地址空间，它提供一种假象：我们的程序独占使用内存系统。

让我们更仔细地审视这些抽象。

### 8.2.1 逻辑控制流

进程为每个程序提供这样一种假象：即使通常有许多其他程序同时运行在系统上，它也独占使用处理器。如果我们用调试器单步跟踪程序的执行，就会观察到一系列程序计数器（PC）值，这些值只对应于我们程序的可执行目标文件中包含的指令，或在运行时动态链接到我们程序的共享对象中的指令。这个 PC 值序列称为逻辑控制流（logical control flow），或简称逻辑流。

### 8.2.2 并发流

逻辑流在计算机系统中有许多不同的形式。异常处理程序、进程、信号处理程序、线程和 Java 进程都是逻辑流的例子。

一个逻辑流，如果它的执行在时间上与另一个流重叠，则称为并发流（concurrent flow），这两个流称为并发运行。更精确地说，当且仅当 X 在 Y 开始之后且 Y 结束之前开始，或者 Y 在 X 开始之后且 X 结束之前开始时，流 X 和 Y 关于彼此是并发的。例如，在图 8.12 中，进程 A 和 B 并发运行，进程 A 和 C 也是如此。另一方面，B 和 C 不并发运行，因为 B 的最后一条指令在 C 的第一条指令之前执行。

多个流并发执行的一般现象称为并发（concurrency）。进程与其他进程轮流执行的概念也称为多任务处理（multitasking）。每次进程执行其流的一部分所经历的时间段称为时间片（time slice）。因此，多任务处理也称为时间分片（time slicing）。例如，在图 8.12 中，进程 A 的流由两个时间片组成。

注意，并发流的概念与流运行在多少个处理器核心或计算机上无关。如果两个流在时间上重叠，则它们是并发的，即使它们运行在同一个处理器上。然而，有时我们会发现识别并发流的一个特殊子集是有用的，

### 8.2.3 私有地址空间

进程为每个程序提供独占使用系统地址空间的假象。在具有 $n$ 位地址的机器上，地址空间是 $2^n$ 个可能地址的集合：0, 1, ..., $2^n - 1$。进程为每个程序提供自己的私有地址空间（private address space）。这个空间是私有的，因为地址空间中某个特定地址所关联的内存字节，通常不能被任何其他进程读取或写入。

尽管每个私有地址空间所关联的内存内容通常各不相同，但每个这样的空间具有相同的通用组织结构。例如，图 8.13 展示了 x86-64 Linux 进程地址空间的组织结构。

地址空间的底部为用户程序保留，具有通常的代码段、数据段、堆和栈段。代码段总是从地址 0x400000 开始。地址空间顶部为内核（操作系统中驻留在内存的部分）保留。这部分地址空间包含内核在代表进程执行指令时（例如，当应用程序执行系统调用时）所使用的代码、数据和栈。

### 8.2.5 上下文切换

操作系统内核使用一种称为上下文切换（context switch）的更高层次的异常控制流来实现多任务处理。上下文切换机制构建在我们在 8.1 节讨论的底层异常机制之上。

内核为每个进程维护一个上下文（context）。上下文是内核重新启动一个被抢占进程所需的状态。它由诸如通用寄存器、浮点寄存器、程序计数器、用户栈、状态寄存器、内核栈以及各种内核数据结构（如描述地址空间的页表、包含当前进程信息的进程表、包含进程已打开文件信息的文件表）等对象的值组成。

在进程执行的某些时刻，内核可以决定抢占当前进程并重新启动一个之前被抢占的进程。这个决定称为调度（scheduling），由内核中称为调度器（scheduler）的代码处理。当内核选择一个新进程来运行时，我们说内核已调度了该进程。内核调度了一个新进程来运行后，它会抢占当前进程，并使用一种称为上下文切换的机制将控制转移到新进程，该机制（1）保存当前进程的上下文，（2）恢复某个之前被抢占进程的已保存上下文，（3）将控制传递给这个新恢复的进程。

当内核正在代表用户执行系统调用时，可能发生上下文切换。如果系统调用因等待某个事件发生而阻塞，那么内核可以让当前进程进入睡眠状态并切换到另一个进程。例如，如果 read 系统调用需要磁盘访问，内核可以选择执行上下文切换并运行另一个进程，而不是等待数据从磁盘到达。另一个例子是 sleep 系统调用，它是让调用进程显式进入睡眠状态的请求。通常，即使系统调用不阻塞，内核也可以决定执行上下文切换而不是将控制返回给调用进程。

上下文切换也可能作为中断的结果而发生。例如，所有系统都有某种生成周期性定时器中断的机制，通常每 1 ms 或 10 ms 一次。每次定时器中断发生时，内核可以决定当前进程已运行足够长时间，并切换到一个新进程。

## 8.3 系统调用错误处理

当 Unix 系统级函数遇到错误时，它们通常返回 -1 并设置全局整型变量 errno 来指示出了什么问题。程序员应该总是检查错误，但遗憾的是，许多人会跳过错误检查，因为它会使代码膨胀并且更难阅读。例如，下面是调用 Linux fork 函数时检查错误的方式：

```c
if ((pid = fork()) < 0) {
    fprintf(stderr, "fork error: %s\n", strerror(errno));
    exit(0);
}
```

strerror 函数返回一个描述与特定 errno 值相关联的错误的文本字符串。我们可以通过定义以下错误报告函数来简化这段代码：

---

<!-- Page 0764 -->

```c
void unix_error(char *msg) /* Unix 风格的错误 */
{
    fprintf(stderr, "%s: %s\n", msg, strerror(errno));
    exit(0);
}
```

有了这个函数，对 fork 的调用从四行缩减为两行：

```c
1 if ((pid = fork()) < 0)
2     unix_error("fork error");
```

我们可以通过使用错误处理包装函数（error-handling wrappers）进一步简化代码，这是 Stevens 在 [110] 中首创的做法。对于给定的基函数 foo，我们定义一个包装函数 Foo，它具有相同的参数，但名称的第一个字母大写。包装函数调用基函数，检查错误，并在出现任何问题时终止。例如，以下是 fork 函数的错误处理包装：

```c
1 pid_t Fork(void)
2 {
3     pid_t pid;
4
5     if ((pid = fork()) < 0)
6         unix_error("Fork error");
7     return pid;
8 }
```

有了这个包装，对 fork 的调用缩减为一行简洁的代码：

```c
1 pid = Fork();
```

我们将在本书的其余部分使用错误处理包装函数。它们让我们的代码示例保持简洁，同时不给人留下可以忽略错误检查的错误印象。注意，当我们在正文中讨论系统级函数时，我们总是用它们的小写基础名称来引用，而不是用它们的大写包装名称。

有关 Unix 错误处理及本书中使用的错误处理包装函数的讨论，请参见附录 A。包装函数定义在名为 csapp.c 的文件中，其原型定义在名为 csapp.h 的头文件中。这些文件可以从 CS:APP 网站在线获取。

### 8.4.1 获取进程 ID

```c
#include <unistd.h>

pid_t getpid(void);

/* 返回值：调用进程或父进程的 PID */
```

getpid 和 getppid 例程返回类型为 pid_t 的整数值，在 Linux 系统中，该类型在 types.h 中定义为 int。

### 8.4.2 创建和终止进程

从程序员的角度来看，我们可以将进程视为处于以下三种状态之一：

**运行（Running）。** 进程正在 CPU 上执行，或者正在等待被执行，并将最终被内核调度。

**停止（Stopped）。** 进程的执行被挂起，不会被调度。进程因接收到 SIGSTOP、SIGTSTP、SIGTTIN 或 SIGTTOU 信号而停止，它将保持停止状态，直到接收到 SIGCONT 信号，此时它再次变为运行状态。（信号是一种软件中断，我们将在 8.5 节中详细描述。）

**终止（Terminated）。** 进程永久停止。进程因以下三种原因之一而终止：（1）收到默认行为是终止进程的信号，（2）从 main 例程返回，或（3）调用 exit 函数。

```c
#include <stdlib.h>
void exit(int status);
/* 该函数不返回 */
```

exit 函数以退出状态 status 终止进程。（设置退出状态的另一种方式是从 main 例程返回一个整数值。）

---

父进程通过调用 fork 函数来创建一个新的运行子进程。

```c
#include <sys/types.h>
#include <unistd.h>

pid_t fork(void);
/* 返回值：在子进程中返回 0，在父进程中返回子进程的 PID，出错时返回 -1 */
```

新创建的子进程几乎（但不完全）与父进程相同。子进程获得父进程用户级虚拟地址空间的一个相同（但独立的）副本，包括代码段、数据段、堆、共享库和用户栈。子进程还获得父进程所有已打开文件描述符的相同副本，这意味着子进程可以读写父进程调用 fork 时已打开的任何文件。父进程与新创建子进程之间最显著的区别是它们具有不同的 PID。

fork 函数很有趣（也常令人困惑），因为它被调用一次，但返回两次：一次在调用进程（父进程）中，一次在新创建的子进程中。在父进程中，fork 返回子进程的 PID。在子进程中，fork 返回值 0。由于子进程的 PID 始终非零，返回值提供了一种明确的方式来判断程序是在父进程还是子进程中执行。

图 8.15 展示了一个简单示例，父进程使用 fork 来创建子进程。当 fork 调用在第 6 行返回时，x 在父进程和子进程中的值都为 1。子进程在第 8 行递增并打印其 x 的副本。类似地，父进程在第 13 行递减并打印其 x 的副本。

这个简单示例有一些微妙之处。

**调用一次，返回两次。** fork 函数由父进程调用一次，但它返回两次：一次到父进程，一次到新创建的子进程。对于创建单个子进程的程序来说，这相当直接。但具有 fork 多个实例的程序可能令人困惑，需要仔细推理。

**并发执行。** 父进程和子进程是分别并发运行的进程。它们逻辑控制流中的指令可以以任意方式被内核交替执行。当我们在系统上运行该程序时，父进程先完成其 printf 语句，然后是子进程。然而，在另一个系统上可能情况相反。一般来说，作为程序员，我们永远不能假设不同进程中指令的交替顺序。

### 8.4.3 回收子进程

当一个进程由于任何原因终止时，内核不会立即将其从系统中移除。相反，进程被保留在已终止状态，直到被其父进程回收（reaped）。当父进程回收已终止的子进程时，内核将子进程的退出状态传递给父进程，然后丢弃已终止的进程，此时进程就不再存在了。一个已终止但尚未被回收的进程称为僵尸进程（zombie）。

当父进程终止时，内核安排 init 进程成为所有孤儿进程的养父进程。init 进程的 PID 为 1，在系统启动时由内核创建，永不终止，是每个进程的祖先。如果父进程在没有回收其僵尸子进程的情况下终止，那么内核安排 init 进程来回收它们。然而，长期运行的程序（如 shell 或服务器）应该总是回收其僵尸子进程。即使僵尸进程不在运行，它们仍然消耗系统内存资源。

进程通过调用 waitpid 函数来等待其子进程终止或停止。

```c
#include <sys/types.h>
#include <sys/wait.h>

pid_t waitpid(pid_t pid, int *statusp, int options);
/* 返回值：若 OK 则返回子进程的 PID，若 WNOHANG 则返回 0，出错则返回 -1 */
```

---

>**旁注 为什么已终止的子进程被称为僵尸？**
>
>在民间传说中，僵尸是一种活死人，是半活半死的存在。僵尸进程与此类似，因为尽管它已经终止，内核仍维护其部分状态，直到它能被父进程回收。

waitpid 函数比较复杂。默认情况下（当 options = 0 时），waitpid 挂起调用进程的执行，直到等待集合中的某个子进程终止。如果在调用时等待集合中已有进程终止，则 waitpid 立即返回。无论哪种情况，waitpid 都返回导致 waitpid 返回的已终止子进程的 PID。此时，已终止的子进程已被回收，内核将其所有痕迹从系统中移除。

#### 确定等待集合的成员

等待集合的成员由 pid 参数确定：

- 若 $pid > 0$，则等待集合为进程 ID 等于 $pid$ 的单个子进程。

- 若 $pid = -1$，则等待集合由父进程的所有子进程组成。

waitpid 函数还支持其他类型的等待集合，涉及 Unix 进程组，此处不作讨论。

#### 修改默认行为

可以通过将 options 设置为 WNOHANG、WUNTRACED 和 WCONTINUED 常量的各种组合来修改默认行为：

**WNOHANG。** 如果等待集合中的子进程尚未终止，则立即返回（返回值为 0）。默认行为会挂起调用进程直到某个子进程终止；当你希望在等待子进程终止的同时继续做有用的工作时，此选项很有用。

**WUNTRACED。** 挂起调用进程的执行，直到等待集合中的某个进程变为已终止或已停止状态。返回导致返回的已终止或已停止子进程的 PID。默认行为只针对已终止的子进程返回；当你想检查已终止和已停止的子进程时，此选项很有用。

**WCONTINUED。** 挂起调用进程的执行，直到等待集合中的某个运行进程被终止，或等待集合中的某个停止进程因收到 SIGCONT 信号而恢复运行。（信号在 8.5 节中解释。）

可以通过按位或将选项组合在一起。例如：

---

<!-- Page 0771 -->

**WNOHANG | WUNTRACED：** 如果等待集合中没有子进程停止或终止，则立即返回，返回值为 0；如果有已停止或已终止的子进程，则返回值等于该子进程的 PID。

#### 检查已回收子进程的退出状态

如果 statusp 参数非 NULL，则 waitpid 将关于导致返回的子进程的状态信息编码到 status 中，status 是 statusp 所指向的值。wait.h 头文件定义了几个用于解释 status 参数的宏：

**WIFEXITED(status)。** 若子进程通过调用 exit 或返回正常终止，则返回 true。

**WEXITSTATUS(status)。** 返回正常终止子进程的退出状态。只有 WIFEXITED() 返回 true 时，此状态才有定义。

**WIFSIGNALED(status)。** 若子进程因未捕获的信号而终止，则返回 true。

**WTERMSIG(status)。** 返回导致子进程终止的信号编号。只有 WIFSIGNALED() 返回 true 时，此状态才有定义。

**WIFSTOPPED(status)。** 若导致返回的子进程当前已停止，则返回 true。

**WSTOPSIG(status)。** 返回导致子进程停止的信号编号。只有 WIFSTOPPED() 返回 true 时，此状态才有定义。

**WIFCONTINUED(status)。** 若子进程因收到 SIGCONT 信号而重启，则返回 true。

#### 错误条件

如果调用进程没有子进程，则 waitpid 返回 -1 并将 errno 设置为 ECHILD。如果 waitpid 函数被信号中断，则返回 -1 并将 errno 设置为 EINTR。

### 8.4.6 利用 fork 和 execve 运行程序

Unix shell 和 Web 服务器等程序大量使用 fork 和 execve 函数。shell 是一个交互式应用级程序，代表用户运行其他程序。最初的 shell 是 sh 程序，随后出现了 csh、tcsh、ksh 和 bash 等变体。shell 执行一系列读取/求值步骤，然后终止。读取步骤从用户处读取命令行。求值步骤解析命令行并代表用户运行程序。

```c
/* eval - Evaluate a command line */
void eval(char *cmdline)
{
    char *argv[MAXARGS]; /* Argument list execve() */
    char buf[MAXLINE];   /* Holds modified command line */
    int bg;              /* Should the job run in bg or fg? */
    pid_t pid;           /* Process id */

    strcpy(buf, cmdline);
    bg = parseline(buf, argv);
    if (argv[0] == NULL)
        return; /* Ignore empty lines */

    if (!builtin_command(argv)) {
        if ((pid = Fork()) == 0) { /* Child runs user job */
            if (execve(argv[0], argv, environ) < 0) {
                printf("%s: Command not found.\n", argv[0]);
                exit(0);
            }
        }

        /* Parent waits for foreground job to terminate */
        if (!bg) {
            int status;
            if (waitpid(pid, &status, 0) < 0)
                unix_error("waitfg: waitpid error");
        }
        else
            printf("%d %s", pid, cmdline);
    }
    return;
}

/* If first arg is a builtin command, run it and return true */
int builtin_command(char **argv)
{
    if (!strcmp(argv[0], "quit")) /* quit command */
        exit(0);
    if (!strcmp(argv[0], "&"))   /* Ignore singleton & */
        return 1;
    return 0;
}
```

```c
/* parseline - Parse the command line and build the argv array */
int parseline(char *buf, char **argv)
{
    char *delim;  /* Points to first space delimiter */
    int argc;     /* Number of args */
    int bg;       /* Background job? */

    buf[strlen(buf)-1] = ' ';    /* Replace trailing '\n' with space */
    while (*buf && (*buf == ' ')) /* Ignore leading spaces */
        buf++;

    /* Build the argv list */
    argc = 0;
    while ((delim = strchr(buf, ' '))) {
        argv[argc++] = buf;
        *delim = '\0';
        buf = delim + 1;
        while (*buf && (*buf == ' ')) /* Ignore spaces */
            buf++;
    }
    argv[argc] = NULL;

    if (argc == 0) /* Ignore blank line */
        return 1;

    /* Should the job run in the background? */
    if ((bg = (*argv[argc-1] == '&')) != 0)
        argv[--argc] = NULL;

    return bg;
}
```

### 8.5.1 信号术语

将信号传递到目标进程的过程发生在两个不同的步骤中：

**发送信号。** 内核通过更新目标进程上下文中的某个状态，向目标进程发送（递交）一个信号。信号被递交的原因有两种：（1）内核检测到了系统事件，如除零错误或子进程终止。（2）进程调用了 kill 函数（在下一节讨论），显式请求内核向目标进程发送信号。进程可以向自身发送信号。

**接收信号。** 当目标进程被内核强制以某种方式对信号的递交作出反应时，目标进程接收了一个信号。进程可以忽略该信号、终止，或通过执行称为信号处理程序（signal handler）的用户级函数来捕获信号。图 8.27 展示了处理程序捕获信号的基本思路。

已被发送但尚未被接收的信号称为待处理信号（pending signal）。在任意时刻，某种特定类型的待处理信号至多只能有一个。如果一个进程有一个类型为 k 的待处理信号，则任何随后发送到该进程的类型为 k 的信号都不会排队；它们只会被丢弃。进程可以有选择地阻塞某些信号的接收。当信号被阻塞时，它可以被

### 8.5.2 发送信号

Unix 系统提供了多种向进程发送信号的机制。所有机制都依赖于进程组（process group）的概念。

#### 进程组

每个进程都恰好属于一个进程组，进程组由一个正整数进程组 ID 来标识。getpgrp 函数返回当前进程的进程组 ID。

```c
#include <unistd.h>
pid_t getpgrp(void);
/* 返回值：调用进程的进程组 ID */
```

默认情况下，子进程与其父进程属于同一进程组。进程可以使用 setpgid 函数来改变自己或其他进程的进程组：

```c
#include <unistd.h>
int setpgid(pid_t pid, pid_t pgid);
/* 返回值：成功返回 0，出错返回 -1 */
```

setpgid 函数将进程 pid 的进程组更改为 pgid。如果 pid 为零，则使用当前进程的 PID。如果 pgid 为零，则使用 pid 指定的进程的 PID 作为进程组 ID。例如，如果进程 15213 是调用进程，则

```c
setpgid(0, 0);
```

创建一个进程组 ID 为 15213 的新进程组，并将进程 15213 添加到这个新组中。

### 8.5.3 接收信号

当内核将进程 p 从内核模式切换到用户模式时（例如，从系统调用返回或完成上下文切换），它检查 p 的未阻塞待处理信号集合（pending & ~blocked）。如果该集合为空（通常情况），则内核将控制传递给 p 逻辑控制流中的下一条指令（$I_{next}$）。但是，如果集合非空，则内核选择集合中的某个信号 k（通常是最小的 k），并强制 p 接收信号 k。接收该信号会触发进程执行某种行为。一旦进程完成该行为，控制就传回 p 逻辑控制流中的下一条指令（$I_{next}$）。每种信号类型都有一个预定义的默认行为，它是以下之一：

- 进程终止。
- 进程终止并转储核心。
- 进程停止（挂起），直到被 SIGCONT 信号重启。
- 进程忽略该信号。

图 8.26 展示了与每种信号类型相关的默认行为。例如，接收 SIGKILL 的默认行为是终止接收进程。另一方面，接收 SIGCHLD 的默认行为是忽略该信号。进程可以使用 signal 函数修改与信号关联的默认行为。唯一的例外是 SIGSTOP 和 SIGKILL，它们的默认行为无法更改。

```c
#include <signal.h>
typedef void (*sighandler_t)(int);

sighandler_t signal(int signum, sighandler_t handler);
/* 返回值：若 OK 则返回指向前一个处理程序的指针，出错则返回 SIG_ERR（不设置 errno）*/
```

---

signal 函数可以通过以下三种方式之一更改与信号 signum 关联的行为：

- 如果 handler 是 SIG_IGN，则忽略类型为 signum 的信号。

- 如果 handler 是 SIG_DFL，则类型为 signum 的信号的行为恢复为默认行为。

- 否则，handler 是用户定义函数的地址，称为信号处理程序，每当进程接收到类型为 signum 的信号时就会调用该函数。通过将处理程序的地址传递给 signal 函数来更改默认行为，称为安装处理程序（installing the handler）。调用处理程序称为捕获信号（catching the signal）。处理程序的执行称为处理信号（handling the signal）。

当进程捕获类型为 k 的信号时，为信号 k 安装的处理程序会以设置为 k 的单个整数参数被调用。这个参数允许同一个处理程序函数捕获不同类型的信号。

当处理程序执行其 return 语句时，控制（通常）传回到进程因接收信号而被中断的控制流中的指令处。我们说"通常"，是因为在某些系统中，被中断的系统调用会立即以错误返回。

### 8.5.4 阻塞和解除阻塞信号

Linux 提供了隐式和显式的信号阻塞机制：

**隐式阻塞机制。** 默认情况下，内核阻塞当前由处理程序处理的类型的任何待处理信号。例如，在图 8.31 中，假设程序已捕获信号 s 并正在运行处理程序 S。如果另一个信号 s 被发送到该进程，则 s 将变为待处理状态，但在处理程序 S 返回之前不会被接收。

**显式阻塞机制。** 应用程序可以使用 sigprocmask 函数及其辅助函数来显式地阻塞和解除阻塞选定的信号。

---

<!-- Page 0791 -->

```c
#include <signal.h>

int sigprocmask(int how, const sigset_t *set, sigset_t *oldset);
int sigemptyset(sigset_t *set);
int sigfillset(sigset_t *set);
int sigaddset(sigset_t *set, int signum);
int sigdelset(sigset_t *set, int signum);
/* 返回值：若 OK 则返回 0，出错则返回 -1 */

int sigismember(const sigset_t *set, int signum);
/* 返回值：若是成员则返回 1，若不是则返回 0，出错则返回 -1 */
```

sigprocmask 函数更改当前已阻塞信号的集合（8.5.1 节中描述的 blocked 位向量）。具体行为取决于 how 的值：

**SIG_BLOCK。** 将 set 中的信号添加到 blocked（blocked = blocked | set）。

**SIG_UNBLOCK。** 从 blocked 中删除 set 中的信号（blocked = blocked & ~set）。

**SIG_SETMASK。** blocked = set。

如果 oldset 非 NULL，则 blocked 位向量的前一个值存储在 oldset 中。

信号集（如 set）通过以下函数操控：sigemptyset 将 set 初始化为空集；sigfillset 函数将每个信号添加到 set；sigaddset 函数将 signum 添加到 set，sigdelset 从 set 中删除 signum，sigismember 若 signum 是 set 的成员则返回 1，否则返回 0。

例如，图 8.32 展示了如何使用 sigprocmask 临时阻塞接收 SIGINT 信号。

```c
sigset_t mask, prev_mask;
Sigemptyset(&mask);
Sigaddset(&mask, SIGINT);
/* Block SIGINT and save previous blocked set */
Sigprocmask(SIG_BLOCK, &mask, &prev_mask);
/* Code region that will not be interrupted by SIGINT */
/* Restore previous blocked set, unblocking SIGINT */
Sigprocmask(SIG_SETMASK, &prev_mask, NULL);
```

### 8.5.5 编写信号处理程序

信号处理是 Linux 系统级编程中较为棘手的方面之一。处理程序具有几个使其难以推理的属性：（1）处理程序与主程序并发运行，并共享相同的全局变量，因此可能干扰主程序和其他处理程序。（2）信号如何以及何时被接收的规则通常是反直觉的。（3）不同的系统可能具有不同的信号处理语义。

在本节中，我们将讨论这些问题，并为你提供一些编写安全、正确且可移植的信号处理程序的基本准则。

#### 安全的信号处理

信号处理程序很棘手，因为它们可以与主程序和彼此并发运行，如图 8.31 所示。如果处理程序和主程序并发访问相同的全局数据结构，则结果可能是不可预测的，通常是致命的。

我们将在第 12 章详细探讨并发编程。这里我们的目标是给出一些保守的准则，用于编写可以安全并发运行的处理程序。如果你忽略这些准则，就有引入微妙并发错误的风险。出现此类错误时，程序大多数时候运行正确。但当它失败时，失败的方式是不可预测且不可重复的，调试起来极其困难。有备无患！

**G0. 尽可能保持处理程序简单。** 避免麻烦的最佳方法是让处理程序尽量简短且简单。例如，处理程序可以简单地设置一个全局标志然后立即返回；所有与接收信号相关的处理都由主程序执行，主程序定期检查（并重置）该标志。

**G1. 只在处理程序中调用异步信号安全的函数。** 异步信号安全（async-signal-safe）的函数，简称安全函数，具有可以从信号处理程序安全调用的属性，这是因为它是可重入的（例如，只访问局部变量；见 12.7.2 节），或者是因为它不能被信号处理程序中断。图 8.33 列出了 Linux 保证安全的系统级函数。注意，许多常用函数（如 printf、sprintf、malloc 和 exit）不在此列表中。

**G2. 保存和恢复 errno。** 许多 Linux 异步信号安全函数在出错返回时会设置 errno。在处理程序中调用此类函数可能会干扰程序中其他依赖 errno 的部分。

解决方法是在进入处理程序时将 errno 保存到一个局部变量中，并在处理程序返回之前恢复它。注意，只有在处理程序返回时才需要这样做。如果处理程序通过调用 `_exit` 终止进程，则不需要。

**G3. 通过阻塞所有信号来保护对共享全局数据结构的访问。** 如果处理程序与主程序或其他处理程序共享一个全局数据结构，则在访问（读取或写入）该数据结构时，你的处理程序和主程序应该临时阻塞所有信号。此规则的原因是：从主程序访问数据结构 d 通常需要一系列指令。如果这个指令序列被访问 d 的处理程序中断，则处理程序可能会发现 d 处于不一致状态，导致不可预测的结果。临时阻塞信号可以保证处理程序不会中断指令序列。

**G4. 用 volatile 声明全局变量。** 考虑一个共享全局变量 g 的处理程序和主例程。处理程序更新 g，main 定期读取 g。对于优化编译器来说，g 的值在 main 中似乎永远不会改变，因此使用缓存在寄存器中的 g 的副本来满足对 g 的每次引用是安全的。在这种情况下，main 函数将永远看不到来自处理程序的更新值。

你可以通过用 volatile 类型限定符声明变量来告诉编译器不要缓存该变量。例如：

```c
volatile int g;
```

volatile 限定符强制编译器在每次在代码中引用 g 时都从内存中读取 g 的值。一般来说，与任何共享数据结构一样，对全局变量的每次访问都应该通过临时阻塞信号来保护。

**G5. 用 sig_atomic_t 声明标志。** 在一种常见的处理程序设计中，处理程序通过向全局标志写入来记录信号的接收。主程序定期读取该标志，对信号作出响应，然后

#### 正确的信号处理

信号的一个反直觉方面是待处理信号不会排队。由于待处理位向量对每种类型的信号恰好包含一个位，因此任意特定类型的待处理信号至多只能有一个。因此，如果在信号 k 被阻塞（因为目标进程当前正在执行信号 k 的处理程序）时，两个类型为 k 的信号被发送到目标进程，则第二个信号被简单地丢弃；它不会排队。关键思想是：待处理信号的存在仅表明至少有一个信号已到达。

为了了解这如何影响正确性，让我们看一个在本质上类似于 shell 和 Web 服务器等真实程序的简单应用程序。基本结构是父进程创建一些子进程，这些子进程独立运行一段时间然后终止。父进程必须回收子进程以避免在系统中留下僵尸进程。但我们也希望父进程在子进程运行时能自由地执行其他工作。因此，我们决定用 SIGCHLD 处理程序来回收子进程，而不是显式等待子进程终止。（回想一下，每当其某个子进程终止或停止时，内核都会向父进程发送 SIGCHLD 信号。）

从输出中可以看出，尽管向父进程发送了三个 SIGCHLD 信号，但只接收了其中两个，因此父进程只回收了两个子进程。如果我们挂起父进程，可以看到子进程 14075 从未被回收，仍然是僵尸进程（由 ps 命令输出中的字符串 `<defunct>` 表示）：

出了什么问题？问题在于我们的代码没有考虑到信号不会排队这一事实。下面是发生的情况：第一个信号被父进程接收并捕获。当处理程序还在处理第一个信号时，第二个信号被递交并添加到待处理信号集合中。然而，由于 SIGCHLD 信号在 SIGCHLD 处理程序中被阻塞，第二个信号不会被接收。稍后，当处理程序还在处理第一个信号时，第三个信号到达。由于已经有一个待处理的 SIGCHLD，这第三个 SIGCHLD 信号被丢弃。后来，在处理程序返回后，内核注意到有一个待处理的 SIGCHLD 信号，并强制父进程接收该信号。父进程捕获信号并第二次执行处理程序。处理程序处理完第二个信号后，没有更多待处理的 SIGCHLD 信号，也不会再有，因为第三个 SIGCHLD 的所有信息都丢失了。关键教训是：信号不能用于统计其他进程中事件的发生次数。

要解决这个问题，我们必须记住：待处理信号的存在仅意味着自上次进程接收该类型信号以来，至少已递交了一个信号。因此，我们必须修改 SIGCHLD 处理程序，使其每次被调用时都尽可能多地回收

#### 可移植的信号处理

Unix 信号处理另一个令人不快的方面是，不同系统具有不同的信号处理语义。例如：

- signal 函数的语义各不相同。某些较旧的 Unix 系统在信号 k 被处理程序捕获后，会将信号 k 的行为恢复为默认值。在这些系统上，处理程序每次运行时必须通过调用 signal 来显式地重新安装自身。

- 系统调用可以被中断。read、wait 和 accept 等可能长时间阻塞进程的系统调用称为慢速系统调用（slow system calls）。在某些较旧版本的 Unix 上，当处理程序捕获信号时被中断的慢速系统调用，在信号处理程序返回后不会恢复，而是立即以错误条件返回给用户，并将 errno 设置为 EINTR。在这些系统上，程序员必须包含手动重启被中断系统调用的代码。

父进程创建新的子进程后，将子进程添加到作业列表中。当父进程在 SIGCHLD 信号处理程序中回收已终止的（僵尸）子进程时，它从作业列表中删除该子进程。

乍一看，这段代码似乎是正确的。然而，以下事件序列是可能发生的：

1. 父进程执行 fork 函数，内核调度新创建的子进程而不是父进程运行。
2. 在父进程能够再次运行之前，子进程终止并成为僵尸进程，导致内核向父进程发送 SIGCHLD 信号。
3. 后来，当父进程再次变为可运行状态但在执行之前，内核注意到待处理的 SIGCHLD，并通过在父进程中运行信号处理程序使其被接收。
4. 信号处理程序回收已终止的子进程，并调用 deletejob，由于父进程尚未将子进程添加到列表中，该调用什么都不做。
5. 处理程序完成后，内核运行父进程，父进程从 fork 返回，并通过调用 addjob 错误地将（不存在的）子进程添加到作业列表中。

因此，对于父进程的主例程和信号处理流的某些交错，deletejob 可能在 addjob 之前被调用。这导致作业列表中出现一个已经不存在且永远不会被删除的作业的错误条目。另一方面，也存在事件以正确顺序发生的交错。例如，如果内核在 fork 调用返回时恰好调度父进程而不是子进程运行，那么父进程将在子进程终止和信号处理程序从列表中删除作业之前正确地将子进程添加到作业列表中。

### 8.5.7 显式等待信号

有时主程序需要显式等待某个信号处理程序运行。例如，当 Linux shell 创建一个前台作业时，它必须等待该作业终止并被 SIGCHLD 处理程序回收，然后才接受下一个用户命令。

图 8.41 展示了基本思路。父进程为 SIGINT 和 SIGCHLD 安装处理程序，然后进入无限循环。它阻塞 SIGCHLD 以避免我们在 8.5.6 节中讨论的父子进程之间的竞态。创建子进程后，它将 pid 重置为零，解除对 SIGCHLD 的阻塞，然后在自旋循环中等待 pid 变为非零。当子进程终止时，处理程序回收它并将其非零 PID 赋给全局 pid 变量。这终止了自旋循环，父进程在开始下一次迭代之前继续执行额外的工作。

虽然这段代码是正确的，但自旋循环浪费了处理器资源。我们可能会想通过在自旋循环体中插入 pause 来解决这个问题：

```c
while (!pid)  /* Race! */
    pause();
```

注意，我们仍然需要循环，因为 pause 可能因接收到一个或多个 SIGINT 信号而被中断。然而，这段代码存在严重的竞态条件：如果 SIGCHLD 在 while 测试之后但在 pause 之前被接收，则 pause 将永远睡眠。

另一种选择是用 sleep 替换 pause：

```c
while (!pid)  /* Too slow! */
    sleep(1);
```

虽然正确，但这段代码太慢了。如果信号在 while 之后、sleep 之前被接收，程序必须等待（相对）很长时间才能再次检查循环终止条件。使用更高分辨率的睡眠函数（如 nanosleep）也不合适，因为没有好的规则来确定睡眠间隔。使其太小，循环太浪费；使其太大，程序太慢。

sigsuspend 函数临时将当前的 blocked 集合替换为 mask，然后挂起进程，直到接收到一个行为是运行处理程序或终止进程的信号。如果行为是终止，则进程终止，不从 sigsuspend 返回。如果行为是运行处理程序，则 sigsuspend 在处理程序返回后返回，将 blocked 集合恢复到调用 sigsuspend 时的状态。

```c
sigprocmask(SIG_BLOCK, &mask, &prev);
pause();
sigprocmask(SIG_SETMASK, &prev, NULL);
```

原子性保证了对 sigprocmask（第 1 行）和 pause（第 2 行）的调用是一起发生的，不会被中断。这消除了在调用 sigprocmask 之后、调用 pause 之前接收到信号的潜在竞态条件。

sigsuspend 版本比原来的自旋循环浪费更少，避免了 pause 引入的竞态条件，并且比 sleep 更高效。

setjmp 和 longjmp 之间的交互乍看起来可能令人困惑。setjmp 函数被调用一次，但返回多次：一次是 setjmp 第一次被调用时调用环境被存储在 env 缓冲区中，还有一次是对每个对应的 longjmp 调用。另一方面，longjmp 函数被调用一次，但从不返回。

非局部跳转的一个重要应用是允许从深层嵌套函数调用中立即返回，通常是作为检测到某些错误条件的结果。如果在嵌套函数调用的深处检测到错误条件，我们可以使用非局部跳转直接返回到公共的局部化错误处理程序，而不是费力地展开调用栈。

## 8.8 小结

异常控制流（ECF）发生在计算机系统的各个层次，是在计算机系统中提供并发的基本机制。

在硬件层次，异常是由处理器中的事件触发的控制流的突然变化。控制流传递给软件处理程序，处理程序执行一些处理，然后将控制返回给被中断的控制流。

异常有四种不同的类型：中断、故障、中止和陷阱。当外部 I/O 设备（如定时器芯片或磁盘控制器）设置处理器芯片上的中断引脚时，中断会异步发生（相对于任何指令）。控制返回到出错指令之后的指令。故障和中止作为指令执行的结果同步发生。故障处理程序重新执行出错指令，而中止处理程序从不将控制返回给被中断的流。最后，陷阱类似于函数调用，用于实现系统调用，为应用程序提供进入操作系统代码的受控入口点。

在操作系统层次，内核使用 ECF 来提供进程的基本概念。进程为应用程序提供两个重要的抽象：（1）逻辑控制流，使每个程序产生独占使用处理器的假象；（2）私有地址空间，使每个程序产生独占使用主存的假象。

在操作系统和应用程序之间的接口，应用程序可以创建子进程，等待子进程停止或终止，运行新程序，以及捕获来自其他进程的信号。信号处理的语义是微妙的，在不同系统之间可能有所不同。然而，在 Posix 兼容系统上存在机制，允许程序明确指定期望的信号处理语义。

最后，在应用程序层次，C 程序可以使用非局部跳转来绕过正常的调用/返回栈规范，直接从一个函数跳转到另一个函数。

### 练习题 8.7 的答案（第 800 页）

每当休眠中的进程接收到未被忽略的信号时，sleep 函数会提前返回。但由于接收到 SIGINT 的默认行为是终止进程（图 8.26），我们必须安装 SIGINT 处理程序以允许 sleep 函数返回。处理程序只需捕获信号并将控制返回给 sleep 函数，sleep 函数立即返回。

`code/ecf/snooze.c`

```c
#include "csapp.h"
/* SIGINT handler */
void handler(int sig)
{
    return; /* Catch the signal and return */
}

unsigned int snooze(unsigned int secs) {
    unsigned int rc = sleep(secs);
    printf("Slept for %d of %d secs.\n", secs - rc, secs);
    return rc;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s <secs>\n", argv[0]);
        exit(0);
    }

    if (signal(SIGINT, handler) == SIG_ERR) /* Install SIGINT */
        unix_error("signal error\n");       /* handler */
    (void)snooze(atoi(argv[1]));
    exit(0);
}
```

### 练习题 8.8 的答案（第 809 页）

这个程序打印字符串 213，这是卡内基梅隆大学 CS:APP 课程的简称。父进程首先打印 '2'，然后 fork 子进程，子进程在无限循环中自旋。父进程然后向子进程发送信号并等待其终止。子进程捕获信号（中断无限循环），将计数器（从初始值 2）递减，打印 '1'，然后终止。父进程回收子进程后，将计数器（从初始值 2）递增，打印 '3'，然后终止。
