正如我们在第 8 章中学到的，如果逻辑控制流在时间上重叠，则它们是并发的。这种普遍现象称为**并发**（concurrency），出现在计算机系统的许多不同层次中。硬件异常处理程序、进程和 Linux 信号处理程序都是我们熟悉的例子。

到目前为止，我们主要将并发视为操作系统内核用来运行多个应用程序的一种机制。但并发不仅限于内核，它在应用程序中也可以发挥重要作用。例如，我们已经看到 Linux 信号处理程序如何允许应用程序响应异步事件，例如用户键入 Ctrl+C 或程序访问虚拟内存的未定义区域。应用级并发在其他方面也很有用：

- **访问慢速 I/O 设备**。当应用程序在等待慢速 I/O 设备（如磁盘）的数据到达时，内核通过运行其他进程来让 CPU 保持忙碌。单个应用程序可以通过将有用工作与 I/O 请求重叠，以类似方式利用并发。

- **与人类交互**。与计算机交互的人需要能够同时执行多项任务。例如，他们可能希望在打印文档的同时调整窗口大小。现代窗口系统使用并发来提供此功能。每次用户请求某个操作（比如通过单击鼠标），都会创建一个单独的并发逻辑流来执行该操作。

- **通过推迟工作来减少延迟**。有时，应用程序可以使用并发，通过推迟其他操作并发执行来减少某些操作的延迟。例如，动态存储分配器可能通过将合并推迟到以较低优先级运行的并发"合并"流来减少单个 `free` 操作的延迟，利用空闲 CPU 周期来执行。

- **为多个网络客户端提供服务**。我们在第 11 章学习的迭代网络服务器是不现实的，因为它们一次只能为一个客户端提供服务。因此，一个慢速客户端可能会拒绝为所有其他客户端提供服务。对于一个可能每秒需要为数百或数千个客户端提供服务的真实服务器，不能允许一个慢速客户端拒绝为其他客户端提供服务。更好的方法是构建一个并发服务器，为每个客户端创建单独的逻辑流。这允许服务器并发地为多个客户端提供服务，并防止慢速客户端独占服务器。

- **在多核机器上并行计算**。许多现代系统配备了包含多个 CPU 的多核处理器。被划分为并发流的应用程序通常在多核机器上运行得比单处理器机器上更快，因为这些流并行执行而不是交错执行。

使用应用级并发的应用程序称为**并发程序**（concurrent programs）。现代操作系统提供三种基本方法来构建并发程序：

---

<!-- Page 0995 -->

- **进程**。使用这种方法，每个逻辑控制流都是一个由内核调度和维护的进程。由于进程具有独立的虚拟地址空间，希望相互通信的流必须使用某种显式的**进程间通信**（IPC，Interprocess Communication）机制。

- **I/O 多路复用**。这是一种并发编程形式，应用程序在单个进程的上下文中显式调度自己的逻辑流。逻辑流被建模为状态机，主程序因文件描述符上的数据到达而显式地将状态机从一个状态转移到另一个状态。由于程序是单个进程，所有流共享相同的地址空间。

- **线程**。线程是在单个进程上下文中运行并由内核调度的逻辑流。你可以将线程视为其他两种方法的混合体：像进程流一样由内核调度，并且像 I/O 多路复用流一样共享相同的虚拟地址空间。

本章将研究这三种不同的并发编程技术。为了使讨论具体，我们将在整章中使用同一个示例应用程序——第 11.4.9 节迭代式回显服务器的并发版本。

### 12.1.2 进程的优缺点

进程有一种清晰的共享状态信息模型：父子进程之间共享文件表，但不共享用户地址空间。进程具有独立的地址空间既是优点也是缺点。一个进程不可能意外覆盖另一个进程的虚拟内存，这消除了很多令人困惑的失败——这是一个明显的优点。

另一方面，独立的地址空间使进程更难共享状态信息。为了共享信息，它们必须使用显式的 IPC（进程间通信）机制（见第 1013 页的旁注）。基于进程设计的另一个缺点是它们往往较慢，因为进程控制和 IPC 的开销较高。

```c
    Signal(SIGCHLD, sigchld_handler);
    listenfd = Open_listenfd(argv[1]);

        connfd = Accept(listenfd, (SA *) &clientaddr, &clientlen);
        if (Fork() == 0) {
            Close(listenfd); /* Child closes its listening socket */
            echo(connfd);    /* Child services client */
            Close(connfd);   /* Child closes connection with client */
            exit(0);         /* Child exits */
        }
        Close(connfd); /* Parent closes connected socket (important!) */
    }
```

## 12.2 基于 I/O 多路复用的并发编程

假设你被要求编写一个回显服务器，它还可以响应用户在标准输入上键入的交互式命令。在这种情况下，服务器必须响应两个独立的 I/O 事件：（1）网络客户端发出连接请求；（2）用户在键盘上键入命令行。我们首先等待哪个事件？两种选择都不理想。如果我们在 `accept` 中等待连接请求，那么我们就无法响应输入命令。类似地，如果我们在 `read` 中等待输入命令，那么我们就无法响应任何连接请求。

解决这一两难问题的一种方法是称为 **I/O 多路复用**的技术。基本思想是使用 `select` 函数要求内核挂起进程，仅在一个或多个 I/O 事件发生后才将控制权返回给应用程序，如以下示例：

- 当集合 $\{0, 4\}$ 中的任何描述符准备好读取时返回。
- 当集合 $\{1, 2, 7\}$ 中的任何描述符准备好写入时返回。
- 如果等待 I/O 事件发生经过了 152.13 秒则超时。

`select` 是一个复杂的函数，有许多不同的使用场景。我们只讨论第一种场景：等待一组描述符准备好读取。完整的讨论见 [62, 110]。

```c
#include <sys/select.h>

int select(int n, fd_set *fdset, NULL, NULL, NULL);
/* 返回：准备好的描述符数（非零），错误时返回 -1 */

FD_ZERO(fd_set *fdset);              /* 清除 fdset 中的所有位 */
FD_CLR(int fd, fd_set *fdset);       /* 清除 fdset 中的位 fd */
FD_SET(int fd, fd_set *fdset);       /* 打开 fdset 中的位 fd */
FD_ISSET(int fd, fd_set *fdset);     /* fdset 中的位 fd 是否打开？ */
/* 操作描述符集合的宏 */
```

---

`select` 函数操作类型为 `fd_set` 的集合，这些集合称为**描述符集合**。从逻辑上讲，我们将描述符集合视为大小为 $n$ 的位向量（在第 2.1 节中介绍）：

$$b_{n-1}, \cdots, b_1, b_0$$

每个位 $b_k$ 对应描述符 $k$。当且仅当 $b_k = 1$ 时，描述符 $k$ 是描述符集合的成员。你只能对描述符集合做三件事：（1）分配它们，（2）将一种类型的变量赋值给另一个，以及（3）使用 `FD_ZERO`、`FD_SET`、`FD_CLR` 和 `FD_ISSET` 宏修改和检查它们。

对于我们的目的，`select` 函数接受两个输入：一个称为读集合的描述符集合（`fdset`）和读集合的基数（`n`，实际上是任何描述符集合的最大基数）。`select` 函数阻塞，直到读集合中至少有一个描述符准备好读取。当且仅当从该描述符读取 1 字节的请求不会阻塞时，描述符 $k$ 才准备好读取。作为副作用，`select` 修改由参数 `fdset` 指向的 `fd_set` 以指示读集合的一个子集，称为**就绪集合**，由读集合中准备好读取的描述符组成。函数返回的值表示就绪集合的基数。注意，由于副作用，我们每次调用 `select` 时都必须更新读集合。

```c
#include "csapp.h"
void echo(int connfd);
void command(void);

int main(int argc, char **argv)
{
    int listenfd, connfd;
    socklen_t clientlen;
    struct sockaddr_storage clientaddr;
    fd_set read_set, ready_set;

    if (argc != 2) {
        fprintf(stderr, "usage: %s <port>\n", argv[0]);
        exit(0);
    }
    listenfd = Open_listenfd(argv[1]);

    FD_ZERO(&read_set);                 /* Clear read set */
    FD_SET(STDIN_FILENO, &read_set);    /* Add stdin to read set */
    FD_SET(listenfd, &read_set);        /* Add listenfd to read set */

    while (1) {
        ready_set = read_set;
        Select(listenfd + 1, &ready_set, NULL, NULL, NULL);
        if (FD_ISSET(STDIN_FILENO, &ready_set))
            command(); /* Read command line from stdin */
        if (FD_ISSET(listenfd, &ready_set)) {
            clientlen = sizeof(struct sockaddr_storage);
            connfd = Accept(listenfd, (SA *)&clientaddr, &clientlen);
            echo(connfd); /* Echo client input until EOF */
            Close(connfd);
        }
    }
}

void command(void) {
    char buf[MAXLINE];
    if (!Fgets(buf, MAXLINE, stdin))
        exit(0); /* EOF */
    printf("%s", buf); /* Process the input command */
}
```

### 12.2.1 基于 I/O 多路复用的并发事件驱动服务器

I/O 多路复用可以作为并发**事件驱动**程序的基础，在这类程序中，流因某些事件而取得进展。一般思路是将逻辑流建模为状态机。非正式地说，状态机是状态、输入事件以及将状态和输入事件映射到状态的转换的集合。每个转换将一个（输入状态，输入事件）对映射到一个输出状态。自环是同一输入状态和输出状态之间的转换。状态机通常被绘制为有向图，其中节点表示状态，有向弧表示转换，弧标签表示输入事件。状态机从某个初始状态开始执行。每个输入事件触发从当前状态到下一个状态的转换。

对于每个新客户端 $k$，基于 I/O 多路复用的并发服务器创建一个新状态机 $s_k$ 并将其与已连接描述符 $d_k$ 关联。如图 12.7 所示，每个状态机 $s_k$ 有一个状态（"等待描述符 $d_k$ 准备好读取"）、一个输入事件（"描述符 $d_k$ 准备好读取"）和一个转换（"从描述符 $d_k$ 读取一行文本"）。

```c
void add_client(int connfd, pool *p)
{
    int i;
    p->nready--;
    for (i = 0; i < FD_SETSIZE; i++) /* Find an available slot */
        if (p->clientfd[i] < 0) {
            /* Add connected descriptor to the pool */
            p->clientfd[i] = connfd;
            Rio_readinitb(&p->clientrio[i], connfd);
            /* Add the descriptor to descriptor set */
            FD_SET(connfd, &p->read_set);
            /* Update max descriptor and pool high water mark */
            if (connfd > p->maxfd)
                p->maxfd = connfd;
            if (i > p->maxi)
                p->maxi = i;
            break;
        }
    if (i == FD_SETSIZE) /* Couldn't find an empty slot */
        app_error("add_client error: Too many clients");
}
```

```c
void check_clients(pool *p)

                p->clientfd[i] = -1;

        }
```

### 12.2.2 I/O 多路复用的优缺点

图 12.8 中的服务器提供了基于 I/O 多路复用的事件驱动编程优缺点的好例子。一个优点是事件驱动设计比基于进程的设计给程序员更多对程序行为的控制。例如，我们可以想象编写一个为某些客户端提供优先服务的事件驱动并发服务器，而这对于基于进程的并发服务器来说将是困难的。

另一个优点是基于 I/O 多路复用的事件驱动服务器在单个进程的上下文中运行，因此每个逻辑流都可以访问整个进程地址空间。这使得在流之间共享数据变得容易。作为单个进程运行的一个相关优点是你可以像调试任何顺序程序一样调试你的并发服务器，使用熟悉的调试工具（如 GDB）。最后，事件驱动设计通常比基于进程的设计效率高得多，因为它们不需要进程上下文切换来调度新流。

事件驱动设计的一个显著缺点是编码复杂性。我们的事件驱动并发回显服务器所需的代码量是基于进程的服务器的三倍。不幸的是，随着并发粒度的减小，复杂性会增加。所谓粒度，是指每个逻辑流每个时间片执行的指令数。例如，在我们的示例并发服务器中，并发粒度是读取整行文本所需的指令数。只要某个逻辑流忙于读取文本行，就没有其他逻辑流可以取得进展。这对我们的示例来说没问题，但它使我们的事件驱动服务器容易受到恶意客户端的攻击，该客户端只发送部分文本行然后停止。修改事件驱动服务器以处理部分文本行是一项非平凡的任务，但基于进程的设计可以干净地自动处理。基于事件设计的另一个显著缺点是它们无法充分利用多核处理器。

## 12.3 基于线程的并发编程

到目前为止，我们已经研究了创建并发逻辑流的两种方法。第一种方法，我们为每个流使用独立的进程。内核自动调度每个进程，每个进程都有自己的私有地址空间，这使得流之间共享数据变得困难。第二种方法，我们创建自己的逻辑流并使用 I/O 多路复用显式调度这些流。由于只有一个进程，流共享整个地址空间。

---

<!-- Page 1008 -->

本节介绍基于**线程**的第三种方法——这是前两种方法的混合体。

线程是在进程上下文中运行的逻辑流。到目前为止，本书中我们的程序由每个进程的单个线程组成。但现代系统也允许我们编写在单个进程中并发运行多个线程的程序。线程由内核自动调度。每个线程都有自己的**线程上下文**，包括唯一的整数**线程 ID**（TID）、栈、栈指针、程序计数器、通用寄存器和条件码。在一个进程中运行的所有线程共享该进程的整个虚拟地址空间。

基于线程的逻辑流结合了基于进程和 I/O 多路复用的流的特性。像进程一样，线程由内核自动调度，并通过整数 ID 为内核所知。像基于 I/O 多路复用的流一样，多个线程在单个进程的上下文中运行，因此它们共享整个进程虚拟地址空间的内容，包括代码、数据、堆、共享库和打开的文件。

### 12.3.1 线程执行模型

多线程的执行模型在某些方面类似于多进程的执行模型。考虑图 12.12 中的例子。每个进程以称为**主线程**的单个线程开始生命。在某个时刻，主线程创建一个**对等线程**，从此时起两个线程并发运行。最终，控制通过上下文切换传递给对等线程，这可能是因为主线程执行了慢速系统调用（如 `read` 或 `sleep`），或者被系统的时间间隔定时器中断。对等线程执行一段时间后，控制重新传回给主线程，如此往复。

线程执行在某些重要方面不同于进程。由于线程上下文比进程上下文小得多，线程上下文切换比进程上下文切换快。另一个区别是线程不像进程那样被组织成严格的父子层次结构。与进程关联的线程形成一个对等线程池。

### 12.3.4 终止线程

线程以以下方式之一终止：

- 当其顶层线程例程返回时，线程**隐式终止**。

- 线程通过调用 `pthread_exit` 函数**显式终止**。如果主线程调用 `pthread_exit`，它会等待所有其他对等线程终止，然后以 `thread_return` 的返回值终止主线程和整个进程。

```c
#include <pthread.h>
void pthread_exit(void *thread_return);
/* 永不返回 */
```

- 某个对等线程调用 Linux `exit` 函数，该函数终止进程以及与进程关联的所有线程。

- 另一个对等线程通过以当前线程的 ID 调用 `pthread_cancel` 函数来终止当前线程。

```c
#include <pthread.h>
int pthread_cancel(pthread_t tid);
/* 返回：成功时返回 0，错误时返回非零值 */
```

### 12.3.5 回收已终止的线程

线程通过调用 `pthread_join` 函数等待其他线程终止。

```c
#include <pthread.h>
int pthread_join(pthread_t tid, void **thread_return);
/* 返回：成功时返回 0，错误时返回非零值 */
```

`pthread_join` 函数阻塞直到线程 `tid` 终止，将线程例程返回的通用（`void *`）指针赋值给 `thread_return` 指向的位置，然后回收已终止线程持有的任何内存资源。

注意，与 Linux `wait` 函数不同，`pthread_join` 函数只能等待特定线程终止。没有办法指示 `pthread_join` 等待任意线程终止。这可能迫使我们使用其他不太直观的机制来检测进程终止，从而使我们的代码复杂化。事实上，Stevens 令人信服地论证这是规范中的一个缺陷 [110]。

### 12.3.6 分离线程

在任意时刻，线程是可连接的（joinable）或已分离的（detached）。可连接的线程可以被其他线程回收和杀死。其内存资源（如栈）在被另一个线程回收之前不会被释放。相反，已分离的线程不能

---

<!-- Page 1012 -->

被其他线程回收或杀死。其内存资源在终止时由系统自动释放。

默认情况下，线程被创建为可连接的。为了避免内存泄漏，每个可连接线程应该被另一个线程显式回收，或者通过调用 `pthread_detach` 函数分离。

```c
#include <pthread.h>
int pthread_detach(pthread_t tid);
/* 返回：成功时返回 0，错误时返回非零值 */
```

`pthread_detach` 函数分离可连接线程 `tid`。线程可以通过以 `pthread_self()` 作为参数调用 `pthread_detach` 来分离自身。

尽管我们的一些示例将使用可连接线程，但在真实程序中使用已分离线程有充分的理由。例如，高性能 Web 服务器可能每次从 Web 浏览器接收到连接请求时都创建一个新的对等线程。由于每个连接由独立的线程处理，服务器没有必要（实际上也不希望）显式等待每个对等线程终止。在这种情况下，每个对等线程在开始处理请求之前应该分离自身，这样在其终止后内存资源可以被回收。

### 12.4.1 线程内存模型

并发线程池在进程的上下文中运行。每个线程都有自己独立的线程上下文，包括线程 ID、栈、栈指针、

---

<!-- Page 1016 -->

程序计数器、条件码和通用寄存器值。每个线程与其他线程共享进程上下文的其余部分。这包括整个用户虚拟地址空间，由只读文本（代码）、读/写数据、堆以及任何共享库代码和数据区域组成。线程还共享相同的打开文件集合。

从操作意义上说，一个线程不可能读取或写入另一个线程的寄存器值。另一方面，任何线程都可以访问共享虚拟内存中的任何位置。如果某个线程修改了内存位置，那么如果其他线程读取该位置，它们最终都会看到变化。因此，寄存器从不共享，而虚拟内存总是共享的。

独立线程栈的内存模型没有那么清晰。这些栈包含在虚拟地址空间的栈区域中，通常由各自的线程独立访问。我们说"通常"而非"总是"，是因为不同线程的栈不受其他线程的保护。因此，如果线程以某种方式获得了指向另一个线程栈的指针，那么它就可以读写该栈的任何部分。我们的示例程序在第 26 行展示了这一点，对等线程通过全局 `ptr` 变量间接引用主线程栈的内容。

### 12.4.2 变量到内存的映射

线程化 C 程序中的变量根据其存储类别映射到虚拟内存：

**全局变量**。全局变量是在函数外部声明的任何变量。在运行时，虚拟内存的读/写区域恰好包含每个全局变量的一个实例，可以被任何线程引用。例如，第 5 行声明的全局变量 `ptr` 在虚拟内存的读/写区域中有一个运行时实例。当变量只有一个实例时，我们直接用变量名表示该实例——在本例中为 `ptr`。

**局部自动变量**。局部自动变量是在函数内部声明且没有 `static` 属性的变量。在运行时，每个线程的栈包含任何局部自动变量的自己的实例。即使多个线程执行相同的线程例程，这也是成立的。例如，局部变量 `tid` 有一个实例，它驻留在主线程的栈上。我们将这个实例表示为 `tid.m`。另一个例子，局部变量 `myid` 有两个实例，一个在对等线程 0 的栈上，另一个在对等线程 1 的栈上。我们分别将这些实例表示为 `myid.p0` 和 `myid.p1`。

**局部静态变量**。局部静态变量是在函数内部用 `static` 属性声明的变量。与全局变量一样，虚拟内存的读/写区域恰好包含程序中声明的每个局部静态变量的一个实例。

---

例如，即使我们示例程序中的每个对等线程都在第 25 行声明了 `cnt`，但在运行时，在虚拟内存的读/写区域中只有 `cnt` 的一个实例。每个对等线程都读写这个实例。

### 12.4.3 共享变量

当且仅当变量 $v$ 的某个实例被多个线程引用时，我们说变量 $v$ 是**共享的**。例如，我们示例程序中的变量 `cnt` 是共享的，因为它只有一个运行时实例，且这个实例被两个对等线程引用。另一方面，`myid` 不是共享的，因为其两个实例中的每一个都只被一个线程引用。但是，重要的是要认识到，局部自动变量（如 `msgs`）也可以是共享的。

## 12.5 用信号量同步线程

共享变量很方便，但它们引入了令人讨厌的同步错误的可能性。考虑图 12.16 中的 `badcnt.c` 程序，它创建两个线程，每个线程都递增一个名为 `cnt` 的全局共享计数器变量。

### 12.5.1 进度图

进度图将 $n$ 个并发线程的执行建模为在 $n$ 维笛卡尔空间中的轨迹。每个轴 $k$ 对应线程 $k$ 的进度。每个点 $(I_1, I_2, \ldots, I_n)$ 表示线程 $k$（$k = 1, \ldots, n$）已经完成指令 $I_k$ 的状态。图的原点对应于还没有线程完成任何指令的初始状态。

图 12.19 展示了 `badcnt.c` 程序第一次循环迭代的二维进度图。水平轴对应线程 1，垂直轴对应线程 2。点 $(L_1, S_2)$ 对应线程 1 已完成 $L_1$，线程 2 已完成 $S_2$ 的状态。

进度图将指令执行建模为从一个状态到另一个状态的转换。转换表示为从一个点到相邻点的有向边。合法的转换向右（线程 1 中的指令完成）或向上（线程 2 中的指令完成）移动。两条指令不能同时完成——对角线转换是不允许的。程序从不向后运行，因此向下或向左移动的转换也是不合法的。

### 12.5.2 信号量

Edsger Dijkstra，并发编程的先驱，提出了一种基于特殊类型变量（称为**信号量**）的经典解决方案，用于同步不同执行线程。信号量 $s$ 是一个具有非负整数值的全局变量，只能通过两种特殊操作来操纵，称为 P 和 V：

$P(s)$：如果 $s$ 非零，则 $P$ 将 $s$ 减一并立即返回。如果 $s$ 为零，则挂起该线程，直到 $s$ 变为非零，并由 $V$ 操作重启线程。重启后，$P$ 操作将 $s$ 减一并将控制权返回给调用者。

$V(s)$：$V$ 操作将 $s$ 加一。如果有任何线程在 $P$ 操作处阻塞，等待 $s$ 变为非零，则 $V$ 操作将重启其中恰好一个线程，该线程随即通过将 $s$ 减一来完成其 $P$ 操作。

---

<!-- Page 1024 -->

> **旁注：P 和 V 名称的由来**
>
> Edsger Dijkstra（1930–2002）最初来自荷兰。P 和 V 这两个名字来源于荷兰语单词 proberen（测试）和 verhogen（递增）。

$P$ 中的测试和递减操作是不可分割的，即一旦信号量 $s$ 变为非零，$s$ 的递减操作便会不受打断地完成。$V$ 中的递增操作也是不可分割的，它会不受打断地完成加载、递增和存储信号量的操作。注意，$V$ 的定义并未规定等待线程被重启的顺序。唯一的要求是 $V$ 必须恰好重启一个等待线程。因此，当多个线程在信号量处等待时，无法预测哪个线程会因 $V$ 操作而被重启。

$P$ 和 $V$ 的定义保证了一个正在运行的程序永远不会进入一个正确初始化的信号量具有负值的状态。这一属性称为**信号量不变式**，为控制并发程序的轨迹提供了强有力的工具，我们将在下一节看到。

POSIX 标准定义了多种用于操作信号量的函数。

```c
#include <semaphore.h>

int sem_init(sem_t *sem, 0, unsigned int value);
int sem_wait(sem_t *s); /* P(s) */
int sem_post(sem_t *s); /* V(s) */
Returns: 0 if OK, -1 on error
```

`sem_init` 函数将信号量 `sem` 初始化为 `value`。每个信号量在使用之前都必须初始化。在我们的使用场景中，中间参数始终为 0。程序通过调用 `sem_wait` 和 `sem_post` 函数分别执行 P 和 V 操作。为了简洁，我们倾向于使用以下等价的 P 和 V 包装函数：

```c
#include "csapp.h"

void P(sem_t *s);    /* sem_wait 的包装函数 */
void V(sem_t *s);    /* sem_post 的包装函数 */
Returns: nothing
```

### 12.5.3 使用信号量实现互斥

信号量提供了一种便捷的方式来确保对共享变量的互斥访问。基本思路是为每个共享变量（或相关共享变量集合）关联一个初始值为 1 的信号量 $s$，

<!-- Page 1025 -->

<div style="text-align: center;"><img src="imgs/img_in_chart_box_71_6_1566_1025.jpg" alt="Image" width="76%" /></div>

<div style="text-align: center;">图 12.22 使用信号量实现互斥。$s < 0$ 的不可行状态定义了一个禁止区域，该区域包围着不安全区域，防止任何可行轨迹触碰到不安全区域。</div>

然后用 $P(s)$ 和 $V(s)$ 操作包围相应的临界区。

以这种方式用于保护共享变量的信号量称为**二元信号量**（binary semaphore），因为它的值始终为 0 或 1。目的是提供互斥的二元信号量通常称为**互斥锁**（mutex）。对互斥锁执行 P 操作称为**加锁**，执行 V 操作称为**解锁**。已加锁但尚未解锁互斥锁的线程称为**持有**该互斥锁。用作一组可用资源计数器的信号量称为**计数信号量**。

图 12.22 中的进度图展示了如何使用二元信号量来正确同步我们的计数器示例程序。

每个状态都标有该状态下信号量 $s$ 的值。关键思想是，P 和 V 操作的组合创建了一组状态，称为**禁止区域**（forbidden region），其中 $s < 0$。由于信号量不变式，任何可行轨迹都不能包含禁止区域中的状态。而由于禁止区域完全包围了不安全区域，任何可行轨迹都不能触碰不安全区域的任何部分。因此，每条可行轨迹都是安全的，无论运行时指令的排列顺序如何，程序都能正确地递增计数器。

---

<!-- Page 1026 -->

> **旁注：进度图的局限性**
>
> 进度图为我们提供了一种在单处理器上可视化并发程序执行并理解为何需要同步的好方法。然而，它们确实存在局限性，尤其是在多处理器的并发执行方面——多处理器中，一组 CPU/高速缓存共享同一主内存。多处理器的行为方式无法用进度图来解释。特别是，多处理器的内存系统可能处于一种与进度图中任何轨迹都不对应的状态。尽管如此，结论依然不变：无论在单处理器还是多处理器上运行，都要始终同步对共享变量的访问。

从操作角度来看，P 和 V 操作创建的禁止区域使得多个线程在任何时刻都不可能同时执行被包围的临界区中的指令。换言之，信号量操作确保了对临界区的互斥访问。

综合起来，要使用信号量正确同步图 12.16 中的计数器示例程序，我们首先声明一个名为 `mutex` 的信号量：

```c
volatile long cnt = 0; /* 计数器 */
sem_t mutex;           /* 保护计数器的信号量 */
```

然后在主例程中将其初始化为 1：

```c
Sem_init(&mutex, 0, 1); /* mutex = 1 */
```

最后，通过在线程例程中用 P 和 V 操作包围共享变量 `cnt` 的更新来保护它：

```c
for (i = 0; i < niters; i++) {
    P(&mutex);
    cnt++;
    V(&mutex);
}
```

当我们运行正确同步的程序时，它每次都能产生正确的结果：

```
linux>./goodcnt 1000000
OK cnt=2000000

linux>./goodcnt 1000000
OK cnt=2000000
```

**生产者-消费者问题**

图 12.23 展示了生产者-消费者问题。生产者线程和消费者线程共享一个具有 $n$ 个槽位的有界缓冲区。生产者线程反复生成新条目并将其插入缓冲区，消费者线程反复从缓冲区中取出条目并消费（使用）它们。具有多个生产者和消费者的变体也是可能的。

由于插入和删除条目都涉及更新共享变量，因此我们必须保证对缓冲区的互斥访问。但仅保证互斥还不够，我们还需要调度对缓冲区的访问。如果缓冲区已满（没有空槽位），生产者必须等待直到有槽位可用；类似地，如果缓冲区为空（没有可用条目），消费者必须等待直到有条目可用。

生产者-消费者交互在实际系统中频繁发生。例如，在多媒体系统中，生产者可能编码视频帧，而消费者则解码并在屏幕上渲染它们。缓冲区的目的是减少由单个帧编解码时间差异引起的视频流抖动。缓冲区为生产者提供槽位储备，为消费者提供已编码帧的储备。另一个常见的例子是图形用户界面的设计。生产者检测鼠标和键盘事件并将它们插入缓冲区，消费者以某种基于优先级的方式从缓冲区中取出事件并更新屏幕。

在本节中，我们将开发一个名为 SBUF 的简单包，用于构建生产者-消费者程序。在下一节中，我们将看到如何使用它来构建一个基于预线程化的有趣并发服务器。SBUF 操作 `sbuf_t` 类型的有界缓冲区（图 12.24）。条目存储在一个动态分配的整数数组（`buf`）中，最多存放 $n$ 个条目。`front` 和 `rear` 索引追踪数组中第一个和最后一个条目。三个信号量同步对缓冲区的访问：`mutex` 信号量提供互斥的缓冲区访问，`slots` 和 `items` 是计数信号量，分别计算空槽位数和可用条目数。

**读者-写者问题**

读者-写者问题是互斥问题的一般化。一组并发线程访问一个共享对象，例如主内存中的数据结构或磁盘上的数据库。某些线程只读取该对象，而其他线程则修改它。修改对象的线程称为**写者**，只读取对象的线程称为**读者**。写者必须对对象拥有独占访问权，但读者可以与无限数量的其他读者共享对象。一般来说，并发读者和写者的数量是无限的。

```c
#include "csapp.h"
#include "sbuf.h"

/* 创建一个空的、有界的、共享的 FIFO 缓冲区，具有 n 个槽位 */
void sbuf_init(sbuf_t *sp, int n)
{
    sp->buf = Calloc(n, sizeof(int));
    sp->n = n;
    sp->front = sp->rear = 0;
    Sem_init(&sp->mutex, 0, 1);
    Sem_init(&sp->slots, 0, n);
    Sem_init(&sp->items, 0, 0);
}

/* 清理缓冲区 sp */
void sbuf_deinit(sbuf_t *sp)
{
    Free(sp->buf);
}

/* 将条目插入共享缓冲区 sp 的尾部 */
void sbuf_insert(sbuf_t *sp, int item)
{
    P(&sp->slots);
    P(&sp->mutex);
    sp->buf[(++sp->rear)%(sp->n)] = item;
    V(&sp->mutex);
    V(&sp->items);
}

/* 从缓冲区 sp 中移除并返回第一个条目 */
int sbuf_remove(sbuf_t *sp)
{
    int item;
    P(&sp->items);
    P(&sp->mutex);
    item = sp->buf[(++sp->front)%(sp->n)];
    V(&sp->mutex);
    V(&sp->slots);
    return item;
}
```

读者-写者交互在实际系统中频繁出现。例如，在在线航空预订系统中，无限数量的顾客可以并发查看座位分配，但正在预订座位的顾客必须独占访问数据库。另一个例子是多线程缓存 Web 代理：无限数量的线程可以从共享页面高速缓存中获取已有页面，但向高速缓存写入新页面的线程必须独占访问。

读者-写者问题有几种变体，每种变体基于读者和写者的不同优先级。**第一读者-写者问题**（favors readers，偏向读者）要求，除非写者已获准使用对象，否则不得让读者等待。换言之，不应仅因有写者在等待就让读者等待。**第二读者-写者问题**（favors writers，偏向写者）要求，一旦写者准备好写入，就应尽快执行写操作。与第一个问题不同，写者到来后到达的读者必须等待，即使写者也在等待。

图 12.26 展示了第一读者-写者问题的解法。与许多同步问题的解法一样，它微妙而看似简单。信号量 `w` 控制对访问共享对象的临界区的访问。信号量 `mutex` 保护对共享变量 `readcnt` 的访问，`readcnt` 计算当前处于临界区的读者数量。写者每次进入临界区时加锁 `w`，每次离开时解锁。这保证了任何时刻临界区中最多只有一个写者。另一方面，只有第一个进入临界区的读者加锁 `w`，只有最后一个离开临界区的读者解锁 `w`。当其他读者存在时进入或离开的读者会忽略 `w` 互斥锁。这意味着，只要有一个读者持有 `w` 互斥锁，无限数量的读者都可以不受阻碍地进入临界区。

对读者-写者任何一个问题的正确解法都可能导致**饥饿**（starvation），即某个线程无限期地阻塞而无法继续执行。例如，在图 12.26 的解法中，写者可能在持续到来的读者流中无限等待。

## 12.6 使用线程实现并行

到目前为止，在我们对并发的学习中，我们假设并发线程在单处理器系统上执行。然而，大多数现代机器都有多核处理器。并发程序通常在这类机器上运行得更快，因为操作系统内核会将并发线程并行调度到多个核心上，而不是在单个核心上顺序执行。在繁忙的 Web 服务器、数据库服务器和大型科学代码等应用中，充分利用这种并行性至关重要；对于 Web 浏览器、电子表格和文档处理器等主流应用，它也变得越来越有用。

图 12.30 展示了顺序程序、并发程序和并行程序之间的集合关系。所有程序的集合可以划分为顺序程序和并发程序两个不相交的子集。顺序程序编写为单一逻辑流，并发程序编写为多个并发流，并行程序是在多个处理器上运行的并发程序。因此，并行程序集合是并发程序集合的真子集。

对并行程序的详细讨论超出了我们的范围，但研究几个简单的示例程序将帮助我们理解并行编程的一些重要方面。例如，考虑如何并行地对整数序列 $0, \ldots, n-1$ 求和。当然，对于这个特定的问题存在闭合形式的解，但它仍然是一个简洁易懂的典型例子，让我们能够就并行程序做出一些有趣的论述。

```c
    for (i = 0; i < nthreads; i++) {
        myid[i] = i;
        Pthread_create(&tid[i], NULL, sum_mutex, &myid[i]);
    }
    for (i = 0; i < nthreads; i++)
        Pthread_join(tid[i], NULL);

    /* 检验最终答案 */
    if (gsum != (nelems * (nelems-1))/2)
        printf("Error: result=%ld\n", gsum);
    exit(0);
}
```

尽管绝对运行时间是衡量任何程序性能的最终标准，但一些有用的相对度量可以提供有关并行程序利用潜在并行性程度的洞察。并行程序的**加速比**通常定义为

$$S_{p}=\frac{T_{1}}{T_{p}}$$

其中 $p$ 是处理器核心数，$T_{k}$ 是在 $k$ 个核心上的运行时间。这种表述有时称为**强缩放**（strong scaling）。当 $T_{1}$ 是程序的顺序版本的执行时间时，$S_{p}$ 称为**绝对加速比**；当 $T_{1}$ 是并行版本在一个核心上的执行时间时，$S_{p}$ 称为**相对加速比**。

绝对加速比是比相对加速比更真实的并行性收益度量。并行程序通常会遭受同步开销，即使在单处理器上运行时也是如此，这些开销会人为地夸大相对加速比数字，因为它们增大了分子。另一方面，绝对加速比比相对加速比更难测量，因为测量绝对加速比需要程序的两个不同版本。对于复杂的并行代码，创建单独的顺序版本可能不可行，原因是代码太复杂或没有源代码可用。

一个相关度量称为**效率**，定义为

$$E_{p}=\frac{S_{p}}{p}=\frac{T_{1}}{pT_{p}}$$

通常以 (0, 100] 范围内的百分比报告。效率是由于并行化而产生的开销的度量。高效率的程序比低效率的程序花费更多时间做有用工作，花费更少时间同步和通信。

图 12.36 展示了我们示例并行求和程序的不同加速比和效率度量。90% 以上的效率非常好，但不要被迷惑。我们能够实现高效率，是因为我们的问题极易并行化。在实践中，通常并非如此。并行编程几十年来一直是活跃的研究领域。随着商品多核机器（其核心数每隔几年翻倍）的出现，并行编程仍然是一个深刻、困难且活跃的研究领域。

加速比还有另一种视角，称为**弱缩放**（weak scaling），它在增加处理器数量的同时也增大问题规模，使得随着处理器数量的增加，每个处理器执行的工作量保持不变。在这种表述下，加速比和效率用每单位时间完成的总工作量来表示。例如，如果我们能将处理器数量翻倍，每小时完成两倍的工作，那么我们就享有线性加速比和 100% 的效率。

弱缩放通常比强缩放更能真实反映实际情况，因为它更准确地体现了我们希望使用更大机器完成更多工作的愿望。对于科学计算代码来说尤其如此，在这些代码中，问题规模可以轻松增大，更大的问题规模直接转化为对自然界更好的预测。然而，有些应用的规模不那么容易增大，对于这些应用，强缩放更为适用。例如，实时信号处理应用执行的工作量通常由产生信号的物理传感器的属性决定。改变总工作量需要使用不同的物理传感器，这可能不可行或没有必要。对于这些应用，我们通常希望利用并行性尽可能快速地完成固定数量的工作。

## 12.7 其他并发问题

你可能已经注意到，一旦需要同步对共享数据的访问，事情就变得复杂得多。到目前为止，我们已经研究了互斥和生产者-消费者同步的技术，但这只是冰山一角。同步是一个从根本上就困难的问题，它引发了顺序程序中根本不会出现的问题。本节是对编写并发程序时需要注意的一些问题的概述（绝非完整）。为了具体起见，我们将把讨论置于线程的背景下。但请记住，这些问题对于任何类型的并发流操纵共享资源时都是典型的。

### 12.7.1 线程安全

当我们使用线程编程时，必须注意编写具有**线程安全**属性的函数。如果且仅当一个函数被多个并发线程反复调用时始终能产生正确结果，则称其为**线程安全的**（thread-safe）。如果一个函数不是线程安全的，则称其为**线程不安全的**（thread-unsafe）。

我们可以识别出四类（非互斥的）线程不安全函数：

**第 1 类：不保护共享变量的函数。**我们已经在图 12.16 的线程函数中遇到过这个问题，该函数

**第 2 类：在多次调用之间保持状态的函数。**伪随机数生成器是这类线程不安全函数的简单示例。考虑图 12.37 中的伪随机数生成器包。

`rand` 函数是线程不安全的，因为当前调用的结果依赖于上一次迭代的中间结果。当我们在单个线程中以 `srand` 调用设置种子后反复调用 `rand` 时，可以期待得到一个可重复的数字序列。然而，如果多个线程都在调用 `rand`，这个假设便不再成立。

使 `rand` 这样的函数变为线程安全的唯一方法是重写它，使其不使用任何静态数据，而是依靠调用者在参数中传递状态信息。缺点是程序员现在被迫同时修改调用例程中的代码。在一个可能有数百个不同调用点的大型程序中，进行这样的修改可能既繁琐又容易出错。

处理这类线程不安全函数有两种方式。一种是重写函数，让调用者传递存储结果的变量地址，这消除了所有共享数据，但需要程序员能访问函数源代码。

如果线程不安全函数难以或无法修改（例如代码非常复杂或没有源代码），则另一种方法是使用**加锁-复制**（lock-and-copy）技术。基本思路是为线程不安全函数关联一个互斥锁。在每个调用点，加锁互斥锁，调用线程不安全函数，将函数返回的结果复制到私有内存位置，然后解锁互斥锁。为了尽量减少对调用者的修改，应该定义一个执行加锁-复制的线程安全包装函数，然后用对包装函数的调用替换所有对线程不安全函数的调用。例如，图 12.38 展示了一个使用加锁-复制技术的 `ctime` 线程安全包装函数。

### 12.7.2 可重入性

有一类重要的线程安全函数，称为**可重入函数**（reentrant functions），其特点是在被多个线程调用时不引用任何共享数据。尽管"线程安全"和"可重入"这两个术语有时被（错误地）用作同义词，但它们之间存在值得保留的明确技术区别。图 12.39 展示了可重入函数、线程安全函数和线程不安全函数之间的集合关系。所有函数的集合被划分为线程安全和线程不安全两个不相交的子集。可重入函数集合是线程安全函数的真子集。

可重入函数通常比非可重入的线程安全函数更高效，因为它们不需要任何同步操作。此外，将第 2 类线程不安全函数转换为线程安全函数的唯一方法就是将其重写为可重入函数。例如，图 12.40 展示了图 12.37 中 `rand` 函数的可重入版本。关键思路是我们将静态变量 `next` 替换为由调用者传入的指针。

是否可以通过检查某个函数的代码先验地宣告它是可重入的呢？遗憾的是，这取决于具体情况。如果所有函数参数都是按值传递的（即没有指针），并且所有数据引用都是对局部自动栈变量的（即没有对静态或全局变量的引用），则该函数是**显式可重入的**（explicitly reentrant），我们可以断言其可重入性，而不管它如何被调用。

然而，如果我们稍微放宽假设，允许在其他方面是显式可重入的函数中某些参数按引用传递（即允许传递指针），则我们得到的是**隐式可重入函数**（implicitly reentrant function），即只有当调用线程谨慎地传递指向

---

<!-- Page 1046 -->

非共享数据的指针时，该函数才是可重入的。例如，图 12.40 中的 `rand_r` 函数是隐式可重入的。

我们始终使用"可重入"这个术语来涵盖显式和隐式可重入函数。然而，重要的是要认识到，可重入性有时是调用者和被调用者共同的属性，而不仅仅是被调用者单方面的属性。

### 12.7.4 竞态条件

当程序的正确性依赖于一个线程在某个控制流点 $x$ 处到达的时间早于另一个线程在点 $y$ 处到达时，就会发生**竞态条件**（race）。竞态条件通常发生在程序员假设线程会在执行状态空间中沿某个特定轨迹运行时，而忘记了黄金法则：线程化程序必须对任何可行轨迹都能正确工作。

### 12.7.5 死锁

信号量引入了一种危险的运行时错误，称为**死锁**（deadlock），即一组线程被阻塞，等待一个永远不会变为真的条件。进度图是理解死锁的宝贵工具。例如，图 12.44 展示了一对使用两个信号量实现互斥的线程的进度图。从这张图中，我们可以获得一些关于死锁的重要见解：

- 程序员错误地排列了 P 和 V 操作，使得两个信号量的禁止区域发生重叠。如果某个执行轨迹碰巧到达死锁状态 $d$，则不可能有进一步的

- 重叠的禁止区域导出了一组称为**死锁区域**的状态。如果一条轨迹碰巧触碰死锁区域中的某个状态，则死锁是不可避免的。轨迹可以进入死锁区域，但永远无法离开。

## 12.8 小结

并发程序由一组在时间上重叠的逻辑流组成。在本章中，我们研究了构建并发程序的三种不同机制：进程、I/O 多路复用和线程。我们始终以并发网络服务器作为驱动应用。

进程由内核自动调度，由于其独立的虚拟地址空间，它们需要显式的 IPC 机制来共享数据。事件驱动程序创建自己的并发逻辑流，这些流被建模为状态机，并使用 I/O 多路复用来显式调度这些流。由于程序在单个进程中运行，流之间的数据共享快速而简便。线程是这两种方法的混合体。与基于进程的流一样，线程由内核自动调度；与基于 I/O 多路复用的流一样，线程在单个进程的上下文中运行，因此可以快速而方便地共享数据。

无论采用哪种并发机制，同步对共享数据的并发访问都是一个困难的问题。信号量上的 P 和 V 操作是为了帮助处理这一问题而开发的。信号量操作可用于提供对共享数据的互斥访问，以及调度对资源的访问，例如生产者-消费者系统中的有界缓冲区和读者-写者系统中的共享对象。并发预线程化回显服务器提供了信号量这些使用场景的生动示例。

并发还引入了其他困难问题。被线程调用的函数必须具有称为线程安全的属性。我们识别了四类线程不安全函数，并提出了使其变为线程安全的建议。可重入函数是线程安全函数的真子集，它们不访问任何共享数据。可重入函数通常比非可重入函数更高效，因为它们不需要任何同步原语。并发程序中出现的其他一些困难问题是竞态条件和死锁。竞态条件发生在程序员对逻辑流如何调度做出错误假设时，死锁发生在某个流等待一个永远不会发生的事件时。

如果我们在第 14 行调用 `pthread_create` 之后立即在主线程中释放内存块，则会引入一个新的竞态，这次发生在主线程中的 `free` 调用与线程例程第 24 行的赋值语句之间。

**练习题 12.14 解答（第 1062 页）**

A. 另一种方法是直接传递整数 `i`，而不是传递指向 `i` 的指针：

```c
for (i = 0; i < N; i++)
    Pthread_create(&tid[i], NULL, thread, (void *)i);
```

在线程例程中，我们将参数转换回 `int` 并赋值给 `myid`：

```c
int myid = (int) vargp;
```

B. 优点是通过消除对 `malloc` 和 `free` 的调用来减少开销。一个重要的缺点是它假设指针的大小至少与 `int` 相同。虽然这在所有现代系统上都成立，但在遗留系统或未来系统上可能不成立。
